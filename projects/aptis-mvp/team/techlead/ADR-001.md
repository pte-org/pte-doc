# ADR-001: Simplified layered architecture over full DDD bounded contexts for the 1-week MVP
**Date:** 2026-06-21
**Status:** Accepted — **AMENDED by ADR-005 (2026-06-21)**: the MVP is now built inside the production aptis-lms repos using the full DDD bounded-context structure (scoped to 6 contexts), not a simplified layered monolith. Read ADR-005 + mvp-slice-mapping.md before this document.

## Context
The project's `.project-config.md` sets `level: senior`, whose default recommended style per the TechLead level-calibration table is "DDD + Clean Architecture — bounded contexts, full domain model." However, the operator's explicit context for this MVP states: a 4-person full-stack generalist team (no dedicated FE/BE specialists), a 7-day delivery window, and an explicit preference for "the simplest architecture that can actually run" — one backend monolith, one frontend web app, one database, no DB-level multi-tenant RLS, no background job queue. The BA scope itself (`requirements.md`) is a single linear flow across 19 REQs and 15 user stories, not a multi-subdomain system. Applying full DDD bounded contexts here would impose ceremony (aggregate roots, domain events, anti-corruption layers between contexts) that 4 generalists cannot safely execute correctly in 7 days, and that the BA scope does not structurally require.

## Decision
We will use a simplified layered architecture inside a single NestJS monolith — Controller → Service → Repository per feature module (auth, host, roster-import, exam, exam-attempt) — instead of full DDD bounded contexts. Modules are organized by feature area for clarity, but there is no enforced domain/infrastructure layer separation beyond Prisma as the repository implementation, and no domain event bus.

## Consequences
### Positive
- Every task in the upcoming PM task-breakdown maps to a single module a generalist can build start-to-finish without cross-team handoff.
- No time spent building DDD scaffolding (aggregate boundaries, domain events) that has no consumer in a 1-week scope.
- Easier code review for 4 peers with equal context, since there's one consistent pattern across all modules.

### Negative / Trade-offs
- If APTIS MVP scope grows post-pilot toward the full 111-FR `aptis-lms` system, this codebase is not a direct stepping stone — the full system's TechLead artifacts (under `projects/aptis-lms/team/techlead/`) already specify DDD bounded contexts, so a future migration is expected, not avoided.
- Cross-cutting concerns (e.g., host_id scoping) are enforced by convention (a shared repository helper) rather than structurally impossible to bypass, raising the risk addressed in ADR-003.

### Risks
- Risk: a developer bypasses the shared host-scoping helper and writes a raw Prisma query missing the `host_id` filter, causing a BR-005 violation. Mitigation: code review checklist item + the cross-tenant threat flagged in architecture.md Security Architecture section.
- Risk: this deviation from the level-recommended style could be miscalibrated for the team's actual senior-level skill (the `level: senior` may reflect skill depth, not available time). Mitigation: this ADR documents the deviation explicitly so it can be revisited if the 7-day constraint changes.

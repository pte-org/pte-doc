# ADR-003: Stateless JWT auth with three roles, app-layer host_id scoping, no DB Row-Level Security
**Date:** 2026-06-21
**Status:** Accepted — **AMENDED by ADR-005 (2026-06-21)**: host scoping is enforced at the repository layer with **RLS deferred-but-planned** (not ruled out forever); the iam token port stays refresh-shaped. Read ADR-005 first.

## Context
The system has three distinct actor types (Admin, Host, Student) each needing authentication, and Host/Student data must be strictly isolated per BR-005. BA `requirements.md` Assumption 5 explicitly states multi-tenant isolation is assumed to be enforced at the application layer, not via database Row-Level Security, for this MVP — a deliberate scope reduction the operator confirmed when commissioning this TechLead pass ("không cần multi-tenant RLS phức tạp"). True Postgres RLS policies would require per-table `CREATE POLICY` definitions and a session-variable-setting strategy on every connection, which is additional infrastructure the 7-day timeline does not budget for.

## Decision
We will use stateless JWT access tokens (no refresh-token rotation in MVP) issued at login for all three roles, with a `role` and (for Host/Student) `hostId` claim embedded in the token. Authorization is enforced via a NestJS Guard that reads these claims, and every repository method touching Host- or Student-scoped data requires an explicit `hostId` parameter sourced only from the verified JWT claim — never from request body or URL parameters. No database Row-Level Security is implemented.

## Consequences
### Positive
- No session-store infrastructure (e.g., Redis) needed for week 1, consistent with the "Cache: None" decision in tech-stack.md.
- A single Guard + a single base-repository convention covers authorization for all Host- and Student-scoped endpoints, keeping the pattern learnable for 4 generalists in one sitting.

### Negative / Trade-offs
- Without DB-level RLS, a missed `hostId` filter in any single repository call is a silent cross-tenant data leak rather than a hard database-level rejection — this pushes the entire correctness burden onto code review and testing rather than the database itself.
- No refresh-token rotation means a compromised access token remains valid until expiry; acceptable for a 1-week pilot with a small, known user base, but flagged as a hardening item if the pilot continues.

### Risks
- **This is the single highest residual risk in the MVP.** A developer writing a new query that omits the `hostId` filter would not be caught by the database — only by code review or a missed test case. Mitigation: the architecture.md Security Architecture section names this as threat #1, and the PM task-breakdown should include an explicit cross-tenant-isolation test task (e.g., "Host A cannot fetch Host B's batch by ID") rather than leaving it implicit in generic CRUD tests.
- Risk: JWT secret leakage (BR-010 — no hardcoded secrets) would compromise all three roles' auth at once, since one secret signs all tokens. Mitigation: secret supplied via environment configuration only, never committed, per BR-010.

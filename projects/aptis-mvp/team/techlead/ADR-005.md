# ADR-005: Build the MVP as the first vertical slice of the production aptis-lms repos (amends ADR-001 / ADR-003, re-scopes ADR-004)
**Date:** 2026-06-21
**Status:** Accepted

## Context
ADR-001/003/004 were written as if the MVP would start from an empty codebase, and therefore chose a deliberately *simplified* architecture: a single layered NestJS monolith with no DDD bounded contexts (ADR-001), application-layer-only `host_id` scoping with no DB Row-Level Security ever (ADR-003), and synchronous in-request Excel processing with no worker (ADR-004).

That assumption is now false. The three repositories already exist and are scaffolded to the **full `aptis-lms`** architecture, and each repo's `RULE.md` binds to the full-project TechLead ADRs after Gate 1:
- `aptis-be`: a NestJS 11 monorepo with **two apps** (`apps/api` + `apps/worker`), **12 DDD bounded contexts** under `libs/modules` (`iam`, `tenancy`, `licensing`, `learning`, `question-bank`, `exam-operations`, `exam-delivery`, `integrity`, `scoring`, `analytics`, `notifications`, `audit`), Clean Architecture layering (domain/application/infrastructure/presentation), **BullMQ + Redis + transactional outbox**, PostgreSQL **RLS as defense-in-depth**, and access-token ≤15 min + **refresh-token rotation**. `docker-compose.yml` runs `postgres:17` + `redis:7`.
- `aptis-web`: Next.js **16** / React 19 / Tailwind **4** (currently a bare `create-next-app`); `RULE.md` marks the Next.js choice **provisional** pending an ADR amending SRS DC-01 (which mandates Flutter for all clients). **Resolved by ADR-006 (2026-06-23):** Next.js is ratified for Vendor/Tenant Portal; DC-01 is narrowed to the Exam Client only.
- `aptis-app`: a full Flutter exam client — **out of scope** for the web-only MVP.

On 2026-06-21 the operator chose to build the MVP **inside these production repos as the first real vertical slice**, rather than as throwaway simplified code, to avoid a later rewrite.

## Decision
The MVP is implemented inside `aptis-be/apps/api` and `aptis-web`, **conforming to each repo's `RULE.md`**. It is the first production vertical slice of `aptis-lms`, not a separate simplified build.

**In-scope bounded contexts** (only those the 15 MVP stories require), implemented `apps/api`-only with the standard layering but a reduced use-case surface:
`iam` · `tenancy` · `question-bank` · `exam-operations` · `exam-delivery` · `scoring`.

**Documented deferrals** (explicit, tracked gaps — closing each later is additive, not a rewrite):
- `apps/worker` + BullMQ/Redis — MVP scoring + Excel run **synchronously in `apps/api`**; but the attempt-finalize write path still commits an **outbox event row** (per `aptis-be/RULE.md` "critical state + outbox commit in one transaction") so the worker can take over later **without changing the write path**.
- **PostgreSQL RLS** — enforced now at the **repository layer** via trusted JWT tenant context (per RULE.md "tenant query includes trusted tenant context; RLS is defense in depth, not a replacement for repository scoping"). RLS policies are deferred but the schema/queries are shaped to add them additively. *This is the corrected stance vs ADR-003's "app-layer-only, no RLS ever".*
- **Refresh-token rotation** — MVP may ship access-token-only, but the `iam` token port must be shaped so refresh is added without touching call sites.
- Contexts `licensing`, `integrity`, `analytics`, `notifications`, full `audit` — not built in MVP.
- `exam-delivery` media (Listening/Reading/Writing/Speaking, timers, shuffle) — MVP is **MCQ-only** (BR-007).
- `aptis-app` (Flutter) — **frozen**; MVP is web-only (BA Out of Scope).

**Excel:** add `exceljs` to `aptis-be`. Roster import + credential export run synchronously in `apps/api`, bounded by the oversized-file rejection (US-007 AC).

**Pre-demo vs post-demo (operator decision, 2026-06-21):** the MVP is production-grade with fewer features (not a throwaway demo) and continues onto the full roadmap after an upcoming demo. The pre-demo slice ships **minimal hardening** — production-correct *structure* (DDD layering, repository host-scoping, outbox-ready write path, refresh-shaped token port) but **without** RLS policies, refresh rotation, or worker. Those are enabled in a **post-demo hardening sprint** (PM Sprint 3 / TASK-028–030), all additive with no rework. This makes the demo gate the earliest point a correct E2E loop is showable, without incurring throwaway code.

## Consequences
### Positive
- MVP code is a genuine foundation — no throwaway, no migration debt; the host-scoping discipline and layering are established correctly from day 1.
- Reuses the senior-grade conventions already encoded in the three `RULE.md` files instead of inventing a parallel set.
- Each MVP story maps onto a real bounded context (see `mvp-slice-mapping.md`), so growth toward the full 111-FR system is incremental.

### Negative / Trade-offs
- DDD ceremony (aggregates, ports/adapters, domain events, typed error taxonomy) raises per-feature cost — **the 1-week Sprint 1 estimate is now at real risk** and should be treated as a target, not a commitment. PM `story-points.md` already flags Sprint 1 as aggressive; this decision widens that risk.
- The PM `task-breakdown.md` "feature modules" must be re-read as **bounded contexts**; ownership (4 devs / which stories) is unchanged, but the repo location and layering per task change. See `mvp-slice-mapping.md`.

### Risks
- **Scope creep** — a dev pulling full-context behavior beyond MVP needs. Mitigation: `mvp-slice-mapping.md` lists exactly which use-cases per context are in scope; anything else is deferred.
- **Deferred-but-forgotten gaps** (worker, RLS, refresh rotation) silently shipping to more than the pilot. Mitigation: the deferral register in `mvp-slice-mapping.md` is the hardening backlog; revisit before any second customer.
- **Host-scoping correctness without RLS** — same residual risk as ADR-003 #1; mitigation unchanged: the cross-tenant isolation test suite (PM TASK-023) is mandatory, now reinforced by RLS-ready repository scoping.

## Relationship to prior ADRs
- **ADR-001** (simplified layered, no DDD) — **amended**: MVP now uses the full DDD bounded-context structure, scoped to 6 contexts.
- **ADR-002** (PostgreSQL + Prisma) — **unchanged** (note version realignment to Prisma 7 / Postgres 17 in `tech-stack.md`).
- **ADR-003** (app-layer-only, no RLS ever) — **amended**: repository-scoped tenant access **with RLS deferred-but-planned**, not ruled out.
- **ADR-004** (synchronous Excel, no worker) — **re-scoped**: synchronous in `apps/api` for MVP, but on a **worker-ready, outbox-committing write path**.

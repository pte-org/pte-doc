# ADR-004: Synchronous in-request Excel import/export, no background job queue
**Date:** 2026-06-21
**Status:** Accepted — **RE-SCOPED by ADR-005 (2026-06-21)**: still synchronous in apps/api for MVP, but on a **worker-ready, outbox-committing write path** so apps/worker can take over later without changing the write path. Read ADR-005 first.

## Context
Two flows in this MVP involve file processing: Host roster upload (parsing a `.xlsx`, REQ relating to US-007/US-008) and credential export generation (REQ relating to US-010). A production-scale LMS would typically offload these to a background worker (e.g., BullMQ + Redis) to keep the API responsive under large files or high concurrency. The operator's explicit context for this MVP states no BullMQ/worker is needed "if xử lý đồng bộ được" (if it can be handled synchronously) — and the BA's `requirements.md` Out of Scope / pilot framing implies modest roster sizes (a single Host's student batch, not tens of thousands of rows) and a small number of concurrent Hosts during the 1-week pilot.

## Decision
We will process both the roster-import parse/validate/create flow and the credential-export workbook-generation flow synchronously, in-process, within the same HTTP request — using the `exceljs` library directly inside the NestJS request handler, with no message queue, no Redis, and no separate worker process.

## Consequences
### Positive
- Removes an entire piece of infrastructure (queue + worker + Redis) from the week-1 build and deployment surface, directly serving the 7-day timeline.
- Simpler error handling: a failed import or export simply returns an HTTP error to the Host immediately, with no job-status polling UI needed on the frontend.

### Negative / Trade-offs
- Large roster files or slow Excel generation will block the API request thread for their full duration, which would not scale past pilot-sized usage.
- No retry-on-failure semantics beyond the Host manually re-submitting the request.

### Risks
- Risk: an oversized roster file could cause a request timeout or memory spike on the single API process. Mitigation: AC for US-007 already specifies an oversized-file rejection before parsing begins (platform-configured max roster size), bounding the worst case.
- Risk: if the pilot's usage grows beyond what synchronous processing can handle, this decision needs revisiting — explicitly flagged here so a future ADR is required before introducing a queue, per the Gate 1 change protocol in architecture.md.

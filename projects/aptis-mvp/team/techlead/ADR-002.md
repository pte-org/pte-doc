# ADR-002: PostgreSQL with Prisma as the persistence layer
**Date:** 2026-06-21
**Status:** Accepted

## Context
The MVP's data model (`ERD.md`) has strong relational integrity requirements directly traceable to business rules: BR-004 (per-Host uniqueness of student identifiers), BR-005 (Host-scoped data access), BR-006 (an Exam needs ≥1 question to be assignable), and BR-009 (a question in an assigned Exam cannot be deleted). These are most reliably enforced with foreign keys, unique constraints, and referential-integrity checks rather than re-implemented as application-level invariants across a 4-person team in 7 days, where inconsistent enforcement across modules is a realistic risk. The team must also iterate on the schema quickly during week 1 as the roster-import and credential-export flows get built.

## Decision
We will use PostgreSQL 15 as the single system of record, accessed exclusively through Prisma 5.x as the ORM/migration tool, across all NestJS modules.

## Consequences
### Positive
- Unique constraints (`STUDENT(host_id, student_identifier)`, `STUDENT.username`, `EXAM_ATTEMPT.student_id`, etc.) push critical business-rule enforcement (BR-004, BR-003) to the database layer, where it cannot be bypassed by a missed `if` check in a single module.
- Prisma's schema-first migrations let all 4 generalists propose and review schema changes via a single `schema.prisma` diff, rather than hand-written SQL migrations that are easy to desync across branches in a fast-moving week.
- Generated TypeScript types from Prisma reduce integration bugs between modules built by different team members in parallel.

### Negative / Trade-offs
- Prisma's migration engine is less flexible than raw SQL for complex data migrations — acceptable here since the MVP has no pre-existing production data to migrate.
- Adds a build-time codegen step (`prisma generate`) every team member must remember to run after pulling schema changes — a minor but real onboarding friction point for a fast week.

### Risks
- Risk: heavy concurrent schema changes from 4 developers in the same week could cause migration conflicts. Mitigation: schema changes should be proposed as small, reviewed PRs against `schema.prisma`, sequenced through the sprint's task dependencies (see upcoming PM task-breakdown).

# ADR-006: Amend SRS DC-01 — Next.js Web for Vendor Portal & Tenant Portal; Flutter remains exclusive to the Exam Client
**Date:** 2026-06-23
**Status:** Accepted

## Context
SRS §3.5 **DC-01** ("Flutter as Mandated Client Framework") states: *"The system shall implement all client-facing applications — Vendor Portal, Tenant Portal, and Exam Client — exclusively in Flutter (Dart). No alternative frontend framework (React, Vue, Angular, etc.) is permitted for any client UI component."* Imposed by: stakeholder mandate for a single cross-platform codebase (Web, Desktop, Mobile) across all clients.

`ADR-005` (2026-06-21) already flagged this as unresolved: the `aptis-web` repo exists and is scaffolded as Next.js 16 / React 19 / Tailwind 4 — not Flutter — and ADR-005 explicitly marked that choice **"provisional pending an ADR amending SRS DC-01."** No such ADR existed until now; this document resolves that open flag.

Since ADR-005, `aptis-web` has been restructured (2026-06-23) into a pnpm-workspaces + Turborepo monorepo:
- `apps/tenant-web` — migrated from the original scaffold via `git mv` (history preserved)
- `apps/vendor-web` — fresh `create-next-app` scaffold, dependency-aligned with `tenant-web`
- `packages/{ui, config, api-client}` — shared UI components, lint/tsconfig, and hand-written API types

Both apps were verified to install, lint, and run independently (`pnpm dev --filter <app>`, HTTP 200), with feature folders named after the `aptis-be` bounded contexts (`iam`, `tenancy`, `question-bank`, `exam-operations`, `exam-delivery`, `scoring`) per `mvp-slice-mapping.md` §1. This is real, working infrastructure — not a throwaway prototype — built on the assumption that Next.js is correct for the portals. That assumption needs to be either ratified or reversed before more feature work lands on top of it.

Separately, `aptis-app` (the Exam Client) is being set up as its own Flutter repository, scoped strictly to exam-taking (per BA Out of Scope and ADR-005's "frozen for MVP" note) — it has no dependency on this decision.

## Decision
We amend **DC-01**: the Flutter mandate is narrowed to the **Exam Client only** (`aptis-app` — Flutter Desktop primary/macOS secondary + Flutter Web, per `_context/tech_stack.md`). **Vendor Portal and Tenant Portal are built as Next.js (App Router) web applications**, inside the `aptis-web` monorepo (`apps/vendor-web`, `apps/tenant-web`), not in Flutter Web.

DC-01's text in the SRS is annotated as amended (not rewritten), per the project's convention of preserving the original constraint and layering amendments on top (see ADR-005's treatment of ADR-001/003/004).

## Consequences

### Positive
- No rewrite cost: the already-built, already-verified `aptis-web` Turborepo monorepo is ratified as-is rather than discarded for a Flutter Web rebuild of two portals.
- Portal UIs are CRUD/dashboard-heavy (question bank, roster import, exam assignment, host management) — exactly the use case React/Next.js tooling (forms, tables, SSR, App Router data fetching) is mature for; Flutter Web has comparatively weaker support for this class of content-heavy admin UI (SEO irrelevant here, but DOM-based accessibility and browser-native form ergonomics favor web frameworks).
- DC-02 (multi-tenant subdomain routing) is unaffected: each Next.js app deploys behind its own subdomain (`admin.aptis-lms.vn` for Vendor, `{slug}.aptis-lms.vn` for Tenant) exactly as DC-02 already specifies, independent of client framework choice.
- `aptis-app` keeps the cross-platform Flutter investment focused on the one client where it matters most: the Exam Client must run on Desktop (kiosk mode, FR-102) and Web from a single codebase — the part of DC-01's original rationale that's load-bearing.

### Negative / Trade-offs
- DC-01's original rationale — "one codebase, one skillset, across all clients" — no longer holds project-wide. Portal developers (TypeScript/React) and Exam Client developers (Dart/Flutter) are now two distinct skillsets instead of one.
- Any future business logic that needs to be shared between the Exam Client and the Portals (e.g., APTIS scoring/band-mapping display rules, validation rules) cannot be shared via a common Dart package anymore. It must live in the backend API (`aptis-be`) as the single source of truth, or be duplicated per client.
- This is a narrowing of a stakeholder-approved hard constraint, not a TechLead-internal implementation choice. The original DC-01 sign-off may have carried intent beyond pure technical tradeoffs (e.g., team hiring strategy around a single Flutter skillset); that intent has not been re-confirmed with whoever owns SRS sign-off.

### Risks
- **Stakeholder mismatch risk:** if DC-01 was driven by a non-technical constraint (vendor relationship, hiring plan) not visible in the SRS rationale line, this amendment could conflict with that intent. *Mitigation:* this ADR must be circulated to the SRS owner for explicit confirmation before the SRS itself is marked non-DRAFT; flagged as a new open item alongside the existing 8 OIs in `_context/session-notes.md`.
- **Drift risk:** if a future contributor reads only DC-01's original SRS text without finding this amendment, they may build a Flutter Web portal in violation of the actual current decision. *Mitigation:* DC-01 in `srs/03-05-design-constraints.md` is annotated in place (see companion edit) pointing to this ADR, mirroring how ADR-005 annotated ADR-001/003/004.

## Relationship to prior ADRs
- **ADR-005** (2026-06-21) — resolved: the "Next.js choice provisional pending an ADR amending SRS DC-01" flag it raised is now closed by this decision.
- **DC-02** (multi-tenant subdomain architecture) — unchanged and unaffected; still satisfied by per-app subdomain deployment regardless of client framework.
- **`mvp-slice-mapping.md`** — unaffected; `aptis-web` feature-folder-per-bounded-context structure already matches this ADR's direction and needs no rework.

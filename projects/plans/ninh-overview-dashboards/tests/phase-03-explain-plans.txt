PERF-001 RESOLVED - students per tenant (UserRepository.countByRoleGroupedByTenant, the heaviest query):
- Before: count(distinct u.id) forced Seq Scan users + Seq Scan user_roles -> Hash Join -> Sort (external merge, 3.2 MB disk spill) ->
  GroupAggregate: 95 ms in the first run, 108 ms in the final run (comparison section "PREVIOUS query" in the raw output below).
- Now (production query uses count(u.id)): Seq Scan users + Seq Scan user_roles -> Hash Join -> HashAggregate (24 kB), NO sort, NO disk
  spill, 56 ms at 100k students (about half). Both tables are still read in full because the answer is "every student, per tenant";
  no index can avoid that, so growth stays linear (~0.6 s at ~1M students, under the 2 s timeout hint and behind the 60 s section cache).
- Exactness caveat (stated in the repository Javadoc): count(u.id) equals the distinct count only while no duplicate (user_id, role) row
  exists in user_roles (the schema has no unique constraint; the application inserts set elements only). The H2 test
  IdentityPlatformOverviewQueriesTest covers multi-role users (counted once per tenant as STUDENT), deleted and tenant-less users.
- Optional if the table grows: user_roles(role, user_id) and users(tenant_id, id) WHERE deleted = false for index-only scans.
Interplay finding (fixed in test code only): with the original 2-tenant Phase 1 seed (tenant A = 50 percent of every table) the planner
now prefers the new narrow time-only indexes (idx_attempts_started/submitted) over idx_attempts_tenant_started/submitted for the
TENANT-scoped host queries, so the Phase 1 IT assertion "forced plan contains the tenant index" failed after V96. With a production-like
20-tenant interleaved seed (tenant A = 5 percent, same row totals) the tenant-leading indexes win again; the Phase 1 seed was changed to
20 tenants and its assertions are unchanged.

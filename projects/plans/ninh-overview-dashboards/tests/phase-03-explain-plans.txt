Sequential scan by default (small tables, no status-less created_at index; all 1.7-5.5 ms at this volume):

  seq scan even when forced); tenants grouped by status 0.7 ms (4k rows); plans grouped (40 rows).
  These scale linearly with table size. The (status, created_at) V96 indexes cannot serve a created_at-only range efficiently (forced plan
  uses a bitmap scan over the whole index). If these tables grow past ~1M rows add created_at-only partial indexes
  (support_ticket, tenant_applications, subscriptions) and license_codes(redeemed_at); not needed at current volumes.

PRODUCTION CONCERN - students per tenant (UserRepository.countByRoleGroupedByTenant, the heaviest query):
- Default plan: Seq Scan on users (100k rows) + Seq Scan on user_roles (100k rows) -> Hash Join -> Sort (external merge, spills 3.2 MB to
  disk) -> GroupAggregate, ~95 ms. Forcing indexes is no better (~100 ms: idx_user_roles_role + users_pkey). No index can avoid reading
  every student row because the result IS "every student, per tenant". It is bounded by the 2s timeout hint and the 60s section cache,
  but it grows linearly: ~1 s at ~1M students, i.e. approaching the 2 s hint.
- Cheap fix (production code, not applied): count(distinct u.id) forces the Sort. user_roles is unique per (user_id, role), so
  count(u.id) (or count(*)) is exact. Same data with count(*) runs ~45 ms (about half: plain HashAggregate, no sort, no disk spill): see the
  "count(*) variant" section below.
- Optional index when the table is large: user_roles(role, user_id) (index-only on the join side) and
  users(tenant_id, id) WHERE deleted = false (index-only on the user side).

Interplay finding (fixed in test code only): with the original 2-tenant Phase 1 seed (tenant A = 50 percent of every table) the planner
now prefers the new narrow time-only indexes (idx_attempts_started/submitted) over idx_attempts_tenant_started/submitted for the
TENANT-scoped host queries, so the Phase 1 IT assertion "forced plan contains the tenant index" failed after V96. With a production-like
20-tenant interleaved seed (tenant A = 5 percent, same row totals) the tenant-leading indexes win again; the Phase 1 seed was changed to
20 tenants and its assertions are unchanged.

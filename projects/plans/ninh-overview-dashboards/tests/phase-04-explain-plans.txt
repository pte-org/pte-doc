Phase 4 EXPLAIN summary (ninh-overview-dashboards) - online revenue (orders) and question bank queries, and the V97 index
Environment: scratch PostgreSQL 17 (container pte-overview-scratch, postgres:17-alpine, port 55439, trust auth), scratch schema
overview_mig_<random> migrated from EMPTY through V97 and dropped by the test; container removed afterwards. No pte-* / postgres
container was touched.
Seed (plain SQL, rows cloned from one template per table, VACUUM ANALYZE): 100001 orders over 730 days (50% VND, 25% USD, 12.5% EUR,
12.5% JPY; 70% PAID / 15% CANCELLED / 10% EXPIRED / 5% PENDING; 1% soft-deleted; 69001 PAID and not deleted, 2831 of them paid in the
last 30 days) and 40001 questions (4 sections, 2 pools, 4 statuses, 2% deleted).
Each query was explained twice: planner default and enable_seqscan=off (shows whether an index CAN serve it).

V97 migration: idx_orders_paid_at verified from an empty schema as a PARTIAL btree on (paid_at) WHERE status = 'PAID' AND deleted = false
(no tenant prefix; no other orders index contains paid_at), idempotent replay leaves the definition unchanged, Hibernate
ddl-auto=validate passes.

VERDICT ON V97 - KEEP. It is used by the DEFAULT planner (not only when forced) for every revenue query shape:
- current 30d window per currency:        Index Scan idx_orders_paid_at, 1.9 ms (0.9 ms warm), 2831 rows read
- previous 30d window per currency:       Index Scan idx_orders_paid_at, 0.9 ms
- monthly bucket (oldest of the 12):      Index Scan idx_orders_paid_at, 0.9 ms
- monthly bucket (current partial month): Index Scan idx_orders_paid_at, 0.4 ms
- production shape (status/paid_at bound as parameters, PREPARE + 6 executions, plan_cache_mode=auto): still Index Scan
  idx_orders_paid_at (PostgreSQL keeps custom plans because the generic plan cannot use the partial index and costs more).
- worst case, plan_cache_mode=force_generic_plan (NOT the default; shown for completeness): the partial index cannot be proven for a
  parameter, so it degrades to Bitmap Heap Scan via idx_orders_status_created (status only), 11.3 ms. Acceptable, not a defect.
Without V97 (index dropped in the scratch schema): Parallel Seq Scan on orders, 21.5 ms for the 30d window and 40.4 ms for the
current-month bucket (each of the 14 queries scans all 100k rows).
Whole revenue load of one cache miss (2 windows + 12 monthly buckets = 14 grouped statements, JDBC bound parameters, 100k orders):
  27.3-27.7 ms WITH idx_orders_paid_at, 151.7-176.3 ms WITHOUT (about 6x faster). The section is cached for 60 s, so this is paid at most
  once a minute per window/bucket. The gain grows linearly with the table (the seq scan reads all rows, the index only the range), so
  V97 is justified by evidence, not only by judgment.
  Cost side: one small partial index (69k of 100k rows here), maintained only on writes that touch PAID and not-deleted orders.

Question bank (no new index needed or recommended):
- counts by status/section/pool (new facade query): Seq Scan questions + HashAggregate, 14.3 ms for 40k rows (39201 rows read, 17 groups).
  Inherent: every shared non-deleted question must be counted; an index cannot avoid reading them (forced idx_questions_visibility is
  slower, 15.7 ms). It replaces the two legacy grouped queries (7.9 + 9.9 ms) with ONE pass for the dashboard, which is fine.
- created-in-window count: Seq Scan 7.4 ms (no created_at index; forced visibility index not faster). Linear growth: the bank is
  expected to stay in the tens of thousands of rows, so this stays in the low tens of ms. If it ever passes ~1M rows add
  questions(created_at) WHERE deleted = false.

Observation (not a defect): the revenue series uses one statement per month (12) plus two for the windows = 14 statements per cache miss
(Hibernate statistics confirm 12 + 1 + 1 prepared statements, 0 entity loads). With V97 each takes about 1 ms; a single grouped query
by month would need a database-specific date function (the phase requires portable JPQL).

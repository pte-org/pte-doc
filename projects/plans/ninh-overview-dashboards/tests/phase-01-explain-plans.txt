Phase 1 - EXPLAIN summary for the host dashboard queries (V94 indexes)
=====================================================================
Run: OverviewMigrationPostgresIntegrationTest.heavyHostQueriesUseTheNewIndexes, PostgreSQL 17 (scratch container
pte-overview-scratch, port 55439), fresh schema migrated V1..V94 by Flyway, Hibernate ddl-auto=validate.
Seed (SQL-cloned from JPA-created template rows, two tenants interleaved in 500-row chunks, time columns
growing with insertion order, then VACUUM ANALYZE):
  exam_attempts 40,002 (20,000/tenant; 3% IN_PROGRESS, 500 distinct students, ~14 months)
  users         40,002 (20,000/tenant, all STUDENT role rows in user_roles)
  exam_sessions 120,002 (60,000/tenant, 4 statuses, ~14 months)
Queried tenant A: window = last 30 days. Full raw plans (with costs and actual rows, planner default AND
enable_seqscan=off): app/target/overview-explain-plans.txt (regenerated by every run).
Stability: 3 consecutive green runs after the seed was made realistic (see note at the end).

Verdict per query (planner default settings)
--------------------------------------------
1. Attempts submitted in window per tenant          -> Bitmap Index Scan on idx_attempts_tenant_submitted (V94)
   35 heap blocks for 1,392 rows, est. cost 1036.      USES INDEX
2. Distinct active students (started_at)            -> Bitmap Index Scan on idx_attempts_tenant_started (V94)
   36 heap blocks for 1,441 rows + sort for DISTINCT   USES INDEX
3. Monthly submitted series (one month bucket;      -> Bitmap Index Scan on idx_attempts_tenant_submitted (V94)
   the service runs 12 of these, one per month)        USES INDEX (37 heap blocks / 1,438 rows per bucket)
4. Attempts in progress now                         -> Bitmap Index Scan on idx_attempts_tenant_status (V94)
                                                       USES INDEX (667 rows)
5. New learners in window (users x user_roles)      -> users: Bitmap Index Scan on idx_users_tenant_created (V94)
                                                       USES INDEX on users. user_roles is hash-joined with a Seq Scan
                                                       (40,002 rows) in the default plan; with seqscan off the planner
                                                       switches to a nested loop with Index Only Scan on
                                                       idx_user_roles_user_role (1,441 probes, 0 heap fetches).
                                                       user_roles has no tenant column, so the planner choice depends
                                                       on how large the tenant's window is relative to all roles; with
                                                       many tenants the selective nested-loop plan is expected.
6. Sessions grouped by status                       -> Bitmap Index Scan on idx_sessions_tenant_status (V94)
                                                       USES INDEX, but the query has no status/time predicate, so it
                                                       reads the tenant's whole slice (60,001 rows, 2,052 heap blocks).
                                                       Cost grows with sessions per tenant (small in practice).
7. Sessions created in window                       -> Bitmap Index Scan on idx_sessions_tenant_created (V94)
                                                       USES INDEX (149 heap blocks / 4,321 rows)

No Seq Scan on exam_attempts, exam_sessions or users for any V94-targeted query. The enable_seqscan=off variants
confirm every V94 index is eligible (the assertion on those plans is unchanged: the expected V94 index name must
appear).

Production concerns
-------------------
None blocking. Two things to be aware of (no production change requested):
  - Query 6 is a tenant-wide aggregate by design; idx_sessions_tenant_status only avoids a heap seq scan, it does not
    make it constant-time. Fine while sessions-per-tenant stays in the thousands.
  - Query 5 relies on the planner choosing the nested loop over user_roles when the tenant window is small relative
    to total user_roles rows; with only two tenants it hash-joins the whole user_roles table.

Test-seed note (not a production issue)
---------------------------------------
Earlier runs on a less realistic seed (tenants physically contiguous, created_at uncorrelated with heap order)
made the planner prefer the pre-existing idx_sessions_tenant for queries 6 and 7 and the test failed on those
two. The seed was changed to interleave tenants and make time columns follow insertion order (as in production);
assertions were not changed.

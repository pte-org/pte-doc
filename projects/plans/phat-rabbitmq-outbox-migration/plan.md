# Plan: RabbitMQ + Polling Outbox Migration (retire Kafka/Debezium/Schema Registry)

Status: ✅ Implementation Complete — manual smoke test + Testcontainers integration testing pending
Date: 2026-07-30
Mode: Hard
Architecture: `personal-docs/rabbitmq_pollingoutbox.md` (rationale, already decided — not re-litigated here), `ADR-002-communication-and-exam-submission-saga.md` (current, superseded by Phase 11 of this plan), `docs/CODING_STANDARDS_MICROSERVICE.md`

## Overview

Replace the platform's event backbone — Kafka + Debezium (WAL-tail CDC) + Schema Registry — with RabbitMQ plus an application-level polling outbox relay, keeping the dual-write-safe atomicity guarantee that Debezium currently provides, but at a fraction of the operational complexity a small student team needs to run. `pte-common`'s outbox WRITER half (`AbstractOutboxEntry`, `AbstractOutboxWriter`) and consumer-side idempotency ledger (`AbstractProcessedEvent`) are reused unchanged; only the "how does a written-but-unpublished row actually reach a broker" mechanism changes, from Debezium tailing Postgres's WAL to each service polling its own `outbox` table with `SELECT ... FOR UPDATE SKIP LOCKED` and publishing to RabbitMQ with publisher confirms.

Reporting's read model is built purely from its `@KafkaListener` consumers today (`AttemptIngestConsumer`, `AnswerScoredConsumer`, `PublishConsumer`) — there is no rebuild/replay trigger anywhere in reporting's current code (verified this session: no admin endpoint, no from-beginning consumer group, nothing). Kafka's retention makes a from-scratch rebuild *theoretically possible* by starting a new consumer group, but that capability was never operationalized — reporting has always been single-consumer-group, steady-state-only. Correction to an earlier draft of this plan: Phase 9 is not replacing a working rebuild feature, it is **adding the first-ever rebuild capability reporting has had** — via an internal-only synchronous REST pull instead of a Kafka-replay-based one, since a from-scratch rebuild becomes actually necessary once Kafka goes away and any future need to reconstruct a lost/corrupted read model must go through the new services' current tables instead. The 6 producing services (exam-delivery, scoring, scheduling, iam, authoring, proctor) each expose a paginated `/internal/**` export endpoint reporting calls on demand (plan-reviewer finding, ACCEPTED).

## Research Summary

Verified this session (trust, do not re-derive):

- `pte-common/.../messaging/` already has the producer-side outbox writer (`AbstractOutboxEntry`, `AbstractOutboxWriter`) and consumer-side idempotency ledger (`AbstractProcessedEvent`), both reused unchanged — the dedup contract is identical under RabbitMQ's at-least-once delivery. `EventEnvelope<T>` also exists in `pte-common` but is currently unused by any producer/consumer (event type/id travel as Debezium Kafka headers today, not through this envelope) — see the open design point below.
- 8 services publish via a concrete `OutboxEntry extends AbstractOutboxEntry` today (one Debezium connector JSON each under `pte-api/docker/debezium/connectors/`): admin, authoring, exam-delivery, iam, proctor, reporting, scheduling, scoring.
- 6 services consume via `@KafkaListener` (`messaging/consumer/*.java`, 4 of them with a per-service `KafkaHeaders.java` helper — exam-delivery, notification, reporting, scoring; iam and scheduling parse headers inline): scoring, scheduling, reporting, notification, iam, exam-delivery.
- `notification`'s `RabbitMqConfig.java` (DirectExchange + DLQ via `x-dead-letter-exchange`/`x-dead-letter-routing-key`, `Jackson2JsonMessageConverter`, `RetryOperationsInterceptor`) is the house style for consumer-side queue config; no publisher-confirm config exists anywhere yet — that part is new.
- `media` does not participate in the event backbone (sync-only, presigned URLs) — out of scope.
- Only `notification` and `scoring` currently depend on `spring-boot-starter-amqp`; all 6 Kafka-consuming services depend on `spring-kafka` (confirmed per-`pom.xml`, not centrally managed in the root or `pte-common` POM).

Target design (from this session, turned into the phases above, not redesigned here):

- `AbstractOutboxEntry` gains `published`/`publishedAt`/`publishAttempts`/`lastError`. A generic `OutboxJpaRepository<T>` in `pte-common` selects an unpublished batch via `#{#entityName}` SpEL + `@Lock(PESSIMISTIC_WRITE)` + `jakarta.persistence.lock.timeout=-2` (Hibernate 6's SKIP LOCKED trigger). `AbstractOutboxRelay<T>` is a `@Scheduled` + `@Transactional` template: select batch, publish each row, `waitForConfirmsOrDie`, flip `published=true` in the same transaction — if the wait throws, the whole transaction rolls back and the row retries next poll, no separate async correlation bookkeeping. `AbstractOutboxCleanupJob<T>` is a separate daily job pruning old published rows, kept out of the hot poll transaction.
- Explicitly NOT using ShedLock for the relay: `SKIP LOCKED` alone gives correct per-row mutual exclusion across instances; ShedLock would wrongly serialize the whole poll to one instance. `AbstractOutboxRelay` carries a Javadoc warning against reaching for it out of Kafka-consumer-group habit.
- Config knobs `pte.outbox.poll-interval-ms` (default 2000–5000) and `pte.outbox.batch-size` (default ~100) via `application.yml`, not hardcoded.
- Per-aggregate ordering that Kafka partitioning gave for free is lost under concurrent pollers; `AbstractProcessedEvent` only dedups, does not reorder. scoring and exam-delivery are the ordering-sensitive consumers (Phases 5–6) and mitigate by keeping same-aggregate-type traffic on one queue with single-consumer concurrency, so enqueue order is preserved even though cross-aggregate publish order is not guaranteed.
- Reporting's rebuild switches from Kafka replay to a paginated internal sync-pull across the 6 producing services (Phase 9), reusing the existing `/internal/**` + shared-key `InternalApiKeyFilter` pattern already established in exam-delivery (Milestone 1 Phase 5) rather than inventing new service-to-service auth.

### Design points — confirmed by user during Validation (no longer open)

- **RabbitMQ correlation/header mechanism replacing `KafkaHeaders.java`**: CONFIRMED — AMQP message properties (`messageId` for the dedup key, custom `headers` entry for event type), not `EventEnvelope<T>`. Applies uniformly across Phases 3–8.
- **Reporting rebuild endpoint pagination/cursor contract** (Phase 9): CONFIRMED — monotonic `(updatedAt, publicId)` keyset cursor per producing service, `GET /internal/{resource}/export?since={cursor}&limit=`, identical shape across all 6 services.

- Phase 9 has no functional predecessor to replace (see Overview correction above — reporting never had a working rebuild path, so there is no "gap window" where a previously-working capability is unavailable). It's still sequenced right after Phase 7 with no other work interleaved, purely so reporting isn't left without ANY rebuild option for longer than necessary once it's fully cut over to RabbitMQ.
- Phase 11 (ADR-002 rewrite) should land last so it describes the migration as actually implemented, not as planned.
- Coordinated Flyway migration across 8 services (Phase 2 + Phases 3–7) — each service's migration is independent (own schema, no cross-service coordination needed at the DB level), but all 8 must land before Phase 10 removes Debezium, or a service still on the old outbox shape has nothing relaying its rows.

## Risks

- HIGH: Publish-confirm blocking-poller-thread ceiling at scale — `waitForConfirmsOrDie` inside the poll transaction means relay throughput is bounded by round-trip confirm latency, not just DB read speed. Mitigation: batch size and poll interval are config knobs (Phase 1), tunable per service without code change; acceptable at this team's scale, documented as a scaling limit revisit item in Phase 11's ADR rewrite.
- HIGH: Lost cross-aggregate ordering — Kafka partitioning guaranteed per-aggregate order for free; concurrent SKIP LOCKED pollers do not. Mitigation: `AbstractProcessedEvent` dedups but does not reorder; Phases 5–6 (exam-delivery, scoring) explicitly route same-aggregate-type traffic through a single queue/single-consumer-concurrency binding so enqueue order is preserved for the two ordering-sensitive consumers; documented, not silently accepted.
- MEDIUM: Coordinated Flyway migration across 8 services — each producer needs its outbox table's Flyway migration to both add publish-state columns AND backfill existing rows to `published=true` (so the new relay doesn't flood-redeliver history on cutover), landing before that service's Debezium connector is removed. Mitigation: Phase 2 establishes the backfill-in-same-migration pattern first on 3 low-risk services before Phases 3–7 repeat it on the 5 services that also have consumers.
- MEDIUM: Reporting rebuild endpoints are a new internal API surface — Phase 9 adds a paginated, potentially bulk-data-exposing endpoint to 6 services. Mitigation: reuse the existing `/internal/**` + shared-key `InternalApiKeyFilter` network-boundary pattern (not a new auth mechanism); explicit tenant-scoping on every export query, no cross-tenant page.
- LOW (resolved during Validation): `KafkaHeaders.java` removal across 4 services — header/correlation mechanism is now confirmed (AMQP message properties), no longer an open gap by the time Phases 3-8 execute.
- NOTED: Phases 2–9 are rollback-safe via a plain git revert, because Kafka/Debezium remain live and still tailing every service's outbox table until Phase 10 explicitly removes them — reverting any single service's `@RabbitListener` back to `@KafkaListener` mid-migration works with no data loss. This is the deliberate rollback mechanism for the whole migration, not an incidental side effect of the phase ordering — Phase 10 is correctly described elsewhere as "the point of no return" precisely because this safety net disappears there (plan-reviewer finding, NOTED).
- NOTED: Phase 9's full-read-model-bootstrap scenario (a brand new reporting instance with an empty DB) needs a distinct internal service-identity credential authorized to iterate ALL tenants, separate from the per-tenant JWT-forwarding path used for narrower operator-triggered rebuilds — the "every export query is tenant-scoped, never a blanket cross-tenant export" rule in Phase 9's Design Constraints otherwise has no valid credential to drive a full bootstrap. Resolved in Phase 9 itself, see that file (plan-reviewer finding, ACCEPTED).

### Decisions made this session

- **Per-row claim instead of batch-claim-then-loop (Phase 1).** The phase file's original wording ("fetch a batch via the repository, then for EACH row calls a separate proxied bean method") would have held a `PESSIMISTIC_WRITE` lock open across an outer transaction while trying to flip each row via a separate `REQUIRES_NEW` connection — that inner UPDATE would block forever on the outer transaction's own still-held lock (same-process, cross-connection self-deadlock). Implemented instead as `poll()` looping up to `batchSize` times, each iteration calling `claimAndProcessOne()` which does `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` + publish + flip **all inside the same short transaction**, one connection, then commits before the next claim. Net effect (per-row transaction boundary, no batch rollback) is identical to what the plan intended; only the SQL shape (N single-row claims vs. 1 N-row claim) differs, and it's the correct way to get there.
- **Used `TransactionTemplate` with `PROPAGATION_REQUIRES_NEW`, not `@Transactional` self-invocation (Phase 1).** The phase file itself flagged the self-invocation pitfall as something to avoid — a plain `this.foo()` call to a same-class `@Transactional` method silently skips the proxy and runs with no transaction. Programmatic `TransactionTemplate` sidesteps this without needing a second bean or `AopContext.currentProxy()`.
- **`AbstractOutboxRelay` holds a `RabbitTemplate` directly (Phase 1)** and exposes a `protected final publishAndConfirm(entry, exchange, routingKey)` helper (not just an abstract `publish()` with no shared implementation) — centralizes the `waitForConfirmsOrDie` + AMQP `messageId`/`eventType`-header wiring so services don't each reimplement the confirm handshake. This is why `pte-common` needs `spring-boot-starter-amqp`, beyond just satisfying the phase's literal instruction to add it.
- `deletePublishedBefore` cleanup query is a single unbounded JPQL bulk `DELETE` (no `LIMIT`, which JPQL bulk deletes don't support) — acceptable at this team's scale since the job runs daily and a service's outbox never accumulates more than ~1 day of published rows between runs.
- **Added a concrete `{Service}OutboxCleanupJob` per service (Phase 2), not listed in the phase file's "Files to touch".** `AbstractOutboxCleanupJob` is abstract — without a concrete subclass registered as a `@Component`, the cleanup job never runs anywhere. Same gap will apply to every later phase that builds a producer relay.
- **Added `@EnableScheduling` to each service's `*Application.java` (Phase 2), not listed in the phase file.** No service in this codebase used `@Scheduled` before this migration, so `@EnableScheduling` was never needed until now — without it, both the relay's `poll()` and the cleanup job silently never fire (no error, just never runs). Same gap will apply to every later phase that builds a producer relay.
- **RabbitMQ exchange/routing-key naming applied per plan.md's template**: `outbox.{service}.exchange` (`TopicExchange`), routing key `{aggregateType}.{eventType}`. proctor's two aggregates (`ProctorCommand`, `ViolationEvent`) share one exchange, differentiated by routing key, since they're both proctor's own outbox rows.
- **Producer-only services' `RabbitMqConfig` declares only a `TopicExchange` + `MessageConverter` bean, no custom `RabbitTemplate` bean.** Spring Boot's autoconfigured `RabbitTemplate` already picks up the `MessageConverter` bean automatically and applies `spring.rabbitmq.publisher-confirm-type`/`publisher-returns`/`template.mandatory` from `application.yml` — a hand-written `RabbitTemplate` bean would be redundant. No listener container factory needed since these 3 services don't consume yet.

- **Consumer queue naming (Phase 3, pattern for Phases 4-8):** each consuming service owns its own queue name (`{service}.{topic}`, e.g. `iam.tenant-events`) bound to the PRODUCER's topic exchange (`outbox.{producer}.exchange`) with a routing pattern matching the aggregate (`{Aggregate}.*`). DLQ config mirrors notification's `EMAIL_QUEUE` shape exactly: `x-dead-letter-exchange`/`x-dead-letter-routing-key` on the primary queue, 3-attempt exponential-backoff `RetryOperationsInterceptor`. One subtlety: the primary queue's binding uses a wildcard PATTERN (can't be reused as the literal dead-letter routing key), so a separate literal routing-key constant is needed for DLX routing + DLQ binding — notification's single-key-reused-three-ways shape only works there because it's a `DirectExchange` with an exact key, not a topic wildcard.
- **`spring-retry` had to be added explicitly to `iam/pom.xml` (Phase 3)** — the `RetryOperationsInterceptor`/`RetryInterceptorBuilder` classes used in every `RabbitMqConfig` with a consumer queue come from `org.springframework.retry:spring-retry`, which is NOT a transitive dependency of `spring-boot-starter-amqp`. notification already had it declared explicitly; every later phase that adds a consumer queue with retry/DLQ (4, 5, 6, 7, 8) will need this same explicit dependency, not just `spring-boot-starter-amqp`.

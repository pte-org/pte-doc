# Phase 2: Offline Answer Outbox

## Requirements

Build the local Drift-backed answer outbox and its background `SyncEngine` — the single most safety-critical component in this spec, since an answer the student believes was submitted must never silently vanish. Every buffered answer is keyed by `(attemptPublicId, pinnedItemPublicId)`, persisted to SQLite (not memory) so it survives process death, and flushed by a connectivity-triggered + periodic-fallback sync loop. Outbox rows must distinguish **retry-pending** from **terminal-rejected** status: a stale/replayed submission or a past-deadline rejection stops retrying forever, while a transient network/server failure keeps retrying. No task-type UI exists yet — this phase is built and verified in isolation, exactly as `plan.md`'s Research Summary and Risks call for, so its process-death-survival property is proven before Phase 5/6 wire any screen to it.

Maps to: **P1 Story #7 ("my answer survives the app being killed or losing network mid-response") | FR-05, FR-06**

## Design Constraints

- Rebuild from the Phase 0 reference copy of the old scaffold's `answer_outbox_table.dart` (composite PK `(attemptId, questionId)`), `answer_outbox_dao.dart` (idempotent `insertOnConflictUpdate` upsert, WAL checkpoint after a flush batch), `sync_engine.dart` (`startSync(attemptId)`/`stopSync()`, `StateError` if started for a second attempt without stopping the first), and `network_canary.dart` (a `Stream<void> available` the sync engine subscribes to) — same shapes, renamed to the real contract's `attemptPublicId`/`pinnedItemPublicId` fields.
- **Diverge from the reference's status model.** The old `AnswerSyncStatus` enum was `{pending, syncing, synced, failed}` — a single `failed` bucket that does not distinguish "keep retrying" from "stop forever." The new enum must be `{pending, syncing, synced, terminalRejected}`: transient failures (network error, 5xx, 429) return the row to `pending` for the next flush pass; a stale-task or past-deadline rejection moves the row to `terminalRejected` and the sync engine must never select a `terminalRejected` row in its pending-query again. This split is the single most important divergence from the reference design — see Risks below on why the *precise* trigger for `terminalRejected` is only provisional in this phase.
- **Diverge from the reference's canary source.** The old `NetworkCanary` piggybacked on a successful timer-sync poll ("the exam API is reachable" as the truth signal, since a captive portal can report OS-level connectivity while the API itself is unreachable). This plan's canary is `connectivity_plus`-based instead (per `plan.md`'s Research Summary and this phase's scope note) because Phase 4's timer service is a separate, later-built component and the outbox must not take a hard dependency on it just to know "we're online." Accept the tradeoff explicitly: `connectivity_plus` reports OS-level connectivity, which can be true while the API itself is unreachable (captive portal, DNS-only outage) — this is why a **periodic fallback tick** (Design Constraint below) is mandatory here, not optional, unlike the reference design which had none. A flush attempt that fails with `NetworkException` simply leaves the row `pending` for the next tick regardless of source, so a false-positive canary event costs nothing beyond one wasted attempt.
- A periodic fallback `Timer` (e.g. every 30–60s, exact interval a build-time decision) must trigger a flush pass independently of the canary stream, in case a connectivity transition is missed (e.g. app was backgrounded across the transition, or the OS event never fires in an edge case). The canary is the fast path; the periodic tick is the correctness backstop.
- `payload` is stored as an **opaque string column** — the outbox schema must never attempt to parse, validate, or coerce it based on task type. Per `plan.md`'s risk analysis, a bug in payload construction at a task-type call site (Phase 5/6) must be caught by that call site's own tests, not silently "fixed" or misvalidated by a generic transport/storage layer that has no business knowing what a `WRITE_ESSAY` payload should look like versus an `MC_READING_SINGLE` one.
- `createdAt`/`updatedAt` remain audit-only columns, exactly as the reference design intended — never read by any retry/backoff/elapsed-time logic. Phase 4's `TimerService` (not this outbox) is the sole owner of elapsed-time truth for anything exam-clock-related; this phase's timestamps exist only for debugging and DAO-level ordering, never for countdown or deadline math.
- `SyncEngine` is a plain Dart service, not a `Bloc` — it is started/stopped by the exam-delivery `Bloc`'s lifecycle (Phase 3 onward), matching the reference's own doc comment ("shared service the exam-delivery Bloc starts and stops"). It must not import or depend on `flutter_bloc` types.
- The only caller of `ApiClient`'s answer-submission method is `SyncEngine._flushOne`. Per `plan.md`'s ordering decision, no widget or UI-facing `Bloc` (Phase 5/6) may ever call `ApiClient` directly to submit an answer — the outbox DAO's `upsertAnswer` is the only write path available to them. This phase must add the answer-submission method to `ApiClient` (or a thin wrapper) but must not export it in a way that invites a shortcut call site later; a code comment on the method should say as much.
- The exact server-side trigger for `terminalRejected` is provisional in this phase. Phase 1's `ApiExceptions` hierarchy (as scoped) does not yet include typed `NotCurrentTaskException`/`ResponseWindowExpiredException` subclasses — those are added in Phase 7. Both conditions return **HTTP 409** from the real `pte-api` (confirmed by direct inspection of `NotCurrentTaskException`/`ResponseWindowExpiredException` in `exam-delivery`'s `domain/exception` package, both extending `DomainException` with `HttpStatus.CONFLICT`), with the machine-readable distinguishing code carried only in the JSON body's `message` field (`{"success":false,"data":null,"message":"NOT_CURRENT_TASK"}` vs `"RESPONSE_WINDOW_EXPIRED"`) — **not** in the HTTP status, which is identical for both. This phase's `_flushOne` must therefore treat *any* 409 response as `terminalRejected` (a conservative-but-correct heuristic, since every currently-known 409 case on this endpoint is in fact terminal) and store the response body's `message` string in `lastSyncError` for diagnostics. Phase 7 replaces this coarse "409 is terminal" rule with precise type-dispatch once the typed exception subclasses exist, but must not change the underlying behavior for these two cases, only make the "why" explicit and extensible to future distinct 409 causes.

## Steps

1. Define `AnswerOutboxTable` (Drift): `attemptPublicId` (text), `pinnedItemPublicId` (text), `payload` (text, opaque), `status` (text, stores `AnswerSyncStatus.name`), `lastSyncError` (text, nullable), `createdAt`/`updatedAt` (int, epoch ms). Composite primary key `{attemptPublicId, pinnedItemPublicId}`.
2. Define `AnswerSyncStatus` enum: `{pending, syncing, synced, terminalRejected}`. Document on the enum itself that `terminalRejected` rows are never re-queried by the sync engine's pending-query and are, for Milestone 1, a dead end the UI may optionally surface but must never retry.
3. Implement `AnswerOutboxDao`: `upsertAnswer({attemptPublicId, pinnedItemPublicId, payload})` (idempotent `insertOnConflictUpdate`, always resets status to `pending` on a new local write — even over a `terminalRejected` row, since a fresh local edit to what the student believes is still an open task should get one honest attempt, not be silently dropped because a *previous* payload for that same key was rejected), `queryPendingByAttempt(attemptPublicId)`, `queryByAttempt(attemptPublicId)` (all rows, any status — needed by Phase 3's resume reconciliation), `markSynced`, `markTerminalRejected(reason)`, `markPending` (returns a row to retry-pending after a transient failure), `deleteByAttempt`, `checkpointWal()` (`PRAGMA wal_checkpoint(RESTART)`, called after each flush batch).
4. Implement `NetworkCanary` wrapping `connectivity_plus`'s `Connectivity().onConnectivityChanged`, exposing `Stream<void> available` that emits only on a transition *into* a connected state (not on every connectivity event, to avoid redundant flush attempts on lateral transitions like wifi-to-wifi).
5. Add an answer-submission method to `ApiClient` (`POST /attempts/{id}/answers` with `SubmitAnswerRequest{pinnedItemPublicId, payload}`), mapping a 409 response to a distinguishable marker the sync engine can act on (at minimum, surface the response body's `message` string alongside the existing `ConflictException`/`ApiException` type from Phase 1, since Phase 1 does not yet have the precise typed subclasses).
6. Implement `SyncEngine`: `startSync(attemptPublicId)` / `stopSync()` per the reference's single-attempt-at-a-time contract (`StateError` if called for a different attempt while already running); subscribes to `NetworkCanary.available` *and* a periodic fallback `Timer`, both triggering the same `_flush(attemptPublicId)` path; `_flush` queries all `pending` rows for the attempt and calls `_flushOne` on each; `_flushOne` catches a 409/conflict response and calls `markTerminalRejected`, catches any other `ApiException`/`NetworkException` and leaves the row `pending` (no-op, next tick retries), and on success calls `markSynced`.
7. Wire `flutter_secure_storage`-free Drift database bootstrap (the `AppDatabase` shell from Phase 0) to include `AnswerOutboxTable`, generating the `.g.dart` DAO/table code.
8. Test: `AnswerOutboxDao` upsert is idempotent — two `upsertAnswer` calls with the same `(attemptPublicId, pinnedItemPublicId)` and different payloads leave exactly one row with the latest payload, not two rows.
9. Test: a fresh local edit via `upsertAnswer` resets a `terminalRejected` row back to `pending` (Step 3's documented behavior), verified explicitly since it is easy to get backwards (i.e. accidentally preserving `terminalRejected` across a new local write).
10. Test: `SyncEngine` flushes exactly the `pending` rows for the started attempt, never rows belonging to a different `attemptPublicId` and never `terminalRejected`/`synced` rows, using a fake `AnswerOutboxDao` and fake `ApiClient` (`mocktail`).
11. Test: a 409 response from the fake `ApiClient` results in `markTerminalRejected` being called, never a retry loop; a `NetworkException` leaves the row untouched for the next tick.
12. Test: process-death survival — write rows via the real Drift database (not a fake/in-memory-only stub), tear down and reconstruct the database instance from the same file path, and confirm the rows and their statuses are intact (this is the core reliability property named in the spec's Non-Functional Requirements; a fake/mocked DAO alone would not actually prove it).
13. Test: starting `SyncEngine` for a second, different `attemptPublicId` while already running throws `StateError`; calling `startSync` again with the *same* `attemptPublicId` while already running is a no-op, not an error (matches the reference's documented behavior).

## Success Criteria

- [ ] `AnswerOutboxTable` uses composite primary key `(attemptPublicId, pinnedItemPublicId)` and idempotently upserts rather than duplicating on repeated writes.
- [ ] `AnswerSyncStatus` has a distinct `terminalRejected` state, separate from `pending`, and no code path re-queries a `terminalRejected` row as flushable.
- [ ] A real (non-mocked) Drift/SQLite-backed outbox row survives destruction and reconstruction of the database instance, proving process-death survival.
- [ ] `SyncEngine` flushes on both a `connectivity_plus`-driven canary event and an independent periodic fallback tick — verified as two distinct trigger paths, not just one implemented and the other assumed.
- [ ] A 409 response from `ApiClient` results in the row being marked `terminalRejected`, never retried again by any subsequent flush pass.
- [ ] No production call site outside `SyncEngine._flushOne` invokes `ApiClient`'s answer-submission method.
- [ ] `payload` is never parsed, validated, or type-branched on inside the outbox table/DAO/sync engine — it is opaque end to end within this phase's code.

## Risks

- **MEDIUM**: Treating "any 409 from the answers endpoint is terminal" is correct for the two known causes today (`NOT_CURRENT_TASK`, `RESPONSE_WINDOW_EXPIRED`, both confirmed via direct inspection of `pte-api`'s `exam-delivery` service) but is a status-code-level heuristic, not a type-level one — if a future, unrelated 409 cause is added to the `answers` endpoint that is actually transient, this phase's coarse rule would incorrectly mark it terminal. Mitigation: Phase 7 replaces the heuristic with precise exception-type dispatch once Phase 1's `ApiExceptions` hierarchy grows the typed subclasses; this phase's Design Constraints call out the heuristic as provisional specifically so Phase 7's hardening isn't mistaken for optional polish.
- **MEDIUM**: `connectivity_plus` reporting OS-level connectivity rather than actual API reachability means a canary-triggered flush can fail silently and repeatedly in a captive-portal scenario, relying entirely on the periodic fallback tick to eventually make progress once real connectivity returns. Mitigation: the periodic fallback tick is a mandatory (not optional) Design Constraint in this phase specifically to bound how long a false-positive canary signal can stall a flush; Phase 7's kill/cold-restart hardening test should include at least one scenario with a flaky/false-positive connectivity signal if feasible.
- **LOW**: WAL checkpointing after every flush batch (carried over from the reference design) trades a small amount of I/O overhead for bounded WAL file growth under high-frequency answer writes (e.g. rapid typing triggering frequent upserts in Phase 5) — acceptable for Milestone 1's scope but worth re-measuring if Phase 5's debounce interval turns out to be very short.

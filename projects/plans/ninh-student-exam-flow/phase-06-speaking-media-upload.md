# Phase 6: Speaking Task & Media Upload

## Requirements

Build the `READ_ALOUD` task screen and the 3-step media upload flow: `record`-package capture to a durable local temp file → `POST /api/media/objects` (presigned URL) → raw `PUT` to MinIO (no auth header) → `POST /api/media/objects/{id}/complete` → the resulting `mediaPublicId` submitted through Phase 2's outbox exactly like any other answer payload. The presigned URL expires in 900 seconds; if the sync/upload coordinator attempts a deferred upload after that window has passed, it must re-request a fresh presigned URL rather than retry the dead one — this is a distinct retry semantic from the generic text-payload outbox retry Phase 2 already built.

Maps to: **P1 Story #5 ("record and submit a READ_ALOUD audio response") | FR-08**

## Design Constraints

- Recording via the `record` package writes to a local temp file path (e.g. under `getTemporaryDirectory()`), never held only as an in-memory buffer — a deferred/retried upload must survive process death, which an in-memory-only recording cannot.
- **`MediaUploadCoordinator` must be wired to the same two trigger sources as Phase 2's `SyncEngine`** — a `NetworkCanary.available` subscription and a periodic fallback `Timer` (reuse the same instances via `GetIt`, rather than standing up a second independent canary/timer pair) — each triggering a scan of all `PendingMediaUploadTable` rows not yet at `ready` status. Without this, a recording made offline would only ever attempt its upload once, immediately after the recording stops, and would never retry once connectivity actually returns — directly breaking the spec's own Success Criterion that an offline `READ_ALOUD` recording uploads and submits once connectivity is restored.
- **The media upload pipeline is a separate track from Phase 2's answer outbox, not an extension of it.** Phase 2's `AnswerOutboxTable`/`SyncEngine` only ever store and flush a fully-resolved `mediaPublicId` string as `payload` — they must never be taught about presigned URLs, upload progress, or re-presign logic. This phase introduces its own small persistence structure (a `PendingMediaUploadTable`, composite-keyed `(attemptPublicId, pinnedItemPublicId)` for the same idempotent-upsert reason Phase 2's table uses that key) that tracks `localFilePath`, `mediaPublicId` (nullable until presigned), `uploadUrl`/`uploadUrlExpiresAt` (nullable, re-set on every presign), and a status (`recorded → uploading → uploaded → completing → ready`). Only once a row reaches `ready` does this phase call `AnswerOutboxDao.upsertAnswer` with `payload = mediaPublicId` — at that point the media-specific machinery is done and Phase 2's ordinary retry semantics take over for the (now perfectly generic) answer submission itself.
- The `PUT {uploadUrl}` request must **not** go through Phase 1's authenticated `Dio` instance/`TokenRefreshInterceptor` chain — the presigned URL itself is the credential (900s TTL), and attaching an `Authorization` header would be sending a bearer token to MinIO, a different origin than the API gateway, for no reason and with real (if narrow) credential-leakage risk. Use a second, bare `Dio` (or `package:http`) instance with no interceptors — the same structural idea as Phase 1's `refreshDio` (a second un-intercepted instance to avoid something specific to auth), reused here for the opposite reason (no auth at all, rather than avoiding refresh recursion).
- Expired-URL detection is failure-driven, not clock-driven-preemptive: attempt the `PUT` with whatever `uploadUrl` is on record; if it fails with a signature/expiry-shaped error (MinIO returns its own error body on an expired presigned URL, distinct from `pte-api`'s `ApiResponse` envelope since this request never touches the gateway), request a fresh presign via `POST /api/media/objects` and retry the `PUT` with the new URL against the *same* local file — never re-record. A proactive "is `uploadUrlExpiresAt` in the past" check before attempting the `PUT` is a reasonable optimization to avoid a doomed request, but the failure-driven fallback must exist regardless, since a URL can expire in the gap between that check and the request actually landing.
- The recording itself is never resumed mid-upload if interrupted — `PUT` is a single non-chunked request, not resumable, so an interrupted `PUT` is retried from the start of the same local file, not partially continued.
- `POST /objects/{mediaPublicId}/complete` takes no body and finalizes the upload; only after this call succeeds does the row move to `ready` and get handed off to the ordinary answer outbox. A `mediaPublicId` that reached `uploaded` but never got a successful `complete` call must not be submitted as an answer payload — the server would not recognize it as finalized.

## Steps

1. Define `PendingMediaUploadTable` (Drift): `attemptPublicId`, `pinnedItemPublicId` (composite PK), `localFilePath`, `mediaPublicId` (nullable), `uploadUrl` (nullable), `uploadUrlExpiresAt` (nullable, epoch ms), `status` (text, enum name), `lastError` (nullable). Generate the corresponding DAO with upsert-by-key, query-by-status, and status-transition methods mirroring Phase 2's `AnswerOutboxDao` shape.
2. Implement recording capture: start/stop via `record`, writing to a path derived from `(attemptPublicId, pinnedItemPublicId)` so a restart can locate the same file; on stop, upsert a `PendingMediaUploadTable` row with `status = recorded`.
3. Implement `MediaRepository`: `requestPresign(contentType)` → `POST /api/media/objects` (`contentType` one of `audio/mpeg | audio/wav | audio/webm`, matching whatever format `record` actually outputs) returning `{mediaPublicId, uploadUrl, expiresInSeconds}`; `completeUpload(mediaPublicId)` → `POST /api/media/objects/{id}/complete`, no body. Both go through Phase 1's normal authenticated `ApiClient`.
4. Implement a bare, uninterceptored `Dio`/`http` client dedicated to the raw `PUT {uploadUrl}` call — instantiated once (e.g. via `GetIt`) and never given the auth-header interceptor, matching the Design Constraint above; confirm via a code comment (and Step 9's test) that no `Authorization` header is ever attached to this specific call.
5. Implement `MediaUploadCoordinator` (plain Dart service, not a `Bloc`, mirroring `SyncEngine`'s shape from Phase 2): drives a `recorded` row through `requestPresign` → `uploading` → raw `PUT` → `uploaded` → `completeUpload` → `completing` → `ready`; on a `PUT` failure recognized as an expired/invalid presigned URL, re-invokes `requestPresign` and retries the `PUT` against the same `localFilePath` rather than surfacing a generic failure. Subscribe to the shared `NetworkCanary.available` stream and a periodic fallback `Timer` (same instances Phase 2's `SyncEngine` uses, resolved via `GetIt`), each triggering a scan of all non-`ready` rows and attempting to advance each one from its current status — this is what makes an offline-recorded upload eventually complete once connectivity returns, not just the initial post-recording attempt.
6. On a row reaching `ready`, call `AnswerOutboxDao.upsertAnswer(attemptPublicId, pinnedItemPublicId, payload: mediaPublicId)` (Phase 2) and mark the `PendingMediaUploadTable` row done (e.g. delete it, or a terminal `submitted` status if keeping it for diagnostics is preferred). Per Phase 2's active-task exclusion, this outbox row is not flushed by background triggers while its task is still active — the `ReadAloudScreen`'s navigate-away handler (Step 7) must call `SyncEngine.flushOne(pinnedItemPublicId)` explicitly, exactly like Phase 5's task-type screens, once the row is confirmed `ready`.
7. Implement `ReadAloudScreen`: record/stop UI, a distinct "processing/uploading" indicator separate from the generic outbox-flush indicator (since a `READ_ALOUD` answer is not yet in the outbox at all until Step 6 completes) — plug it into the task-type dispatcher established in Phase 5. The navigate-away handler must not proceed to the next task while the row is still short of `ready` (block/disable "next" with a visible "still uploading" state) — advancing before the media pipeline finishes would leave nothing for the eventual `flushOne` call to submit for this task.
8. Test: happy-path coordinator run (`recorded → ... → ready`) against a fake `MediaRepository`/raw-upload client produces exactly one `AnswerOutboxDao.upsertAnswer` call with `payload` equal to the resolved `mediaPublicId`, and no earlier partial state (e.g. `uploading`) ever reaches the outbox.
9. Test: the raw upload `Dio`/`http` instance used for `PUT {uploadUrl}` carries no `Authorization` header — assert directly on the request configuration/interceptor list, not just on a successful mocked response.
10. Test: a `PUT` failure simulated as an expired-URL response (using a fake clock advanced past 900s, or a directly injected failure) triggers a fresh `requestPresign` call and a retried `PUT` against the same local file path — not a retry against the stale `uploadUrl`, and not a fresh recording.
11. Test: process-death simulation — persist a `PendingMediaUploadTable` row at `uploaded` status (upload succeeded, `complete` not yet called) via the real Drift database, reconstruct the coordinator/DAO from the same file, and confirm it resumes at `completing`/`complete` rather than re-uploading or discarding the row.
12. Test: a row left at `recorded` (offline when recording stopped, so the initial presign attempt never happened or failed) advances through the full pipeline once a simulated `NetworkCanary.available` event or periodic tick fires — using a fake `MediaRepository`/upload client, not a real network — confirming the coordinator doesn't just run once at recording-stop time and then go silent.
13. Test: navigating away from a `READ_ALOUD` task calls `SyncEngine.flushOne` exactly once, and only after the row has reached `ready` — attempting to navigate while still `uploading`/`completing` is blocked by the UI (Step 7), not silently allowed to proceed with nothing to flush.

## Success Criteria

- [ ] A `READ_ALOUD` recording, once fully uploaded and completed, results in exactly one Phase 2 outbox row whose `payload` is the `mediaPublicId` string — never raw audio bytes, never an intermediate upload-state marker.
- [ ] The raw `PUT {uploadUrl}` request never carries the app's bearer `Authorization` header, verified directly, not assumed from "it uses a different `Dio` instance."
- [ ] An expired presigned URL encountered during a deferred upload triggers a fresh presign + retried `PUT` against the same local recording file, never a re-record and never a dead-URL retry loop.
- [ ] A process-death mid-upload (recording done, upload/complete not yet finished) is recoverable on relaunch from the persisted `PendingMediaUploadTable` row, without re-recording.
- [ ] Phase 2's `AnswerOutboxTable`/`SyncEngine` contain no media-upload-specific logic (no presign/URL/expiry awareness) — confirmed by code review that this phase added zero changes to Phase 2's files.
- [ ] `MediaUploadCoordinator` retries a `recorded`-or-later row on both a connectivity-restore event and a periodic fallback tick — an offline recording is not limited to a single attempt at recording-stop time.
- [ ] Navigating away from a `READ_ALOUD` task only proceeds once its row has reached `ready`, and triggers exactly one `SyncEngine.flushOne` call at that point.

## Risks

- **LOW (carried from `plan.md`)**: The 900-second presigned-URL TTL creates a narrow window where a student who records offline, later goes online, requests a presign, but takes longer than 15 minutes to actually `PUT` the file (large recording, slow connection) hits an expired URL on the very first attempt, not just on a later retry. Mitigation: the Design Constraint's failure-driven (not only proactive-clock-check) re-presign path exists specifically to cover this — Step 10's test should include a variant where the expiry happens *during* the very first attempted `PUT`, not only on a subsequently retried one.
- **MEDIUM (elevated for this app's desktop/Windows target)**: `record`'s actual output `contentType` (`audio/mpeg` vs `audio/wav` vs `audio/webm`) depends on platform/codec configuration chosen when this phase wires up the recorder — if it doesn't match one of the three values `POST /api/media/objects` accepts, the presign call itself would fail before any upload logic is even exercised. This risk is larger than usual here because Milestone 1 targets desktop (Windows), a less-common `record` target than mobile — confirm both (a) that `record` actually supports Windows recording at all in the installed version, and (b) the configured recording format against the accepted `contentType` values, as an early spike in this phase (or even pulled into Phase 0 as a go/no-go check), not discovered only when the first real device test fails. If `record`'s Windows support proves inadequate, this phase's scope may need to shift to an alternative recording package before the rest of the upload pipeline is built against it.
- **LOW**: A `PendingMediaUploadTable` row that reaches `uploaded` but whose `completeUpload` call fails repeatedly (e.g. transient server error) has no terminal-rejected equivalent defined in this phase, unlike Phase 2's outbox — it will keep retrying `complete` indefinitely via whatever retry trigger the coordinator uses. Given `complete` has no plausible *permanent* rejection reason analogous to `NOT_CURRENT_TASK`/`RESPONSE_WINDOW_EXPIRED` (the upload already succeeded; `complete` merely finalizes it), unbounded retry is likely the correct behavior here rather than a gap. However, unbounded retry with no backoff at all (unlike Phase 7's 429 handling for the answer-outbox path) risks hammering the media service under sustained transient failure — Phase 7 extends its backoff mechanism to cover `MediaUploadCoordinator`'s retry loop too, not just `SyncEngine`'s, so this is resolved there rather than left unexamined.

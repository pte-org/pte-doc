Status: 🟡 Not Started

Target platform: Desktop (Windows primary)

## Overview

Full rewrite of `pte-app` (Flutter) into the student-facing exam-taking client for `pte-api`: login with silent token refresh, starting/resuming an attempt, answering all 3 Milestone-1 task types (`MC_READING_SINGLE`, `WRITE_ESSAY`, `READ_ALOUD`) through an offline-first Drift-backed outbox, a poll-resynced server-authoritative timer, force-submit, and a published/not-yet-published report screen. The old `features/*`/`core/*` scaffold (pre-pivot "Aptis", different backend/domain) is deleted outright; only three of its patterns are kept as *design references* (composite-key outbox table, canary-driven sync engine, single-flight token-refresh interceptor) and rebuilt from scratch against the real `pte-api` contract. Unblocks the first end-to-end student-facing verification of Milestone 1's backend (already smoke-tested manually per Member 1).

## Research Summary

Decisions below were established via prior user Q&A and direct codebase/backend inspection (not re-derived here):

1. **Full rewrite, pattern-reuse only**: `pte-app/lib/core/{storage/tables/answer_outbox_table.dart, sync/sync_engine.dart, network/interceptors/token_refresh_interceptor.dart}` are deleted along with the rest of the old scaffold, but their *shape* — composite primary key `(attemptId, questionId)`-style outbox, a canary-driven `SyncEngine.startSync(attemptId)`/`stopSync()` with a `NetworkCanary` stream, and a single-flight `TokenRefreshInterceptor` using a second un-intercepted Dio instance plus `Future<String>? _refreshInFlight` — is the concrete reference every equivalent Phase 1/2 component is rebuilt from, adapted to the new `pte-api` field names (`attemptPublicId`/`pinnedItemPublicId` instead of `attemptId`/`questionId`) and endpoint shapes.
2. **Outbox-first ordering**: the offline answer outbox (Phase 2) is built and tested before any task-type UI exists (Phase 5/6), so every task-type screen is wired to it from day one rather than retrofitted — no call site is ever allowed to submit answers directly to `ApiClient`.
3. **Timer is poll-only**: confirmed directly against the backend that no WebSocket/SSE/push mechanism exists for timer or task state; `GET /api/exam-delivery/attempts/{id}/timer` polling is the only mechanism, and this is a hard, non-negotiable constraint on Phase 4 — no push-based design should be attempted or left as a "future hook."
4. **Dependency baseline**: `pte-app/pubspec.yaml` already carries `flutter_bloc`, `dio`, `drift`, `sqlite3`, `get_it`, `record`, `just_audio`, `equatable`, `connectivity_plus`, `logger` — all kept as-is. New additions: `flutter_secure_storage` (refresh-token persistence) and dev-only `bloc_test` + `mocktail`, unconditionally. `sqlite3_flutter_libs` is added **conditionally** — drift's packaging model changed around 2.32+ (the already-pinned `drift ^2.34.0`/`sqlite3 ^3.3.3` may be past the point where this package is required at all); Phase 0 confirms via drift's current docs and/or a smoke build before adding it, rather than asserting the older "always required" rationale as fact.
5. **Coding standards baseline**: `pte-app/CLAUDE.md` and `pte-app/docs/CODING_STANDARDS_APP.md` mandate feature-first Clean Architecture (`data/domain/presentation`), `snake_case` filenames, sealed-class BLoC events, immutable per-case BLoC states (no boolean-flag state class), `GetIt`-based `{feature}_module.dart` DI registration, a 300-line file cap (exempting Drift/Freezed/JSON-codegen `.g.dart` output), mandatory `mounted` checks after every `await` before touching `BuildContext`, controller/subscription disposal, and `BlocSelector` over `BlocBuilder` for partial-state-dependent widgets. `flutter analyze` + `flutter test` must exit zero-issue at Milestone-1 handoff (Phase 9 is the dedicated gate for this).
6. **Member-3 dependency (open risk)**: the mechanism by which a student obtains a `sessionPublicId` (self-service session list vs. a host-shared/deep-linked value) is unresolved, owned by Member 3, and not expected to resolve before this plan executes. Phase 3 implements a placeholder manual-entry/deep-link screen behind a swappable `SessionEntryRepository`-style interface so that whichever mechanism Member 3 lands on later is a drop-in replacement with no change to the attempt BLoC/repository contract. This is called out explicitly in Phase 3's Design Constraints and again below in Risks.
7. **Backend contract summary** (base URL `http://localhost:8080`, JWT bearer via gateway, RS256/JWKS, Redis rate-limit 20/s burst 40) — full detail lives in `spec.md` FR-01..FR-13; the two contract properties with the widest blast radius across phases are: (a) `SubmitAnswerRequest{pinnedItemPublicId,payload}` is one generic shape for all 3 task types, with `payload` semantics differing per type (decimal-string order index / raw text / media UUID), so the outbox and repository layers must not special-case task type in the transport layer, only at the call site that constructs the payload; and (b) both "not yet published" and "not owned" report states return an indistinguishable 404, so the client must never treat report 404 as a hard error under any circumstance.
8. **Endpoint path convention** (added during red-team review — was originally missing/inconsistent across FR-03/05/09/10 and Phases 2/3/4/7): `ApiClient`'s base URL is `http://localhost:8080` with **no** `/api` suffix; every call site passes the full gateway-relative path, e.g. `/api/exam-delivery/attempts`, `/api/exam-delivery/attempts/{id}/timer`, `/api/exam-delivery/attempts/{id}/answers`, `/api/exam-delivery/attempts/{id}/submit`, `/api/exam-delivery/attempts/{id}/next-task` — the `exam-delivery` service's own `context-path` plus the gateway's route prefix means the bare `/attempts/...` form used in earlier drafts of this plan would 404 at the gateway. `spec.md` and Phases 1–4/7/9 now consistently use the full path; Phase 1's Design Constraints state the base-URL/path-prefix convention explicitly so it isn't rediscovered per call site.
9. **Submit-and-advance semantics + active-task flush exclusion** (added during red-team review — the most significant design addition beyond the original scope): a successful `POST /api/exam-delivery/attempts/{id}/answers` call causes the server to advance the attempt's current-task pointer immediately — submitting is equivalent to "end this task now," not a passive save. Phase 2's `SyncEngine` therefore never flushes the outbox row for the currently-displayed task via its background (canary/periodic) triggers — only via an explicit `flushOne(pinnedItemPublicId)` call made at navigate-away/force-submit time (Phase 5/6's flush-before-navigate hook, Phase 7's force-submit). `SyncEngine.setActiveTask()` (called by Phase 3's `ExamAttemptBloc` on every task transition) tracks which row is currently exempt from background flush. Getting this wrong would mean the outbox's own resilience mechanism — not app kill — becomes the thing that silently discards a student's in-progress answer, directly undermining the spec's top-priority NFR. See Phase 2/3/5/6's Design Constraints for the full mechanism, and the new Risk entry below.

## Risks

- **HIGH (open, external dependency)**: Member 3's session-discovery mechanism (self-service list vs. host-shared link) is unresolved as of this plan's writing. Mitigation: Phase 3 builds a placeholder manual/deep-link entry screen strictly behind a `SessionEntryRepository`-shaped interface consumed only by the attempt BLoC/repository boundary; no other phase may depend on the concrete placeholder implementation. If Member 3's decision lands mid-build, only Phase 3's data-layer implementation needs to change — this is the explicit acceptance test for whether the interface was cut at the right seam.
- **MEDIUM**: Backend contracts in `spec.md` were captured via direct controller/DTO inspection, not a generated OpenAPI spec (none exists yet). If `pte-api` contracts drift before Milestone-1 handoff, the affected phase(s) need a contract-diff pass before their Success Criteria can be re-verified. Mitigation: Phase 9's QA gate includes a final contract spot-check against the running `pte-api` instance, not just against this plan's transcribed contract.
- **MEDIUM**: The generic `SubmitAnswerRequest{pinnedItemPublicId,payload}` shape means a bug in payload construction at one task type's call site (e.g. sending raw text where a decimal-string order index was expected) would not be caught by the transport layer at all — only by task-type-specific tests. Mitigation: Phase 5/6 each include an explicit payload-shape assertion test per task type, and Phase 2's outbox schema stores `payload` as an opaque string so it cannot silently coerce/validate the wrong shape.
- **MEDIUM**: Offline-outbox correctness is the single most safety-critical property in this spec (an answer the student believes was submitted must never silently vanish). Mitigation: Phase 2 is scoped and built before any task-type UI so its process-death-survival property is verified in isolation first; Phase 7 adds a dedicated kill/cold-restart recovery test that exercises the full stack (UI → outbox → sync) rather than the outbox alone.
- **HIGH (added during red-team review)**: The submit-and-advance semantics of `POST /api/exam-delivery/attempts/{id}/answers` (Research Summary item 9) mean a naive "flush everything pending" background sync design would submit the currently-displayed task's answer prematurely, closing it out from under the student without an explicit "submit and move on" action ever being taken. This correctness property spans three phases' code (Phase 2's `SyncEngine.setActiveTask`/`flushOne`, Phase 3's call to `setActiveTask` on every task transition, and Phase 5/6's flush-before-navigate hook calling `flushOne`) rather than being containable to one file. Mitigation: each of those phases' Design Constraints and dedicated tests cover their part of the mechanism; `ck:quality`'s gate for Phases 2, 3, 5, and 6 should specifically cross-check that the three pieces agree with each other, not just that each phase's own tests pass in isolation.
- **LOW**: This plan targets desktop (Windows primary), not mobile — `flutter_secure_storage`'s Windows backend (Credential Locker/DPAPI) is a less-common path for this package than Android Keystore/iOS Keychain, and the `record` package's Windows recording support (Phase 6) is similarly less-tested than its mobile support. Neither is expected to be a Milestone-1 blocker, but Phase 0/1 should verify both early via a smoke check rather than assuming parity with the packages' mobile-oriented documentation, and Phase 9 should not silently skip a final manual confirmation of secure-storage behavior on Windows.
- **LOW**: The 900-second presigned-upload-URL TTL (Phase 6) creates a narrow window where a student who records offline, then goes online, requests a presign, but takes longer than 15 minutes to actually PUT the file (e.g. large recording over a slow connection) would hit an expired URL on the very first attempt, not just on retry. Mitigation: Phase 6's re-presign logic must trigger on any PUT failure indicating URL expiry, not only on a retried/previously-failed upload.

# Phase 3: Session Entry & Attempt Lifecycle

## Requirements

Build `ExamAttemptRepository` (wrapping `POST /api/exam-delivery/attempts` start/resume and `GET /api/exam-delivery/attempts/{id}/next-task` advance) and `ExamAttemptBloc`, plus a placeholder session-ID entry screen behind a swappable `SessionEntryRepository`-shaped interface so Milestone 1 is usable before Member 3's session-discovery UI decision lands. `AttemptTaskResponse.completed=true`/`task:null` must be handled as a first-class terminal state, not an error — the server auto-completes and auto-submits the attempt once tasks run out, and the client must recognize and render that outcome cleanly. Resuming an attempt (calling `POST /api/exam-delivery/attempts` again for a `sessionPublicId` with an in-progress attempt) must reconcile with any Phase 2 outbox rows already pending from a previous app session for that same `attemptPublicId`.

Maps to: **P1 Story #2 ("start or resume an attempt for a given exam session") + P2 Story ("a session-ID entry screen... so Milestone 1 is usable before Member 3's decision lands") | FR-03, FR-04**

## Design Constraints

- `ExamAttemptRepository` depends **only** on Phase 1's `ApiClient` — never on Phase 2's `AnswerOutboxDao`/`SyncEngine` directly. Attempt lifecycle (start/resume/advance/complete) and answer submission are different concerns with different retry/persistence semantics; conflating them here would make it unclear which layer owns which failure mode. The one exception is the resume-reconciliation step below, which reads (not writes through) the outbox DAO from the `Bloc` layer, not the repository layer — see Steps.
- The placeholder session-ID entry screen sits behind a `SessionEntryRepository`-shaped interface (`Future<String> resolveSessionPublicId()`, throwing a `SessionResolutionException` on invalid/empty input — e.g. an empty manual-entry submission or an unparseable deep link — rather than returning an empty string or never resolving; `ExamAttemptBloc` catches it and emits `AttemptError`, the same error state any other repository failure produces), consumed only by `ExamAttemptBloc`. Per `plan.md`'s Risks (Member 3's session-discovery mechanism — self-service list vs. host-shared link — is unresolved as of this plan's writing), this phase's placeholder implementation is a manual text-entry or deep-link-parsing screen, and it must be the *only* thing that changes when Member 3's decision lands; the `Bloc`/repository contract on the other side of the interface — including this error contract — must not need to change. This is the explicit acceptance test for whether the interface was cut at the right seam — do not let any attempt-lifecycle logic leak into the placeholder implementation itself.
- `AttemptTaskResponse{attemptPublicId, attemptStatus, completed, task}` with `completed:true, task:null` is a distinct, named `Bloc` state (e.g. `AttemptCompleted`), not folded into a generic error state and not inferred implicitly by the UI checking `task == null` on every render. The `next-task` endpoint auto-advances past server-expired tasks and can return this terminal shape without any prior error ever occurring — it is a normal, expected outcome of a full attempt, and must read as one in the state machine.
- Resuming is not simply "call start again and hope." When `POST /api/exam-delivery/attempts` returns an in-progress attempt (same `attemptPublicId` as a prior local session), the `Bloc` must query Phase 2's `AnswerOutboxDao.queryByAttempt(attemptPublicId)` for any rows left over from before the app was killed/backgrounded, and ensure `SyncEngine.startSync(attemptPublicId)` is called so those rows get an immediate flush attempt rather than waiting on the next canary event or periodic tick that might be tens of seconds away. This repository does not perform this reconciliation itself (it has no outbox dependency, per the Design Constraint above) — the `Bloc` layer, which legitimately depends on both, is where this composition happens.
- `ExamAttemptBloc` must call Phase 2's `SyncEngine.setActiveTask(pinnedItemPublicId)` every time the current task changes — on the initial `AttemptInProgress` emission, on every subsequent `fetchNextTask` response, and with `null` on `AttemptCompleted` (so no row is exempted from background flush once the attempt is over). This is the `Bloc`-side half of Phase 2's active-task exclusion design constraint; without this call happening at every transition, the exclusion silently stops tracking the true current task and a stale/wrong row could be excluded (or the real current row could be left flushable) instead.
- `POST /api/exam-delivery/attempts/{id}/submit` (force-submit, FR-10) may have its repository method stubbed here for completeness, but is **not** wired to any user-facing `Bloc` event in this phase — per `plan.md`'s phase mapping, the explicit force-submit *action* is Phase 7's scope. Adding the method now without an event that triggers it avoids Phase 7 needing to touch this repository's shape at all.
- Per the spec's Out of Scope note, the `Bloc` must tolerate a server-driven state change occurring mid-attempt (e.g. a proctor-initiated force-submit) gracefully — this phase does not need to build or test proctor-interaction handling, but the state machine must not crash or enter an unrecoverable state if `next-task` or `timer` (Phase 4) responses reflect a task advance the client did not itself trigger. Concretely: `AttemptInProgress` transitions are always driven by the server's response to whatever request was just made, never assumed client-side.
- `ExamAttemptBloc` events are a sealed class; states are separate immutable classes covering at minimum: initial/idle, resolving-session-id, starting-or-resuming, in-progress (carrying the current `task`), completed (terminal), and error (carrying a typed exception from Phase 1's `ApiExceptions`).

## Steps

1. Define `ExamAttemptRepository`: `startOrResumeAttempt(String sessionPublicId)` → `POST /api/exam-delivery/attempts`, returning a domain `AttemptTaskResponse` model (`attemptPublicId`, `attemptStatus`, `completed`, `task` nullable); `fetchNextTask(String attemptPublicId)` → `GET /api/exam-delivery/attempts/{id}/next-task`, same response shape; `forceSubmit(String attemptPublicId)` → `POST /api/exam-delivery/attempts/{id}/submit` (stubbed per Design Constraints, unwired).
2. Define the domain `TaskView` model matching the full field set (`pinnedItemPublicId, orderIndex, totalTasks, section, taskType, title, promptText, audioPromptRef, imagePromptRef, minWordCount, maxWordCount, options[{text, orderIndex}], prepSeconds, responseSeconds, prepDeadline, responseDeadline, serverNow`) — this phase only needs to carry the fields through untouched; Phase 4/5/6 are what actually consume `prepDeadline`/`responseDeadline`/`options` etc.
3. Define `SessionEntryRepository` interface and a placeholder implementation (a simple screen with a text field for `sessionPublicId`, or basic deep-link URI parsing if a scheme is already available in `pte-app`'s existing routing setup — whichever is less speculative to build now). Document in a code comment exactly what Member 3's eventual replacement must implement to be a drop-in swap.
4. Implement `ExamAttemptBloc`: sealed events (`SessionResolutionRequested`, `NextTaskRequested`, `AttemptResumeReconciled` or similar internal event for Step 5's async composition); states (`AttemptIdle`, `AttemptStarting`, `AttemptInProgress(TaskView)`, `AttemptCompleted`, `AttemptError(ApiException)`).
5. Implement resume reconciliation: after a successful `startOrResumeAttempt` call returns an in-progress attempt, the `Bloc` calls `AnswerOutboxDao.queryByAttempt(attemptPublicId)` and `SyncEngine.startSync(attemptPublicId)` before emitting `AttemptInProgress`, so any leftover outbox rows begin flushing immediately rather than passively waiting.
6. Implement `completed:true/task:null` handling: both `startOrResumeAttempt` and `fetchNextTask` responses are checked for this shape first, before checking `task` for rendering — emit `AttemptCompleted` and (per the `Bloc`'s lifecycle contract with Phase 2) call `SyncEngine.stopSync()` since no further answers can be submitted for a completed attempt.
7. Wire the placeholder session-entry screen to dispatch `SessionResolutionRequested` into `ExamAttemptBloc`, listening for `AttemptStarting`/`AttemptInProgress`/`AttemptError` to drive navigation (via UI listening to `Bloc` state, never the `Bloc` holding a `BuildContext`, consistent with Phase 1's `AuthBloc` constraint); a `SessionResolutionException` from the placeholder implementation is caught and re-emitted as `AttemptError`.
8. Call `SyncEngine.setActiveTask(task.pinnedItemPublicId)` at every point `ExamAttemptBloc` emits `AttemptInProgress` (initial start/resume and every subsequent `fetchNextTask`), and `SyncEngine.setActiveTask(null)` immediately before emitting `AttemptCompleted` — per Phase 2's active-task exclusion design constraint, this call must happen at every transition, not just the first one.
9. Test: `startOrResumeAttempt` returning `completed:true, task:null` produces `AttemptCompleted`, never `AttemptError`.
10. Test: resuming an attempt with pre-existing `pending` outbox rows (seeded via a fake `AnswerOutboxDao`) triggers `SyncEngine.startSync` before `AttemptInProgress` is emitted — verifies the reconciliation ordering, not just that the method is called at some point.
11. Test: swapping the placeholder `SessionEntryRepository` implementation for a second fake implementation (simulating Member 3's eventual replacement) requires no change to `ExamAttemptBloc` — this is the explicit interface-seam acceptance test called out in `plan.md`'s Risks.
12. Test: `AttemptCompleted` calls `SyncEngine.stopSync()` exactly once; a subsequent stray `NextTaskRequested` event dispatched after `AttemptCompleted` does not crash the `Bloc` or re-open a stopped sync session.
13. Test: a `SessionEntryRepository` that throws `SessionResolutionException` (fake implementation) results in `AttemptError`, never a crash or an unresolved/hanging state.
14. Test: `SyncEngine.setActiveTask` is called with the new task's `pinnedItemPublicId` on every `AttemptInProgress` emission (including a second call after `fetchNextTask` returns a different task) and with `null` immediately before `AttemptCompleted` — verified via a fake `SyncEngine` (`mocktail`) capturing call arguments in order, not just call count.

## Success Criteria

- [x] `ExamAttemptRepository` has no import of or dependency on `AnswerOutboxDao`/`SyncEngine`.
- [x] `AttemptTaskResponse.completed=true`/`task:null` renders as a dedicated terminal UI state, never the generic error state.
- [x] Resuming an attempt with outbox rows left over from a prior app session triggers an immediate flush attempt (via `SyncEngine.startSync` + the new `SyncEngine.flushNow`), not a passive wait for the next canary/periodic tick.
- [x] The placeholder session-entry screen is swappable for a different implementation of `SessionEntryRepository` with zero changes required to `ExamAttemptBloc` or `ExamAttemptRepository`.
- [x] `ExamAttemptBloc` events are sealed; states are separate immutable classes with no boolean-flag shape.
- [x] A server-driven task advance the client did not itself request (simulated in tests) does not crash or corrupt the `Bloc`'s state machine.
- [x] `SyncEngine.setActiveTask` is called with the correct `pinnedItemPublicId` on every task transition and with `null` on completion — verified in order, not just presence.
- [x] A `SessionResolutionException` from the session-entry implementation produces `AttemptError`, never a crash or a hang.

## Risks

- **HIGH (open, external dependency, carried from `plan.md`)**: Member 3's session-discovery mechanism (self-service list vs. host-shared link) is unresolved as of this plan's writing. This phase's entire mitigation *is* the `SessionEntryRepository` seam — if that interface is cut wrong (e.g. the placeholder leaks a manual-entry-specific concept like "raw text input" into the `Bloc`'s event shape instead of just a resolved `sessionPublicId` string), Member 3's eventual replacement will not be a clean swap and this phase's Success Criteria's swap test would need to be revisited. Treat Step 10's test as load-bearing, not a formality.
- **MEDIUM**: The two attempt-lifecycle endpoints (`POST /api/exam-delivery/attempts`, `GET /api/exam-delivery/attempts/{id}/next-task`) both return the same `AttemptTaskResponse` shape, which is convenient but means a caller that forgets to check `completed` first and instead null-checks `task` directly will silently mishandle the terminal state as if the task list were merely "not loaded yet." Mitigation: Step 6 explicitly orders the check (`completed` before `task`), and Step 8's test targets this exact ordering bug.
- **LOW**: Because `ExamAttemptBloc` composes both `ExamAttemptRepository` and Phase 2's `AnswerOutboxDao`/`SyncEngine` for resume reconciliation, this `Bloc` has more dependencies than a typical feature `Bloc` in this codebase. Acceptable for Milestone 1's scope, but Phase 9's QA gate should specifically check this `Bloc` isn't exceeding the 300-line file cap once Phase 4–7 add their own event/state cases on top of it.

# Phase 4: Timer Service & Attempt Shell

## Requirements

Build the poll-resynced, server-authoritative `TimerService` and the shared exam shell (`ExamAppBar`, `ExamBottomBar`, phase indicator) that every task-type screen (Phase 5/6) renders inside. The countdown must be seeded from `TaskView.serverNow` vs. `prepDeadline`/`responseDeadline` and computed via `Stopwatch`, never `DateTime.now()`, so a device clock change mid-exam has zero effect on the displayed value. `GET /attempts/{id}/timer` is the only resync mechanism — there is no push/WebSocket path on the backend, confirmed directly against `pte-api`, and this is a hard, non-negotiable constraint, not a placeholder for a future push design.

Maps to: **P1 Story #6 ("the exam timer reflects the server's authoritative deadline, not just my device's clock") | FR-09**

## Design Constraints

- `TimerService` is `Stopwatch`-based, adapted from the Phase 0 reference copy of the old scaffold's `timer_service.dart`: seed a target duration, `start()` a `Stopwatch`, and compute `remaining = target - stopwatch.elapsed` on every read, clamped at zero — never `target - DateTime.now()`. The reference's injectable `TimerScheduler` typedef (`Timer Function(Duration, void Function())`) is reused verbatim in shape so tests drive poll ticks deterministically instead of waiting on real `Timer`s, exactly as Phase 1's proactive-refresh tests already do for the auth token schedule.
- **The reference's data model does not carry over directly.** The old `TimerService` tracked a single `timeRemainingSeconds` reconciled from a single server-provided value. This spec's contract has two absolute deadlines per task (`prepDeadline`, `responseDeadline`) plus a `phase` field that only exists on `TimerStateResponse` (`GET /attempts/{id}/timer`), **not** on `TaskView` itself. This means the *initial* seed (from a freshly-fetched `TaskView`, before any timer poll has happened) must derive its own phase by comparing `TaskView.serverNow` against `prepDeadline` and `responseDeadline`: `serverNow < prepDeadline` → prep phase, counting down to `prepDeadline`; else `serverNow < responseDeadline` → response phase, counting down to `responseDeadline`; else already past both (task effectively expired at fetch time — render zero/expired immediately rather than a negative or nonsensical countdown). Every poll *after* that first seed uses the server's own authoritative `phase` field directly from `TimerStateResponse`, so this derivation logic is a one-time bootstrap concern, not a permanent parallel source of truth.
- Client timer is UX-only. Every submit action (Phase 5/6/7) must be prepared for the server to reject with a deadline-expired response regardless of what the client's countdown currently displays — the client timer never gates whether a submit is *attempted*, only how it's *displayed*. Do not build any client-side "block submit if timer says zero" logic in this phase; that would let a slow/drifted client clock silently swallow an answer the server would have actually accepted, or conversely let a fast client clock submit something the UI claims is still valid but the server correctly rejects — Phase 7 owns the server-response side of this and this phase must not attempt to preempt it.
- Poll interval is a fixed, injectable `Duration` (default a few seconds — the reference used 10s; keep close to that unless a build-time measurement shows drift exceeding the spec's Non-Functional "should not exceed a few seconds of drift" bound). The poll runs via the same injectable `TimerScheduler`, not a second independent `Timer` mechanism, so a single fake-scheduler test harness drives both the countdown-tick assertions and the poll-cadence assertions.
- `TimerStateResponse.currentOrderIndex` changing between polls without the client itself having requested `next-task` is a signal the server advanced the attempt out from under the client (e.g. a proctor-initiated action, per the spec's Out of Scope note that the client must tolerate this gracefully even though testing the proctor-trigger path itself is not this plan's scope). `TimerService` must surface this as a distinct, observable signal (not silently absorb it into the countdown update) so `ExamAttemptBloc` (Phase 3) can react by re-fetching the current task rather than continuing to display a countdown for a task that is no longer current.
- **The reference shell's timer-ticking logic must not be copied.** The old `ExamScaffold` ran its own independent `Timer.periodic(Duration(seconds: 1))` inside `_ExamScaffoldState`, decrementing a locally-held `_remaining` value once per second — a second, competing "clock" entirely separate from `TimerService`. Copying this pattern would reintroduce exactly the client-clock-as-truth anti-pattern this phase's `TimerService` exists to eliminate. Only the reference's *visual/layout* structure (`ExamAppBar`/`ExamBottomBar`/`ExamContentFrame` composition) is a valid design reference here — the new shell's countdown display must be driven by `TimerService`'s own tick stream (surfaced through whichever `Bloc`/`Cubit` owns it), with no independent per-second timer logic living inside the widget itself.
- The reference shell's `ExamBottomBar` exposed `onBack`/`onFlag`/`onNext` affordances that do not map cleanly onto this contract: there is no "previous task" capability (tasks are served strictly in order via `pinnedItemPublicId`, one at a time, with no endpoint to go back) and no flagging concept anywhere in the spec/FRs. The new shell's bottom bar must be scoped to what the contract actually supports for a given phase (e.g. an implicit "submit and advance" affordance driven by the task-type screen itself in Phase 5/6, plus a separate force-submit affordance wired in Phase 7) rather than the old three-button layout ported wholesale.
- `phase` (prep vs. response) drives which UI region the shared shell shows (e.g. a prep countdown/instructions view vs. the active response-capture view) — this phase builds the shell's capacity to switch on `phase`, but the actual prep/response content per task type is Phase 5/6's scope.

## Steps

1. Define a `TimerPhase` enum (`prep`, `response`) and a `TimerSnapshot` value object (`phase`, `remaining` as `Duration`, `currentOrderIndex`) as the shape `TimerService` exposes on every tick/reconciliation.
2. Implement `TimerService`: `seedFromTask(TaskView task)` deriving initial `phase`/target deadline per the Design Constraint's bootstrap logic; `Stopwatch`-based `currentSnapshot` getter; `reconcileFromServer(TimerStateResponse response)` resetting the `Stopwatch` and adopting the server's own `phase` directly (no re-derivation after the first seed); a `Stream<TimerSnapshot> ticks` broadcast stream emitting on every reconciliation and on a lightweight local sub-second UI tick (for smooth countdown display between polls) driven by the same injectable `TimerScheduler`.
3. Implement `startPolling(attemptPublicId, {Duration interval})` using `TimerScheduler` to schedule `GET /attempts/{id}/timer` calls; on each response, detect a `currentOrderIndex` change versus the last known value and expose it via a separate `Stream<void> taskAdvancedExternally` (or equivalent), distinct from the regular `ticks` stream, so listeners can tell "countdown updated" apart from "the current task itself changed."
4. Integrate `TimerService` with `ExamAttemptBloc` (Phase 3): on `AttemptInProgress`, start the timer seeded from the current `TaskView` and start polling; on `AttemptCompleted`, stop both; on `taskAdvancedExternally`, dispatch an internal `NextTaskRequested`-equivalent event rather than trusting the currently-displayed task.
5. Build `ExamAppBar`: phase indicator + `orderIndex`/`totalTasks` + countdown display, subscribed to `TimerService.ticks` via `BlocSelector` (selecting only the `TimerSnapshot` slice of whatever state holds it) so unrelated state changes elsewhere in the attempt `Bloc` do not force a full app-bar rebuild.
6. Build `ExamBottomBar` scoped to the contract's actual affordances per the Design Constraint above (no back/flag) — leave the specific submit/advance action wiring to Phase 5/6, this phase only builds the container and the phase-driven visual switch.
7. Build the shared `ExamScaffold`-equivalent composing `ExamAppBar` + content region (task-type-specific body, injected by Phase 5/6) + `ExamBottomBar`, with no internal `Timer.periodic` of its own.
8. Test: seeding from a `TaskView` where `serverNow` is between `prepDeadline` and `responseDeadline` derives `phase = response`, not `prep` — and the inverse case, plus the already-expired-at-fetch-time edge case (both deadlines already passed) renders zero/expired immediately.
9. Test: using a fake `TimerScheduler`, verify `reconcileFromServer` resets the `Stopwatch`-derived remaining time to the server's value and adopts the server's `phase` field directly, without the client re-running its own derivation logic on subsequent reconciliations.
10. Test: a poll response with an unchanged `currentOrderIndex` does not emit on `taskAdvancedExternally`; a poll response with a changed `currentOrderIndex` does, exactly once per change.
11. Test: `TimerService.dispose()` cancels the poll scheduler and closes both streams — no timer continues firing after an `AttemptCompleted` transition (verified via the fake scheduler's cancellation, not a real-time wait).

## Success Criteria

- [ ] Countdown arithmetic never calls `DateTime.now()` — confirmed by code review/grep as part of this phase's own check, not deferred to Phase 9.
- [ ] Initial phase derivation from a bare `TaskView` (no prior timer poll) correctly distinguishes prep vs. response vs. already-expired, covered by tests for all three cases.
- [ ] All poll cadence and countdown-tick tests run via the injectable `TimerScheduler` with zero real wall-clock waiting.
- [ ] A `currentOrderIndex` change between polls is surfaced as a distinct signal from a normal countdown tick, and is observably wired to trigger a task refresh rather than being silently absorbed.
- [ ] The shared exam shell contains no independent per-second `Timer` — the countdown display is driven exclusively by `TimerService.ticks`.
- [ ] `ExamAppBar`'s countdown widget rebuilds only on `TimerSnapshot` changes (`BlocSelector`), not on unrelated attempt-state changes.

## Risks

- **MEDIUM**: A poll scheduled only while the app is in the foreground (mirroring Phase 1's proactive-refresh risk) could let the countdown silently drift out of sync with the server while backgrounded, surfacing only once the app resumes and the next poll lands. Mitigation: this is a UX-only concern per this phase's own Design Constraint (client timer never gates submit eligibility) — Phase 7's kill/cold-restart hardening test should include at least one backgrounded-then-resumed scenario to confirm the resync-on-resume path actually fires promptly rather than waiting a full poll interval.
- **LOW**: Deriving the initial phase from `TaskView` fields (`serverNow` vs. `prepDeadline`/`responseDeadline`) duplicates, in a small way, logic the server already encodes explicitly in `TimerStateResponse.phase` — an unavoidable consequence of `TaskView` not carrying a `phase` field itself. If a future backend change adds `phase` directly to `TaskView`, this bootstrap derivation becomes dead code that should be removed rather than left as a redundant parallel check.

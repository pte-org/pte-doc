# Phase 7: Submission Resilience & Hardening

## Requirements

Cross-cutting hardening over Phase 2/5/6's outbox and sync/upload machinery: replace the provisional "any 409 is terminal" heuristic from Phase 2 with precise typed-exception dispatch, add exponential backoff for 429 responses (both `SyncEngine` and Phase 6's `MediaUploadCoordinator`), wire `POST /api/exam-delivery/attempts/{id}/submit` (force-submit) as an explicit `ExamAttemptBloc` action, and run a dedicated kill-app-mid-response → relaunch → confirm-answer-survives-and-flushes verification — the single reliability property the spec names as most important, and one that deserves its own explicit pass rather than living only as implicit unit-test coverage.

Maps to: **FR-06, FR-10, FR-11 + the spec's Non-Functional Requirement ("an answer already accepted by the local outbox must survive app kill / OS termination... the single most important non-functional requirement of this spec") + Success Criteria's kill/relaunch verification**

## Design Constraints

- Extend Phase 1's `ApiExceptions` hierarchy with `NotCurrentTaskException` and a `ResponseWindowExpiredException` (matching `pte-api`'s actual exception class name in `exam-delivery`'s `domain/exception` package — not "`ResponseExpiredException`"; verified by direct inspection, not assumed), reusing Phase 1's `RateLimitException` for 429 as-is. Both new exceptions correspond to server-side `DomainException` subclasses that return **HTTP 409** with the distinguishing code carried only in the JSON body's `message` field (`ApiResponse{success:false, data:null, message:"NOT_CURRENT_TASK"}` vs. `"RESPONSE_WINDOW_EXPIRED"}`) — the HTTP status alone cannot distinguish them from each other or from any other current/future 409 on this endpoint. `ApiClient`'s error-mapping function must therefore branch on the response body's `message` string for a 409 on the `/api/exam-delivery/attempts/{id}/answers` endpoint specifically, not on status code alone; a 409 with an unrecognized `message` value (including the already-known `ANSWER_ALREADY_SUBMITTED` case, which Phase 2's concurrent-flush guard should make rare but not impossible if the guard is ever bypassed) should fall back to Phase 2's original conservative "treat as terminal" behavior rather than crash or silently retry (i.e. tighten the mapping without regressing the safety property Phase 2 already established).
- `SyncEngine._flushOne` (Phase 2) is edited, not replaced: catching `NotCurrentTaskException` or `ResponseWindowExpiredException` now calls `markTerminalRejected` with the specific typed reason (instead of the previous "409 means terminal" blanket rule) and additionally signals `ExamAttemptBloc` to re-fetch `next-task`, since the server has already recorded a blank/rejected answer for that task and the client's local view of "current task" is now stale — the UI should advance, not sit on a task the server considers closed. This mirrors the same `taskAdvancedExternally` signal shape Phase 4's `TimerService` already established for a different trigger (out-of-band task advance), reusing that pattern rather than inventing a second, differently-shaped notification mechanism.
- 429 handling gets genuine backoff, not immediate same-tick retry: track a per-`SyncEngine`-instance (not per-row) cooldown window on a `RateLimitException`, since a 429 from the shared Redis token bucket (20/s burst 40) is a signal about the whole client's request rate, not about any one answer row specifically — retrying every pending row again on the very next canary/periodic tick while still rate-limited only worsens the burst. Respect a `Retry-After` header if `pte-api`/the gateway supplies one; otherwise use capped exponential backoff (e.g. 1s → 2s → 4s → ... capped at a reasonable ceiling), resetting the backoff state on the next successful flush. **Apply the identical backoff mechanism to Phase 6's `MediaUploadCoordinator`** — it shares the same gateway rate limit and currently has no backoff at all on any of its retry paths (`requestPresign`, the raw `PUT`, `completeUpload`); a shared/reusable backoff-tracker class (rather than two independent copies of the same logic) is the cleaner structure, but at minimum both services must respect the same cooldown discipline.
- `POST /api/exam-delivery/attempts/{id}/submit` (force-submit) becomes a real, user-triggerable `ExamAttemptBloc` event in this phase (`ForceSubmitRequested` or similar) — Phase 3 already stubbed the repository method; this phase adds the sealed event, the state transition (to `AttemptCompleted` on success, matching the same terminal state Phase 3 already defined for the natural end-of-tasks case — force-submit and running-out-of-tasks are the same terminal outcome from the UI's perspective), and the UI affordance (e.g. a confirm-then-submit action in Phase 4's shell) that dispatches it.
- The dedicated kill/cold-restart recovery test is this phase's centerpiece, not an afterthought bolted onto existing unit tests. Given Flutter's constraints around fully killing and relaunching a process from an automated test, this phase should attempt an `integration_test`-driven version if feasible within Milestone 1's scope (start app → answer a task → simulate process termination → relaunch → assert outbox state and eventual flush), and must otherwise fall back to a clearly documented, repeatable manual test procedure — either way, this is called out by name in `plan.md`'s Risks as deserving explicit verification, and "we have unit tests for the outbox DAO" is not a substitute for actually exercising the full stack (UI → outbox → sync) end to end.
- This phase touches Phase 2/5/6's existing files (the `ApiExceptions` hierarchy, `SyncEngine`, `ExamAttemptBloc`) rather than adding new standalone features — it is explicitly a hardening pass, and its diff should read as narrowing/correcting behavior already built, not introducing new capability surface area beyond the force-submit wiring FR-10 already scoped to this phase.

## Steps

1. Add `NotCurrentTaskException` and `ResponseWindowExpiredException` to Phase 1's `ApiExceptions` hierarchy (as subclasses of the existing base `ApiException`/`ConflictException`-equivalent type), each carrying the server's `message` code string for diagnostics.
2. Update `ApiClient`'s error-mapping: for the `/api/exam-delivery/attempts/{id}/answers` endpoint's 409 responses, inspect the JSON body's `message` field and map `"NOT_CURRENT_TASK"` → `NotCurrentTaskException`, `"RESPONSE_WINDOW_EXPIRED"` → `ResponseWindowExpiredException`, `"ANSWER_ALREADY_SUBMITTED"` → the existing generic conflict/terminal fallback (no dedicated exception class needed — it's already handled correctly as terminal, this just documents it explicitly instead of leaving it an unstated side effect of the catch-all), any other/unrecognized 409 body → the same fallback.
3. Update `SyncEngine._flushOne` to catch the two new typed exceptions specifically (calling `markTerminalRejected` with the typed reason) instead of Phase 2's blanket "409 is terminal" catch, and to emit a task-advanced-style signal so `ExamAttemptBloc` re-fetches `next-task` after either terminal rejection.
4. Add per-engine backoff state to `SyncEngine` **and** to Phase 6's `MediaUploadCoordinator`: on catching `RateLimitException`, record a cooldown deadline (respecting `Retry-After` if present, else capped exponential backoff from a base interval) and skip flush/upload attempts (for all rows, not per-row) until that deadline passes, resetting the backoff on the next successful flush/upload step. Extract the cooldown-tracking logic into one small shared class both services hold an instance of, rather than duplicating the timer/deadline bookkeeping twice.
5. Add `ForceSubmitRequested` to `ExamAttemptBloc`'s sealed events; on dispatch, call `ExamAttemptRepository.forceSubmit(attemptPublicId)` (already stubbed in Phase 3) and transition to `AttemptCompleted` on success, `AttemptError` on failure; wire a UI affordance (e.g. in Phase 4's shell) that dispatches it, ideally behind a confirmation step given its irreversible nature.
6. Design and execute the kill/cold-restart recovery test: attempt an automated `integration_test`-based version first (answer a `WRITE_ESSAY` or select an `MC_READING_SINGLE` option, force-kill the process, relaunch, assert the answer is present in the outbox and eventually reaches `synced` once connectivity/mocked backend responds); if process-kill automation proves infeasible within this phase's time budget, write a step-by-step manual procedure instead and execute it at least once, recording the outcome.
7. Repeat the same kill/cold-restart procedure for the `READ_ALOUD` media-upload path from Phase 6 (kill mid-upload, specifically at the `uploaded`-but-not-`completed` state if reachable, per Phase 6's own Step 11 unit test — this step is the full-stack version of that unit test, exercised through the real UI rather than a fake DAO).
8. Test: a mocked 409 with `message: "NOT_CURRENT_TASK"` produces `NotCurrentTaskException`, not the generic conflict fallback; same for `"RESPONSE_WINDOW_EXPIRED"`; an unrecognized 409 body still falls back to the prior terminal-by-default behavior rather than throwing an unhandled type error.
9. Test: a mocked `RateLimitException` on one flush attempt suppresses further flush attempts (for all pending rows) until the backoff window elapses, verified via a fake clock/scheduler, not a real wait; a subsequent successful flush resets the backoff state.
10. Test: `ForceSubmitRequested` dispatched from any `AttemptInProgress` state transitions to `AttemptCompleted` on a successful `POST /api/exam-delivery/attempts/{id}/submit`, and to `AttemptError` (not a crash) on failure.
11. Test: a mocked `RateLimitException` on `MediaUploadCoordinator`'s upload path suppresses further upload attempts until its backoff window elapses, mirroring Step 9's `SyncEngine` test — verifies the shared cooldown-tracker class behaves identically in both call sites, not just that `SyncEngine`'s copy works.

## Success Criteria

- [x] A 409 with `message: "NOT_CURRENT_TASK"` or `"RESPONSE_WINDOW_EXPIRED"` is mapped to its specific typed exception, distinguishable from the other and from any generic conflict, purely from the response body — not inferred from HTTP status alone.
- [x] `SyncEngine` never retries a `NotCurrentTaskException`/`ResponseWindowExpiredException`-rejected row, and the UI advances past the stale task rather than sitting on it silently.
- [x] A 429 response measurably suppresses the *entire* sync engine's flush attempts for a backoff window, not just the one row that received the 429 — and the same holds for `MediaUploadCoordinator`'s upload attempts.
- [x] Force-submit is a real, dispatchable `ExamAttemptBloc` event reachable from the UI, transitioning to the same `AttemptCompleted` terminal state as the natural end-of-tasks path.
- [x] The kill/cold-restart recovery test (automated or documented-manual) has actually been executed at least once for both a text-payload answer and the media-upload path, with the outcome recorded — not merely planned.
- [x] This phase's diff touches only existing Phase 1/2/3/5/6 files plus the force-submit wiring — no new feature surface beyond what FR-10 already scopes here.

## Risks

- **HIGH**: If the kill/cold-restart recovery test (Steps 6–7) surfaces an actual data-loss bug (e.g. a debounced Phase 5 write that hadn't yet reached the outbox at kill time, or a Phase 6 upload-coordinator row that doesn't resume correctly), this phase's scope necessarily expands beyond "hardening" into an actual fix in an earlier phase's code — budget for that possibility rather than treating Steps 6–7 as a formality that will obviously pass since the unit tests already did.
- **MEDIUM**: The 409-body-inspection mapping (Step 2) is specific to the `/api/exam-delivery/attempts/{id}/answers` endpoint's known error codes as of this plan's writing; if `pte-api`'s exam-delivery service adds a new 409 cause later without updating this mapping, it silently falls into the "generic terminal fallback" path (safe, but potentially wrong for a genuinely-transient new 409 cause). Mitigation: this is the same tradeoff already accepted in Phase 2's Risks; Phase 9's final contract spot-check is the intended catch-all if new server behavior has appeared since this phase was built.
- **LOW**: Automated process-kill testing in Flutter/`integration_test` has known platform-specific limitations (true OS-level process termination isn't always cleanly triggerable from a test harness, versus a Dart-level "restart the isolate" simulation that doesn't fully prove the SQLite file was actually fsynced to disk). If full automation proves infeasible, the manual procedure is not a lesser substitute for Milestone 1's purposes, but should be documented precisely enough (exact steps, exact task type, exact timing relative to the debounce window) to be repeatable by someone other than whoever ran it originally.

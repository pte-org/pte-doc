# Phase 4: pte-app — TimerService one-shot deadline poll

**P1 coverage: 1/3** — delivers the "recording starts promptly" story (P1 #3) directly.

## Requirements
`TimerService` schedules one additional one-shot poll timed to fire exactly when the local countdown is expected to reach zero, on top of its existing fixed-interval polling — so a short-prep task type's phase transition (prep → response) is reconciled promptly instead of waiting up to the full fixed poll interval. The existing fixed-interval polling and its cadence are unchanged for every task type, and firing the one-shot must never leave two independent periodic-poll chains running in parallel.

## Steps
1. Schedule a one-shot callback timed to fire when the current local countdown is expected to hit zero, using the same injectable scheduling mechanism already used for the existing periodic poll and local tick — not a new or separate timer mechanism.
2. Before that one-shot callback does anything else, explicitly cancel the currently-pending periodic poll timer (not just overwrite the field that references it) — this must happen first, every time, so the one-shot can never end up running alongside a still-armed periodic chain from before it fired.
3. Immediately after that cancellation, trigger a server reconciliation and let the existing periodic-poll routine's own tail-end rescheduling run from there — the net result after the one-shot fires must be exactly one active periodic chain, not two.
4. Re-schedule the one-shot itself (replacing any still-pending one) every time the countdown target is reseeded from a fresh server reconciliation, so it always targets the current, up-to-date deadline rather than a stale one.
5. Ensure the one-shot poll is cancelled cleanly alongside the existing timers whenever polling stops or a task transition begins, so no stale callback from a superseded countdown can ever fire.
6. Ensure a callback from an already-superseded scheduling generation — for both the one-shot and any periodic chain it triggers — is a safe no-op, consistent with how the existing timers already guard against this.
7. **First extend the existing fake-scheduler test convention itself**, per the 2nd-pass plan-reviewer finding: the current `_CapturingScheduler` (`test/unit/features/exam_attempt/timer_service_test.dart`) only captures the raw `(duration, callback)` pairs handed to it — it never captures the `Timer` objects it *returns*. That's insufficient for this phase's regression test: manually re-invoking a captured `callback` closure bypasses real `Timer.cancel()` semantics entirely, so a test built only on closure re-invocation cannot actually tell "the old periodic timer was cancelled" apart from "the old periodic timer's closure still happens to exist and still works" — it would pass even if Step 2's cancellation were silently removed later. Extend `_CapturingScheduler` to also capture and expose the `Timer` it returns for each scheduling call (e.g. a list of `(duration, callback, timer)` records), so tests can assert on real `Timer.isActive` state.
8. Add unit test coverage using the now-extended fake-scheduler: the one-shot poll is scheduled with the expected duration; firing it triggers a reconciliation; firing it leaves **exactly one** active periodic-poll chain afterward, verified by asserting the *previously*-captured periodic `Timer`'s `.isActive` is `false` after the one-shot fires (not merely that a new one was scheduled) — the specific duplicate-chain regression found during plan review; a reseed replaces a previously-scheduled one-shot; a stale-generation callback does nothing.

## Success Criteria
- For a short-prep task type, a unit test confirms a one-shot poll is scheduled to fire at the expected countdown-zero moment and that firing it triggers a server reconciliation, without waiting for the next periodic poll.
- The fake-scheduler test double (`_CapturingScheduler`) is extended to expose the `Timer` objects it returns, not just the raw callback/duration it was invoked with.
- A unit test confirms that firing the one-shot poll leaves exactly one active periodic-poll chain afterward — asserted via the previously-captured periodic `Timer`'s real `.isActive` becoming `false`, not just via closure re-invocation — directly covering the duplicate-poll-chain bug found during plan review (and the 2nd-pass finding that closure-only assertions can't actually detect it).
- A unit test confirms cancelling/stopping the service (or a task transition) leaves no orphaned one-shot callback capable of firing.
- The existing fixed-interval poll and local tick behavior are unchanged — existing `timer_service_test.dart` tests continue to pass unmodified except where directly testing the new behavior.
- All new and existing `pte-app` unit tests pass; `flutter analyze` reports no new issues.

## Risks
- HIGH (plan-reviewer finding): a naive implementation that lets the one-shot callback trigger reconciliation by reusing the periodic poll's own self-rescheduling routine, without first cancelling the still-pending `_pollTimer`, leaves the old periodic `Timer` armed and running on its own original schedule — resulting in two independent periodic-poll chains silently doubling `fetchTimerState` traffic for the rest of that task. Mitigated by Steps 2–3's explicit cancel-before-reconcile ordering and Step 8's dedicated single-active-chain unit test.
- MEDIUM (2nd-pass plan-reviewer finding): a regression test built only on re-invoking the fake scheduler's captured callback closures cannot actually detect a missing cancellation — closure invocation bypasses real `Timer.cancel()` semantics entirely. Mitigated by Step 7 extending `_CapturingScheduler` to also capture and expose the real `Timer` objects it returns, so Step 8's test can assert genuine `.isActive == false` on the previously-active periodic timer.
- The one-shot poll landing at nearly the same real moment as a regularly-scheduled periodic poll (a different, already-considered scenario) is harmless once the cancel-before-reconcile ordering above is in place — both paths converge on the same idempotent reconciliation call, and only one chain is ever active at a time.
- Must not introduce a second, parallel timer-management pattern alongside the existing poll/tick pair — mitigated by reusing the identical injectable scheduler, generation-guard, and cancellation-in-`stop()` conventions already established for both existing timers.

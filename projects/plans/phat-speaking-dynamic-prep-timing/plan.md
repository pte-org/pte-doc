## Overview
Replace the static per-task-*type* `prepSeconds` for the 5 audio-prompt Speaking task types with a per-item value computed server-side from the real uploaded audio's WAV-header duration, and add a one-shot poll to `TimerService` so recording starts promptly once that (often short) prep window genuinely ends — fixing both the label/progress-bar desync and the late-recording-start bugs found during `phat-speaking-audio-prompt-e2e`'s post-completion exploratory walkthrough at their shared root cause.

## Phases
- [x] Phase 1: media — WAV-only audio-prompt uploads + duration extraction — restrict content-type for audio-prompt uploads, compute+persist exact WAV duration at complete-upload, expose it via the existing internal audio-URL response, fail fast on unparseable files, and update the seed script to opt in.
- [x] Phase 2: exam-delivery — dynamic per-item prep timing — consume duration from the existing internal media call, move `preListenSeconds`/`preRecordSeconds` to server config (scoped to the 5 types, nullable elsewhere), compute `prepSeconds`/`prepDeadline` dynamically for the 5 audio-prompt types only.
- [x] Phase 3: pte-app — server-driven sub-stage constants — the 5 Speaking screens read `preListenSeconds`/`preRecordSeconds` (nullable client-side) from the task response instead of local hardcoded constants.
- [x] Phase 4: pte-app — TimerService one-shot deadline poll — add an anticipatory one-shot poll timed to the local countdown reaching zero, cancelling any still-pending periodic poll first so exactly one poll chain is ever active.
- [x] Phase 5: Manual E2E walkthrough — re-seed a known-duration WAV fixture, confirm label/progress-bar agreement and prompt recording start on a real local stack.

## Research Summary
Built entirely on findings already confirmed by source-reading + the brainstorm session (`plans/reports/260831-phat-speaking-dynamic-prep-timing-brainstorm.md`) and the requesting session's own direct source verification, further reconciled against a `plan-reviewer` WARN pass (findings incorporated below and in each phase file) — not re-derived here:

- **Bug 1 root cause (label/progress-bar desync):** `AudioListeningPrepCard` (`audio_prompt_record_body.dart`)'s countdown label already computes `audioSeconds = task.prepSeconds - preListenSeconds - preRecordSeconds` correctly in principle; it only disagrees with the real-audio-driven progress bar (`AudioPromptCubit`, from the prior plan) because `task.prepSeconds` is a static per-type number today, not derived from the real audio's actual duration. Once `prepSeconds` is computed server-side from real audio duration, this existing arithmetic is automatically correct — **no FE display-logic change needed**, confirmed by direct read of the widget.
- **Bug 2 root cause (late recording start):** `TimerService` (`timer_service.dart`) polls every fixed `_defaultPollInterval = Duration(seconds: 10)`; `phase` never self-advances locally between polls (deliberate "trust server exclusively" design, per its own class doc comment). For a short-prep audio-prompt task type, up to 10s worst-case staleness after the real `prepDeadline` is a large fraction of the whole window. User's chosen fix: one additional one-shot poll timed to the local countdown reaching zero, layered on the existing interval poll, reusing the already-injected `TimerScheduler` typedef (used today for both `_scheduleLocalTick` and `_pollTimer`) — not a new timer mechanism, not a lowered global interval. **Plan-reviewer HIGH finding, now resolved in Phase 4:** a naive implementation that lets the one-shot trigger the periodic poll's own self-rescheduling routine without first cancelling the still-pending `_pollTimer` leaves two parallel periodic-poll chains running — Phase 4 now explicitly cancels the pending periodic timer before the one-shot's reconciliation runs, with a dedicated unit test asserting exactly one active chain afterward.
- **Media service has no audio-processing library and no ffmpeg/ffprobe anywhere** (`pte-api/services/media/pom.xml`, shared `pte-api/Dockerfile`) — confirmed by direct inspection during brainstorm. Chosen approach: WAV-only audio-prompt uploads, duration read byte-exact from the WAV header via JDK-native `javax.sound.sampled` — zero new dependency. MP3/WebM audio-prompt support explicitly deferred (P3).
- **`PresignService.requestUpload`/`completeUpload`/`MediaObject` read directly** (`pte-api/services/media/.../service/PresignService.java`, `domain/MediaObject.java`): `RequestUploadRequest` today carries only `contentType` — there is **no existing signal distinguishing "this upload is a Speaking audio prompt for one of the 5 task types" from any other caller of the same generic `/objects` endpoint** (candidates' own recorded answers via `pte-app`'s `MediaRepositoryImpl`, or any other future use). Phase 1 resolves this by adding an explicit, opt-in signal (see Risks). `completeUpload` currently only flips status to `UPLOADED` — it never touches the uploaded bytes; a default (non-presigning) `MinioClient` bean already exists in `MinioConfig` but is currently unused anywhere in `PresignService`, and is the natural way to fetch the object stream for header parsing.
- **`seed-e2e.ps1` is the only real caller of the audio-prompt upload flow in this codebase** — no content-authoring UI exists for it. **Plan-reviewer HIGH finding, now resolved:** Phase 1 Step 7 explicitly updates that script's existing Repeat Sentence audio-upload call to opt into the new signal, so re-seeding after Phase 1 lands continues to produce a WAV-validated, duration-computed audio prompt instead of silently skipping both and breaking Phase 2's pin-time computation at Phase 5.
- **`SnapshotPinService.toPinnedItem`/`resolveAudioUrl` read directly** (`pte-api/services/exam-delivery/.../service/SnapshotPinService.java`) — the exact class the prior plan's Phase 1 already modified for audio-URL resolution. `resolveAudioUrl` already calls `mediaClient.presignGet(...)` once per item with a non-null `audioPromptRef`. **Plan-reviewer MEDIUM finding, now resolved:** rather than adding a second internal call purely to fetch duration (doubling pin-time network calls and failure surface for the same `MediaObject` row), Phase 1 extends the existing internal presigned-download response DTO with the duration field, and Phase 2 consumes it from that same, already-existing call. `PinnedItem.prepSeconds` is set once, per-item, at pin time from `TaskTimingConfig.timingFor(taskType)`; this is the single place dynamic computation must replace that static lookup for the 5 audio-prompt types (every other type: unchanged). Downstream, `TimerState.prepDeadline` is computed from `PinnedItem.prepSeconds` at task-start time (`AttemptMapper`'s doc comment) — so once `PinnedItem.prepSeconds` is dynamic, `prepDeadline` is automatically correct with no separate change needed.
- **`TaskTimingConfig`/`task-timing.json` read directly**: existing schema is `{prepSeconds, responseSeconds}` per task type, loaded once at startup, fails fast (`TaskTimingNotConfiguredException`) on an unconfigured type. Extending this same file's schema with optional `preListenSeconds`/`preRecordSeconds` fields (present only for the 5 audio-prompt types) is the most natural fit for the newly-server-owned sub-stage constants, per spec.md's own Assumptions — confirmed workable by direct read, not a new config surface.
- **`PinnedItem`/`PinnedItemView`/`TaskView`/`AttemptMapper` read directly**: none of these currently carry `preListenSeconds`/`preRecordSeconds` — all four need the new fields threaded through (entity → cache projection → student-facing DTO → mapper), mirroring exactly how `prepSeconds`/`responseSeconds` already flow today. **Plan-reviewer HIGH finding, now resolved:** these new fields must stay nullable/absent for every task type outside the 5 audio-prompt types (both server config and client `TaskView`) — Phase 2 and Phase 3 now explicitly agree on this (nullable on the client, populated only for 5 types on the server), correcting an earlier draft where Phase 3 had described them as required, which would have broken client-side deserialization for every other task type the moment Phase 3 shipped.
- **`MediaClient`/`InternalMediaController` read directly** (`pte-api/services/exam-delivery/.../client/MediaClient.java`, `pte-api/services/media/.../controller/InternalMediaController.java`): the existing internal `GET /internal/media-objects/{publicId}/presigned-url` service-to-service pattern (circuit-breaker-wrapped, `ROLE_INTERNAL_SERVICE`-protected) is reused as-is, with its response DTO extended (not replaced or duplicated) to also carry duration.
- **5 Dart screens read directly** (`pte-app/lib/features/exam_attempt/speaking_writing/presentation/pages/*.dart`): confirmed exact current hardcoded `preListenSeconds`/`preRecordSeconds` pairs — Repeat Sentence 3/3, Retell Lecture 3/10, Answer Short Question 3/3, Summarize Group Discussion 5/10, Respond to a Situation 20/10. Respond to a Situation's screen doc comment explicitly documents its 20s as a deliberate merge of 15s situation-reading + 5s audio-wait — must be preserved unchanged as that type's server-config `preListenSeconds`.

## Risks
- HIGH: no existing signal on `RequestUploadRequest`/`/objects` distinguishes a Speaking-audio-prompt upload (WAV-only, duration-required) from any other caller of the same generic endpoint (candidates' own recorded answers, any future use) — **planner's call, pre-approved per spec.md's Assumptions, but flagged here for plan-reviewer/user visibility**: Phase 1 adds an explicit purpose/usage signal to the upload-request call (e.g. a new optional request field defaulting to the existing general-purpose behavior) so the WAV-only restriction applies only to audio-prompt uploads for the 5 task types, never narrowing the existing general `ALLOWED_CONTENT_TYPES` path candidates' own recordings use. Mitigation: Phase 1 includes a regression test confirming the existing (non-audio-prompt) upload path is completely unaffected.
- HIGH: `completeUpload` currently never touches the uploaded object's bytes — reading the WAV header requires a real MinIO round-trip at complete-upload time that doesn't exist today, using the already-defined but currently-unused default `MinioClient` bean — Mitigation: Phase 1 adds unit tests for valid/corrupt/non-WAV cases against this new read path specifically, not just the content-type gate.
- HIGH (plan-reviewer finding, resolved): `seed-e2e.ps1` is the only real caller of the audio-prompt upload flow in this codebase — if its upload call isn't updated to opt into Phase 1's new signal, re-seeding silently skips WAV validation/duration computation and Phase 2's pin-time duration lookup fails loudly at Phase 5's very first walkthrough attempt. Mitigation: Phase 1 Step 7 explicitly updates the script's existing upload call as part of Phase 1, not deferred to Phase 5.
- HIGH (plan-reviewer finding, resolved): a naive one-shot-poll implementation (Phase 4) that reuses the periodic poll's own self-rescheduling routine without first cancelling the still-pending `_pollTimer` leaves two independent periodic-poll chains running in parallel for the rest of the task, silently doubling `fetchTimerState` traffic. Mitigation: Phase 4 Steps 2–3 explicitly cancel the pending periodic timer before the one-shot's reconciliation/reschedule runs, verified by a dedicated unit test asserting exactly one active chain afterward.
- HIGH (plan-reviewer finding, resolved): `preListenSeconds`/`preRecordSeconds` cannot be modeled as required/non-nullable on the client (`TaskView`) while the server only ever populates them for 5 of ~20 task types (Phase 2's config is explicitly scoped to those 5) — a hard non-null cast would break deserialization for every other task type's response the moment Phase 3 shipped. Mitigation: reconciled as nullable (`int?`) on the client — Phase 2's config/response stays scoped to the 5 types, Phase 3's 5 Speaking screens assert non-null only at their own read sites; every other task type never reads these fields at all.
- MEDIUM: **exact server-config location for `preListenSeconds`/`preRecordSeconds`** — planner's chosen approach is extending `task-timing.json`'s existing per-task-type schema (optional fields, present only for the 5 audio-prompt types) rather than a new config surface, per spec.md's own Assumptions (pre-approved as "planner's call," flagged here for visibility per this plan's explicit instructions). Mitigation: Phase 2 keeps this change additive and backward-compatible — every other task type's config entry is untouched, `TaskTimingConfig.Timing` gains nullable fields rather than replacing existing ones.
- MEDIUM (plan-reviewer finding, resolved): a naive design would have exam-delivery make two separate internal media calls per audio-prompt item at pin time (the existing URL-resolution call, plus a new duration-only call) — same `mediaPublicId`, same tenant, same call site, doubling network calls and failure surface for no benefit. Mitigation: Phase 1 extends the existing internal presigned-download response DTO with an optional duration field instead of adding a new endpoint; Phase 2 consumes duration from that same existing call.
- MEDIUM: `task-timing.json`'s existing static `prepSeconds` for the 5 audio-prompt types (added by `phat-speaking-audio-prompt-e2e` Phase 1) becomes dead/superseded once dynamic computation ships for those types — Mitigation: Phase 2 leaves the static values in place as an inert, unused fallback (documented as such in the config's own comment) rather than removing them, since `responseSeconds` in that same entry is still read normally (only `prepSeconds` for these 5 types stops being consulted).
- MEDIUM: widening the WAV-only restriction must not affect candidates' own recorded-answer uploads (already WAV-only via `AudioRecorderServiceImpl`, a separate content-type path per spec.md's own Assumptions) — Mitigation: Phase 1's regression test explicitly exercises that path unchanged.
- LOW (plan-reviewer NOTED, resolved): the missing-duration guard (Phase 2 Step 5) needs an explicitly-named exception rather than an ad-hoc mid-cook decision — mirroring the existing `MissingAudioPromptException` precedent (not `AudioResolutionFailedException` — that one's 503 is for a call failure, this is a data-completeness problem), Phase 2 names its own new exception `MissingAudioDurationException` at `HttpStatus.UNPROCESSABLE_ENTITY` (422).
- HIGH (2nd-pass plan-reviewer finding, resolved): Phase 1's Step 6 originally described "the existing internal presigned-download response DTO" as one shared type — it's actually **two separate record classes**, media-service's own `PresignedDownloadResponse` and exam-delivery's independently-maintained mirror `MediaClient`'s `MediaPresignedDownloadResponse` (explicitly documented in its own file as "not a shared class"). Extending only one would leave Phase 2's consuming code looking for a field that doesn't exist on its side. Mitigation: Phase 1 Step 6 now explicitly names both classes and requires both to gain the new field.
- MEDIUM (2nd-pass plan-reviewer finding, resolved): Phase 4's originally-described regression test ("reuse the existing fake-scheduler convention to assert exactly one active periodic chain") can't actually detect the bug it's meant to catch — the existing `_CapturingScheduler` test double only captures raw `(duration, callback)` pairs, not the `Timer` objects returned, so a test built on re-invoking captured closures bypasses real `Timer.cancel()` semantics entirely and would pass even if the cancellation fix were later silently removed. Mitigation: Phase 4 Step 7 now explicitly extends `_CapturingScheduler` to also capture and expose the returned `Timer` objects, so the regression test can assert real `.isActive == false` on the previously-active periodic timer.
- LOW: dev/test audio-prompt `MediaObject`s created before this ships (e.g. the prior plan's Repeat Sentence fixture) have no stored duration — per spec.md's own Assumptions, these are expected to be re-seeded fresh, not migrated; Phase 5 re-seeds (via the now-updated `seed-e2e.ps1`) rather than reusing old data.
- LOW: Phase 5's fixture must have a genuinely audible, non-trivial, precisely-known duration for the sync to be visually/aurally verifiable — resolved (user confirmed): Phase 5 generates a new, longer (~5-6s) fixture rather than reusing the existing 2.5s tone, which risked being too short to distinguish "in sync" from "coincidentally close."

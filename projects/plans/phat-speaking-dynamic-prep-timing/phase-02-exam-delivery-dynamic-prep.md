# Phase 2: exam-delivery — dynamic per-item prep timing

**P1 coverage: 3/3** — this phase is what makes the accurate-prep-timing story (P1 #1) actually true server-side; it also depends on and completes Phase 1's typed-error story reaching a live pinning flow safely (an item whose audio duration can't be resolved must not silently pin with a wrong window), and its unaffected-non-audio-prompt-types guarantee underlies the "recording starts promptly" story (P1 #3) not regressing other task types' behavior.

## Requirements
For a pinned item of one of the 5 audio-prompt Speaking task types, exam-delivery computes that item's prep window dynamically from its own real audio's duration (pre-listen + real audio length + pre-record) instead of a static per-type lookup — while every other task type keeps its existing static timing completely unchanged. The pre-listen/pre-record sub-stage lengths themselves move from client-hardcoded values to server-owned configuration, populated and exposed only for these 5 types (every other task type's config and client response simply omit them — never required/non-null there).

## Steps
1. Consume the already-existing internal audio-URL resolution call's response (extended in Phase 1 with the new duration field) for the item's real audio duration — do not add a second internal call; the existing `resolveAudioUrl` call site in `SnapshotPinService` becomes the single source for both the URL and the duration for these 5 task types.
2. Add server-side configuration for each of the 5 audio-prompt task types' pre-listen and pre-record sub-stage lengths, alongside their existing prep/response timing configuration — configured only for these 5 types; every other task type's configuration entry is untouched and simply has no such values.
3. Preserve Respond to a Situation's existing combined 20-second "Beginning" sub-stage exactly as today's value for its pre-listen configuration — only the portion after it becomes duration-driven.
4. At pinning time, for the 5 audio-prompt task types only, compute that item's prep duration as pre-listen + the item's own real audio duration (from Step 1) + pre-record, instead of reading the static per-type prep value — every other task type keeps using the existing static lookup unchanged.
5. If the resolved response from Step 1 reports no duration for one of the 5 audio-prompt task types (e.g. a legacy media object uploaded before duration was computed, or any other unresolved case), fail the pin attempt with a new, distinct exception — `MissingAudioDurationException`, using `HttpStatus.UNPROCESSABLE_ENTITY` (422), mirroring `MissingAudioPromptException`'s status exactly since this is the same category of problem (an authoring/data-completeness issue on the pinned item), not `AudioResolutionFailedException`'s 503 (that one is for a call failure, not missing data) — rather than defaulting to a guessed value or proceeding silently.
6. Expose the new pre-listen/pre-record sub-stage values to the client alongside the item's existing prep/response fields, populated only for the 5 audio-prompt task types — every other task type's client-facing task response simply omits them (nullable/absent), matching how the server-side config itself is scoped; do not make these fields required/non-null across all task types.
7. Add unit test coverage for all 5 audio-prompt task types' dynamic prep computation (including Respond to a Situation's preserved 20s pre-listen value), a regression test confirming a non-audio-prompt task type (e.g. Read Aloud) computes its prep exactly as before and never populates the new fields, and a case confirming the new missing-duration exception fires when the resolved response carries no duration for one of the 5 types.

## Success Criteria
- For each of the 5 audio-prompt task types, a pinned item's prep duration equals pre-listen + its real audio duration + pre-record, verified by unit test.
- Respond to a Situation's pre-listen value is unchanged at its existing combined value, verified by unit test.
- Read Aloud (and every other non-audio-prompt task type) pins with exactly its existing static prep/response values and no pre-listen/pre-record values in its response — no regression (spec.md Success Criteria #5).
- The client-facing task response includes the new pre-listen/pre-record values for the 5 audio-prompt task types only, and only one internal media call is made per audio-prompt item at pin time (URL + duration together), verified by unit test.
- A pin attempt for one of the 5 audio-prompt task types whose resolved media response carries no duration fails with the new, explicitly-named exception, verified by unit test.
- All new and existing exam-delivery unit tests pass.

## Risks
- Exact server-config location for the new pre-listen/pre-record values (extending the existing per-task-type timing config vs. a new config surface) is an implementation detail this phase resolves by extending the existing config — flagged for visibility since it's a new decision made during planning, not a re-litigated one.
- The existing static prep value for these 5 task types becomes dead/unused once this ships — left in place as an inert fallback rather than removed, to avoid an unrelated config-shape change in the same phase.
- Downstream prep-deadline computation already derives from the per-item prep value at task-start time — confirmed by source read to require no separate change, but worth an explicit end-to-end check in this phase's tests that a dynamic item's deadline reflects the dynamic value, not just that the value itself is computed correctly.
- `preListenSeconds`/`preRecordSeconds` must not be modeled as required/non-nullable on the client while the server only ever populates them for these 5 of ~20 task types (plan-reviewer HIGH finding) — resolved here by keeping them nullable/absent for every other task type on both the config and the client-response side; Phase 3 reads them as nullable and asserts non-null only at the 5 Speaking screens' own read sites.
- The missing-duration guard's exception must be explicitly named (not left as an ad-hoc mid-cook decision, per plan-reviewer NOTED finding) — this phase names it `MissingAudioDurationException` at `HttpStatus.UNPROCESSABLE_ENTITY` (422), mirroring `MissingAudioPromptException`'s naming and status exactly (a data-completeness problem, not a call failure like `AudioResolutionFailedException`'s 503).

## Research Summary
Two prior `/ck:plan` researchers resolved the plan's open questions (see spec.md "Resolved" section):
- **Seed mechanism:** the existing in-process pattern (`services/authoring/.../seed/ReadingTaskSeedRunner.java`, a `@Profile`-gated Spring `CommandLineRunner`) was rejected for this use case — it is structurally scoped to one service's own repositories and JVM, and this flow spans 4 separately-deployed services (admin, iam, authoring, scheduling). Instead, `pte-api/scripts/seed-e2e.ps1` is a standalone external script that calls only the gateway's public REST API (`http://localhost:8080/api/...`) in sequence, using `Invoke-RestMethod` (native JSON parsing, matches the developer's shell, no new runtime dependency in a Java-only backend repo).
- **Idempotency (revised after plan-reviewer findings):** get-or-create per HTTP call is necessary but not sufficient — two of the eleven steps have no API-level way to recover an existing resource's `publicId` after a process restart: `SnapshotPublishService.publish()` has no server-side idempotency guard and no "get snapshot by blueprint" lookup endpoint (every call mints a new version), and the bootstrap admin's `GET /users` call returns empty for a platform-scoped caller (`UserService.listByTenant`), so an existing host/student's `publicId` can't be self-discovered after a 409. The script therefore uses a **local state file** (`pte-api/scripts/seed-e2e.state.json`, git-ignored) as its primary idempotency source of truth, recording every resource's `publicId` the moment it's created, keyed by fixed sentinel identifiers (tenant name, host/student email, question title). Known, accepted limitation: if the state file and the actual DB ever drift out of sync (e.g. `docker compose down -v` without deleting the state file), the fix is deleting both together — not a runtime reconciliation feature (see Phase 2 Risks).
- **`gatewayBaseUrl`:** confirmed via source read (`lib/core/config/app_config.dart:10`) to be a plain hardcoded `static const String`, currently pointing at the raw `iam` service port (`8081`, bypasses the gateway and its `/api/{service}/**` routing entirely) instead of the actual gateway (`8080`, confirmed against `pte-api`'s `docker-compose.services.yml`).
- **Bootstrap constraint (confirmed against current entity source during this planning pass):** `pte-api` has no self-registration endpoint. The first account must be inserted directly via SQL: `users` (`email` unique, `full_name`, `tenant_id` nullable, `status` enum `ACTIVE`/`SUSPENDED`, `deleted` boolean, `id`/`public_id`/`created_at`/`updated_at` all required — `public_id` and the timestamps are Hibernate-managed, not DB defaults, so the manual insert must supply them explicitly). **Critical FK detail (plan-reviewer HIGH finding):** `user_roles.user_id` and `login_hashes.user_id` both FK to `users.id` — the internal auto-generated bigint — **never `public_id`**, even though `public_id` is this codebase's convention for cross-references everywhere else. The bootstrap SQL must use `INSERT INTO users (...) RETURNING id` and thread that captured value into both dependent inserts.
- **Ordering constraint:** a scheduling session's `opensAt` must be strictly future (`@Future`), and the session must be explicitly `open`ed with the student explicitly enrolled and composition set — skipping or misordering any of these three steps throws `PinnedSnapshotEmptyException` or `NotEntitledException` at attempt-start time regardless of the timing window. **Corollary (plan-reviewer MEDIUM finding):** `opensAt`/`closesAt` must be computed relative to the script's current execution time on every run, never a fixed literal timestamp — unlike the other natural-key sentinels, a hardcoded past-by-now value permanently breaks session creation with no get-or-create path to notice or recover.

## Dependencies
- Docker Desktop / `docker compose` available and working locally (brings up `pte-api`'s full stack behind the gateway at `localhost:8080` via `docker compose -f docker-compose.yml -f docker-compose.services.yml up --build`).
- A `psql` client (or equivalent) able to reach `localhost:5432` for the one manual bootstrap insert and later DB verification queries.
- A BCrypt hash generator available locally for the bootstrap password (e.g. `htpasswd` from Git Bash's Apache tools, per spec.md Assumptions).
- `pte-app` buildable and runnable against a local backend (desktop or emulator target — Phase 3 must confirm which, since emulator targets need `10.0.2.2` instead of `localhost`).

## Risks
- HIGH: the manual SQL bootstrap insert (BCrypt hash generation, exact column values for `public_id`/timestamps that Hibernate normally auto-supplies) is wrong or incomplete, silently blocking every downstream API call — Mitigation: exact column list and constraints already verified against current entity source (`User.java`, `LoginHash.java`, `BaseEntity.java`) in this planning pass; Phase 2 documents the precise statements and Phase 3 verifies the bootstrap admin can actually log in before proceeding.
- MEDIUM: the session's `opensAt` future-timestamp window can go stale if the manual walkthrough (Phase 3) happens well after seeding — Mitigation: the seed script is idempotent, so re-running it immediately before testing refreshes nothing that's wrong, but Phase 3 should seed with a comfortably long `opensAt`→`closesAt` window and seed shortly before testing.
- LOW: `pte-app`'s target platform (desktop vs. Android emulator) changes what "localhost:8080" resolves to — Mitigation: Phase 3 explicitly confirms the run target before pointing the app at the gateway.
- NOTED (plan-reviewer): spec.md's Security NFR ("profile-gated exactly like `ReadingTaskSeedRunner`") doesn't translate to an external-script design — a Spring `@Profile` gate has no analog outside the JVM. The chosen equivalent safeguard is hardcoding the script's target to `http://localhost:8080` and having it abort if that's ever changed to anything not containing `localhost`/`127.0.0.1` (Phase 2 Risks), rather than a runtime confirmation prompt or config flag. Accepted as sufficient for this plan's scope; spec.md's NFR wording is superseded by this note rather than being literally satisfiable.

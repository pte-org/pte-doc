# Phase 3: Manual Full-Stack Walkthrough (human-executed)

## Requirements
A developer-executed pass confirms the entire real chain works: `pte-api` running live, seeded via the script from Phase 2, and `pte-app` (with the Phase 1 fix) completing a real login, session resolution, Read Aloud task fetch, recording, and answer submission that lands in the database — not a code-review-level claim, an observed one.

**This phase cannot be delegated to an automated tester agent.** It requires a running Docker stack, a real device/emulator or desktop app instance, an actual audio recording, and direct DB inspection — the same category of manual-only phase as the prior `phat-windows-audio-playback-fix` plan's Phase 3.

## Steps
1. Bring up the full `docker compose` stack from `pte-api` (`docker compose -f docker-compose.yml -f docker-compose.services.yml up --build`) and confirm every service reports healthy before proceeding.
2. Perform the one-time `PLATFORM_ADMIN` bootstrap SQL insert documented at the top of `seed-e2e.ps1` against the `iam` database — skip this step if it has already been done against this stack's current data volume.
3. Idempotency verification, two rounds:
   a. Run `seed-e2e.ps1` once against the running stack, then immediately run it a second time — no errors and no new/duplicate rows on the second run (full-success idempotency).
   b. Reset to a clean stack, run `seed-e2e.ps1` again but interrupt it partway through (e.g. Ctrl+C right after the student user is created but before the question/blueprint/snapshot steps), then run it a third time to confirm it correctly resumes from the state file rather than erroring or duplicating the already-created tenant/host/student (partial-failure idempotency — this is the scenario spec.md actually motivates the script for: resuming after a failure hit mid-debugging, not just re-running after a clean success).
4. Rebuild or hot-restart `pte-app` (Windows desktop target — confirmed with the developer, `localhost:8080` resolves directly, no `10.0.2.2` adjustment needed) with the corrected gateway URL, and log in through the real `LoginPage` using the seeded student's credentials.
5. Resolve the seeded session, open the Read Aloud task, and confirm the on-screen prompt text matches the seeded question's actual `promptText` (not fixture/placeholder text).
6. Record an answer and let the app's existing auto-upload/submit flow run to completion, confirming the UI reflects a successful submission.
7. Query the relevant service databases directly (media, exam-delivery) to confirm a `MediaObject` row with status `UPLOADED` exists for the recording and a corresponding `attempt_answers` row references it, then record pass/fail against each item below.

## Risks
- HIGH: the `docker compose` stack fails to start cleanly (port conflicts, missing/stale images) — Mitigation: check `docker compose ps` and service logs before proceeding; retry with `--build`; confirm no other local process is already bound to the gateway or DB ports.
- **HIT during this walkthrough (2026-08-29), fixed:** `exam-delivery` exited (code 1) on first `up --build` — `EncryptionKeyProvider` refuses to start without a configured RSA keypair unless `spring.profiles.active` is `dev`/`local` (fail-fast by design, not a bug: an ephemeral keypair in a real deployment would invalidate every STRICT-pinned attempt's public key on restart). `docker-compose.services.yml` never set `SPRING_PROFILES_ACTIVE` for `exam-delivery` — nobody had exercised the full-stack compose flow through an actual attempt-start before this plan. Fixed by adding `SPRING_PROFILES_ACTIVE: dev` to `exam-delivery`'s environment block (confirmed via source read: no other `@Profile`-gated bean exists in exam-delivery, so this has no other side effect). Rebuilt with `docker compose -f docker-compose.yml -f docker-compose.services.yml up --build -d exam-delivery`; now starts healthy in ~8s. This is exactly the class of real gap this plan exists to surface — out of the original 3 phases' scope, but a necessary fix to proceed with Phase 3 at all.
- MEDIUM: the seeded session's `opensAt` window is in the past by the time this phase actually runs, causing entitlement checks to fail for reasons unrelated to the app — Mitigation: seed shortly before testing and use a comfortably long `opensAt`→`closesAt` window; re-run the idempotent script if needed.
- LOW: run target is confirmed as Windows desktop (not an emulator), so `localhost:8080` resolves directly — no host-adjustment risk this round.
- LOW: the local object-storage container (S3-compatible, required for the media upload flow) isn't included or healthy in the compose profile used — Mitigation: confirm it's present and healthy in `docker-compose.services.yml` during step 1's health check.
- **HIT during this walkthrough (2026-08-29), fixed:** `pte-app`'s real login → `POST /api/exam-delivery/attempts` failed with HTTP 500 (`Something went wrong. (Unexpected response (500))`). Root cause (confirmed via `exam-delivery` logs): the server's `StartAttemptRequest` DTO has a required primitive `boolean deviceCheckConfirmed` field ("client self-attestation... absent/false always means not confirmed" — only actually enforced when a session's policy sets `isDeviceCheckRequired()`, otherwise it's audit-only) that `ExamAttemptRepositoryImpl.startOrResumeAttempt` never sent at all — Jackson fails deserialization outright (missing value for a non-nullable primitive) before any business logic runs, a genuine FE/BE contract drift, not a config/infra issue. Fixed by always sending `deviceCheckConfirmed: false` (honest given the standalone "Test Mic and Sound" dev-preview screen — `features/device_check` — is explicitly not wired into this real pre-exam flow yet, a separate prior product decision, see `plans/phat-device-check-test-mic-and-sound-ui`). `flutter analyze` clean, full suite 500/500 pass (no existing test asserted the exact request body, so none needed updating). Wiring a real device-check gate into this flow is a distinct, larger follow-up, not done here.
- **HIT immediately after the above fix, also resolved:** next attempt-start failed with HTTP 409 (`ConflictException` → "That action conflicts with the current state"). Root cause: `GlobalExceptionHandler.handleDomain()` deliberately does not log expected `DomainException`s (only `handleUnexpected()`'s true-error fallback logs), so this genuinely reached the server with no visible log entry — not a request that silently failed to arrive. The seeded session was created via the original `seed-e2e.ps1` without specifying `examMode`, defaulting to `MOCK_TEST` (`CreateSessionRequest`'s own doc comment), whose `ExamPolicy.mockTestDefault()` sets `deviceCheckRequired=true` — combined with the honest `deviceCheckConfirmed: false` above, this correctly threw `DeviceCheckRequiredException` (409). Not a bug — the system behaving exactly as designed; this plan's scope is verifying the Read Aloud task path, not exercising the device-check-required gate. `PATCH .../policy` on the already-`open`ed session was rejected (`POLICY_LOCKED`, by design — policy locks once past pre-open). Fixed by adding `examMode = 'PRACTICE'` (→ `deviceCheckRequired=false`) to `seed-e2e.ps1`'s session-creation call, and creating a fresh session under a distinct name (`E2E Seed Session - Read Aloud (Practice)`, publicId `7fc2c9bd-ea10-4903-b3cd-c1ba3b6b019b`) rather than trying to mutate the locked one. Confirmed via `GET /sessions/{id}`: `deviceCheckRequired: false`.
- **HIT after that, fixed — the most significant finding of this plan:** the Read Aloud screen rendered correctly (prompt text matched, confirming login/session/task-fetch all genuinely work), but the UI froze permanently at "Preparation 00:00" / "Beginning in 0 seconds", never reaching the recording phase. Root cause (confirmed via a direct `GET /attempts/{id}/timer` call against the real attempt): `TimerState.phase` (`exam-delivery`) is write-once — set exactly once in `TimerService.startTaskTimer()` and never revisited by anything afterward, including the timer-poll endpoint (`AttemptMapper.toTimerResponse` returned `timer.getPhase().name()` directly, unchanged). Since `pte-app`'s `TimerService` deliberately trusts the server's reported phase exclusively and never advances it locally (existing, documented design constraint — avoids client/server drift), **any task with `prepSeconds > 0` (i.e. most Speaking tasks) gets permanently stuck in `PREP` forever once the prep deadline passes**, with no path to ever reach `RESPONSE` — a systemic bug affecting every such task in production, not specific to this test. Confirmed via `grep`: only 2 call sites read `TimerState.getPhase()` anywhere in `exam-delivery` (a unit test asserting write-once creation behavior, and this one mapper), so the fix has a small, well-understood blast radius. Fixed in `AttemptMapper.toTimerResponse`: recompute phase dynamically (`PREP` stored + `now >= prepDeadline` → report `RESPONSE`; otherwise pass the stored phase through unchanged, so section-scoped `RESPONSE`-from-creation tasks are never affected). Added 3 regression tests to `AttemptMapperTest` (prep-deadline-passed → RESPONSE; prep-deadline-not-yet-reached → still PREP; already-RESPONSE phase never flips back regardless of deadline) — full `exam-delivery` suite 44/44 pass after the fix.
- **HIT once the Read Aloud screen actually rendered (prompt text confirmed correct — login/session/task-fetch all working), fixed:** recording the answer failed with `RawUploadException: Failed host lookup: 'minio'`. Root cause: `media`'s `PresignService` signed upload URLs using `MinioClient`'s configured `endpoint` (`media.storage.endpoint` = `http://minio:9000`, the docker-compose-internal hostname needed for `media`'s own server-to-server MinIO calls) — but a presigned URL is handed to an *external* caller (`pte-app` on the Windows host), which cannot resolve `minio` at all. Fixed with a second, distinct `MinioClient` bean (`presignMinioClient`, `MinioConfig.java`) built from a new `media.storage.public-endpoint` config property (env `MINIO_PUBLIC_ENDPOINT`, set to `http://localhost:9000` in `docker-compose.services.yml` — minio's container port 9000 is host-mapped to the same port, confirmed via `docker-compose.yml`), used only by `PresignService`'s two presign methods; the original client stays on the internal endpoint for bucket bootstrap. Hit a second-order issue immediately after: `PRESIGN_FAILED` (also a silent `DomainException`) — the MinIO Java SDK resolves a bucket's region via a real `GetBucketLocation` network call on first use per client when no region is explicitly configured, which the new public-endpoint client cannot make from inside the container (same unreachable-`localhost` problem, mirrored). Fixed by pinning `.region("us-east-1")` (MinIO's own placeholder-region convention) on both `MinioClient` builders, eliminating the auto-detection call entirely. Verified end-to-end: `POST /api/media/objects` now returns `uploadUrl` starting `http://localhost:9000/...`, and a real `PUT` against it returns `200`.
- **Code-review finding (MEDIUM), fixed:** `.region("us-east-1")` had been pinned on *both* `MinioClient` beans, but the admin-scoped `minioClient` bean (bucket bootstrap) never needed it — it has real connectivity and region auto-detection works fine there; only `presignMinioClient` needed the pin (to avoid the unreachable auto-detect call). Also, the value was a source-level literal rather than externalized like every other MinIO setting. Fixed: removed the pin from `minioClient`; added `media.storage.region` (env `MINIO_REGION`, default `us-east-1`) and wired it only into `presignMinioClient`. Rebuilt, re-verified: presigned URLs still correctly signed for `us-east-1`, `media` still starts healthy (bucket bootstrap unaffected).
- **Investigated after the fixes above, initially thought to be a testing-only timing issue, but turned out to be a real production bug — the most significant finding of this plan:** the full pipeline (record → presign → upload → complete → local outbox write) worked correctly end-to-end — confirmed by reading the local SQLite outbox table directly (`answer_outbox_table` in `pte_app.sqlite`) — the row had the *correct* `payload` (the real, `UPLOADED` `MediaObject`'s publicId) and status `terminalRejected` with `last_sync_error: RESPONSE_WINDOW_EXPIRED`. First hypothesis (WRONG, corrected after retesting): assumed 40s was simply too tight for *manual* testing and worked around it with `timingOverrideSeconds: 180` — but the same rejection recurred even at 180s, with the real upload again completing successfully (confirmed via `media_objects`) just milliseconds before the recorded rejection. Root cause (confirmed via `TimerState.isResponseWindowExpired`): the server check was `now.isAfter(responseDeadline)` with **zero grace**, while the client (`AutoRecordCubit`) — correctly, by design — stops recording exactly *at* the deadline it was told, meaning the subsequent presign→upload→complete→submit round-trip *always* lands after that exact instant. With zero grace, **no audio-recording-based answer could ever successfully submit, for any candidate, at any response-window length** — not specific to this test environment. Fixed with a 15-second grace window added to `TimerState.isResponseWindowExpired` (both call sites in `AttemptService` — answer submission and auto-advance-on-poll — share this one method, so neither prematurely advances past a task nor rejects an answer still mid-flight). Applied uniformly to every task type for consistency, not just audio-recording ones. 5 new unit tests added (`TimerStateTest`) covering the exact-boundary, within-grace, and past-grace cases; full `exam-delivery` suite 49/49 pass. Measured real round-trip latency on localhost (upload+complete+submit) was well under 1 second — 15s is ample margin, not a loophole. `seed-e2e.ps1`'s `timingOverrideSeconds` reverted to `$null` (real production default, 40s) once this fix was in place, to verify against realistic timing rather than an inflated test-only window.

## Testing
This entire phase is the test — there is no automated substitute. Neither `pte-api`'s JUnit suite nor `pte-app`'s Dart test suite exercises a live multi-service backend plus real device audio recording plus real object storage; the checklist above, executed and observed by a human, is the only verification this feature has.

# Phase 2: `pte-api` Seed Script (`scripts/seed-e2e.ps1`)

## Requirements
A single, re-runnable PowerShell script that, given a running `pte-api` stack and a bootstrapped `PLATFORM_ADMIN` account, creates (or confirms the prior existence of) one tenant, one host admin, one student, one published `READ_ALOUD` question/blueprint/snapshot, and one opened scheduling session with the student enrolled — entirely through the gateway's public REST API, safe to run any number of times without duplicating data or erroring.

## Steps
1. Document the one-time manual `PLATFORM_ADMIN` bootstrap this script depends on, as a comment block at the top of the script, with the exact SQL — critically, using `INSERT INTO users (...) VALUES (...) RETURNING id` and referencing **that captured `id` value** (the internal auto-generated bigint, `GenerationType.IDENTITY`) — **not** `public_id` — as the `user_id` FK in both the `user_roles` and `login_hashes` inserts (confirmed via `LoginHash.java`/`User.java`: both FK to `users.id`, never `public_id`, even though `public_id` is the convention used everywhere else in the codebase for cross-references — this is the one deliberate exception). Include the exact command to generate the required BCrypt password hash.
2. **Local state file for idempotency** (`pte-api/scripts/seed-e2e.state.json`, git-ignored): the script reads this file first on every run. It records every resource's `publicId` this script has itself created (tenant, host, student, question, blueprint, published snapshot, session), keyed by the fixed sentinel identifier used to create it (tenant name, host/student email, question title, etc.). This is the *primary* idempotency mechanism — not solely 409-catching — because two of the eleven steps have no way to recover an existing resource's `publicId` from the API alone if the process restarts without this file:
   - `SnapshotPublishService.publish()` has **no idempotency guard on the server** — every call creates a new `ExamSnapshot` version, and there is no "get snapshot by source blueprint" lookup endpoint. Pre-check `GET /blueprints/{publicId}` for `status == PUBLISHED` before ever calling publish; if already published, the snapshot's `publicId` MUST come from the state file (there is no other way to retrieve it after the fact).
   - Platform-admin-scoped `GET /users` (`UserService.listByTenant`) returns `List.of()` for a `tenantId() == null` caller, so the bootstrap admin cannot self-discover an existing host/student's `publicId` by listing. On a 409 from user-create, the script must already have that user's `publicId` in the state file — if it doesn't (e.g. the state file was deleted but the DB wasn't reset), this is a genuinely unrecoverable state for this script's design; fail loudly with a message telling the developer to delete both the state file and the stack's DB volume together, rather than silently guessing.
   Document this limitation explicitly in the script's top comment block, not just in this plan.
3. Choose fixed, stable identifiers (tenant name, host email, student email, question title, etc.) that the script reuses on every run as the state file's lookup keys — **except** `opensAt`/`closesAt` (see step 6).
4. Implement a login step for the bootstrap admin and reuse of the resulting bearer token for every subsequent authenticated call.
5. Implement get-or-create logic for the tenant, the host admin user, and the student user: check the state file first; if absent, attempt create; on success, record the returned `publicId` to the state file; on a 409, treat as the unrecoverable case documented in step 2 unless the state file already had it.
6. Implement get-or-create logic for the host's own login, the `READ_ALOUD` question, the blueprint, and its published snapshot — per step 2's snapshot-specific handling. When creating the scheduling session (this step or the next), compute `opensAt`/`closesAt` **relative to the script's current execution time** (e.g. `opensAt = now + 5 minutes`, `closesAt = opensAt + 2 hours`) on every run, including re-runs — never a fixed literal timestamp, since `@Future` validation means a hardcoded past-by-now value permanently breaks the very first `create()` call with no way for get-or-create logic to notice or recover (it isn't reached yet).
7. Implement get-or-create logic for the scheduling session itself, and — in the correct order — setting its composition, opening it, and enrolling the seeded student.
8. Add a clear progress message before/after each step describing which resource is being created or found (from state file vs. freshly created), and make any unexpected failure stop the script immediately with the exact HTTP status code and response body rather than continuing silently.

## Success Criteria
- `pte-api/scripts/seed-e2e.ps1` exists and parses as valid PowerShell with zero syntax errors (verified by the script parser, not by executing it against a live stack — that happens in Phase 3).
- The bootstrap SQL comment block correctly threads `users.id` (via `RETURNING id`), not `public_id`, into `user_roles`/`login_hashes`.
- Every step in the sequence has a corresponding, distinct console message identifying what it created or found, and whether it was resolved from the state file.
- `opensAt`/`closesAt` are visibly computed from current time in the script, not hardcoded literals.
- A deliberately-triggered failure (e.g. an unreachable gateway) surfaces the real HTTP error detail instead of a generic or swallowed exception.

## Risks
- Request/response field names drift from what's assumed (e.g. tenant creation fields, session composition item shape) — Mitigation: every call in this script is written against the actual controller/DTO source read during this planning pass, not assumption; verified for real in Phase 3.
- A resource's "already exists" signal isn't actually a 409 for every endpoint — Mitigation: prefer a pre-check GET by natural key over relying solely on catching a 409 where a list/lookup endpoint is available; where neither exists (snapshot, user), rely on the state file per step 2.
- The state file and the actual DB can drift out of sync (state file present but DB was reset via `docker compose down -v`, or vice versa) — Mitigation: documented explicitly as a known limitation in the script's own header comment; the fix is deleting both together, not a runtime reconciliation feature (out of scope for this plan's effort level).
- Steps run out of order (e.g. enrolling before opening the session) silently produce a session that looks seeded but rejects attempts later — Mitigation: hard-code the step order documented in this plan's Research Summary (composition → open → enroll) rather than inferring it.
- The script could accidentally be pointed at a non-local gateway if the base URL is ever made configurable later — Mitigation: hardcode the target to `http://localhost:8080` and add a guard that aborts if the configured URL doesn't contain `localhost`/`127.0.0.1`, since this design has no Spring `@Profile` gate to fall back on (see plan.md Risks).

## Testing
No automated test suite in either repo can exercise a standalone PowerShell script — `pte-api`'s JUnit suite doesn't run it, and `pte-app` has no visibility into it. Its real verification happens in Phase 3: once clean, once immediately re-run against the already-seeded stack (full-success idempotency), and once more killed deliberately partway through a clean run and re-run to confirm resumability (partial-failure idempotency) — since spec.md's actual motivation for this script is surviving repeated re-runs *during debugging*, which most often means resuming after a partial failure, not just re-running after a clean success.

## Actual Results (2026-08-29)
- `pte-api/scripts/seed-e2e.ps1` written — parses cleanly (`[System.Management.Automation.Language.Parser]::ParseFile`, 0 errors).
- **Implementation exceeds the plan's minimum design**: while writing it, found two real GET/list endpoints the plan-reviewer's own investigation had missed, which make idempotency fully API-recoverable (not state-file-dependent) for every resource except the snapshot:
  - `GET /api/iam/users/by-tenant/{tenantId}` (`UserController.java:75-79`, `PLATFORM_ADMIN`-only, doc comment: "so a platform admin can look up an arbitrary tenant's users without overloading [the caller-tenant-scoped `GET /users`] endpoint's existing semantics") — directly resolves the plan-reviewer's HIGH finding about host/student `publicId` being unrecoverable after a 409/restart.
  - `GET /api/admin/tenants`, `GET /api/authoring/questions`, `GET /api/authoring/blueprints`, `GET /api/scheduling/sessions`, `GET /api/scheduling/sessions/{id}/enrollments` all exist and are used as real pre-check lookups (find-by-natural-key) instead of relying on 409-catching.
  - The **only** resource still solely dependent on the state file is the published snapshot, exactly as the plan-reviewer identified — no lookup-by-blueprint endpoint exists anywhere in authoring, confirmed again while implementing.
- Also confirmed while implementing: `SessionResponse` already carries `status` and `composition` fields directly in its GET/list response, so composition/open idempotency needed no extra lookups; `CompositionService.setComposition()` clears-then-reapplies server-side (safe to re-call); `ExamSession.open()` is a trivial idempotent status setter (safe to re-call).
- Discovered `CreateQuestionRequest.visibility` must be `PRIVATE`, not `SHARED` — `SHARED` (platform-owned bank) is `PLATFORM_AUTHOR`-only to write, and this script only ever authenticates as `HOST_ADMIN` for authoring calls.
- Discovered the actual tenant DTO is `OnboardTenantRequest` at `POST /tenants` (not a differently-named "CreateTenantRequest" as loosely referenced during planning) — same field shape as assumed (`name`, `organizationType`, `packageName`, `studentLimit`), no functional difference.
- Verified (no live backend running yet, so this doubled as the deliberate-failure test from Success Criteria): running the script against an unreachable gateway fails loudly with `no HTTP response (Unable to connect to the remote server)`, not a swallowed/generic exception; running it against a non-localhost URL aborts immediately via the safety guard before any network call.
- `pte-api/.gitignore` updated with `scripts/seed-e2e.state.json`.
- Not yet verified: actual execution against a live stack (real create/get-or-create behavior, real idempotency across re-runs, real partial-failure resume) — that is Phase 3's job specifically, per this phase's own Testing section above.

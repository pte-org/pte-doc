# Plan: Test Mic and Sound (Device Check) Screen
Status: ✅ Complete

## Overview
Add a new, standalone "Test Mic and Sound" screen where a candidate can record and play back their own voice to check the microphone, and separately play a bundled sample clip to check speaker/headphone output — reachable only via a `kDebugMode`-gated dev-preview entry point, with no wiring into any real pre-exam flow (none exists yet).

## Phases
- [x] Phase 1: Device-check audio player + strings — new feature-scoped `just_audio` seam that supports both local-file and asset playback, plus the `DeviceCheckStrings` constants class.
- [x] Phase 2: Cubit, state, and screen UI — manual, non-timer-driven mic-test and sound-test sub-flows wired into a new `Scaffold` screen.
- [x] Phase 3: Dev-preview wiring + tests + full regression gate — reachable from the existing dev-standalone menu/routes, full cubit + widget test coverage, `flutter analyze` / `check-standards.sh` / `flutter test` all clean.

## Research Summary
Verified directly against the codebase before writing this plan:

- **`AudioPlayerService`/`AudioPlayerServiceImpl`** (`lib/features/exam_attempt/listening/{domain,data}/audio_player_service*.dart`) calls `_player.setAsset(source)` unconditionally — confirmed by reading the impl. This is documented as deliberate ("the asset-vs-remote distinction stays inside this file, never leaks to callers") and is registered in `exam_attempt_module.dart` via `registerFactory<AudioPlayerService>` (fresh instance per screen). It cannot play a candidate's locally-recorded file. Per the feature spec, this plan does **not** touch it — a new `DeviceCheckAudioPlayer` seam is built instead, backed directly by `just_audio`, mirroring the same lifecycle pattern (`playerStateStream` → completion signal → broadcast `StreamController<bool>` → `close()` disposes subscription + player) but exposing two entry points (`playFile` via `setFilePath()`, `playAsset` via `setAsset()`).
- **`AudioRecorderService`/`AudioRecorderServiceImpl`** (`lib/features/exam_attempt/speaking_writing/domain/audio_recorder_service.dart`) is already generic (`start(filePath)`, `stop()`, `isRecording()`) and registered as `registerLazySingleton<AudioRecorderService>` in `exam_attempt_module.dart`. Reused as-is, no changes.
- **Path-resolution precedent**: `read_aloud_cubit.dart`'s top-level `resolveRecordingFilePath(attemptPublicId, pinnedItemPublicId)` joins `getTemporaryDirectory()` with a deterministic filename via `package:path`. The new feature follows the same shape but with no attempt/item context — a fixed filename (e.g. `device_check_test.wav`), overwritten on every re-record.
- **Bundled sound-test asset**: `assets/audio/` contains 8 existing `listening_sample_*.wav` files (`listening_sample_dictation.wav`, `listening_sample_fill_blanks.wav`, `listening_sample_highlight_correct_summary.wav`, `listening_sample_highlight_incorrect_words.wav`, `listening_sample_mc_multiple.wav`, `listening_sample_mc_single.wav`, `listening_sample_select_missing_word.wav`, `listening_sample_summarize.wav`). `pubspec.yaml` already declares `assets: - assets/audio/` as a blanket folder include, so no pubspec change is needed. Plan selects `assets/audio/listening_sample_dictation.wav` (Phase 1 must confirm at implementation time — via `flutter_soundpool`/`just_audio` metadata or simply listening to it — that it is a short, clearly-speech clip, not a mid-sentence fragment; swap to another file in the list if it isn't).
- **Dev-entry-point pattern — corrected from the feature brief**: there is no literal `FloatingActionButton` for Reading/Listening/Speaking-Writing previews. The actual pattern (read in `lib/app.dart`) is: (1) a `kDebugMode`-gated `routes` map entry on `MaterialApp` (e.g. `'/dev/listening-preview': (_) => _buildListeningTaskPreviewScreen()`), plus (2) when the app is launched with `DEV_SKIP_AUTH=true`, a `_DevStandaloneMenu` `Scaffold`/`ListView` of `ListTile`s (icon + title + subtitle) navigating to `/dev/standalone/{name}` routes, built via `static Widget _buildXScreen()` helpers that resolve dependencies from `GetIt.instance`. This plan follows that real pattern instead of inventing a FAB: a new `'/dev/device-check'` route + a new `_DevStandaloneMenu` `ListTile` + `/dev/standalone/device-check` route + a `_buildTestMicAndSoundScreen()` helper, all in `lib/app.dart` (not `lib/main.dart`, which only wires up DI module setup and `runApp`).
- **DI decision**: `AudioRecorderService` needs no new registration (already a `registerLazySingleton`, resolved via `GetIt.instance<AudioRecorderService>()` in the new builder helper, same as every existing preview builder). `DeviceCheckAudioPlayer` is constructed directly by the screen in `initState` (not GetIt-registered) — this is a single-screen, dev-only feature with no second call site and no test-time need to swap implementations app-wide (widget tests inject a mock directly via constructor, same as how screens in this app already take service instances as constructor parameters).
- **Strings convention**: `SpeakingWritingStrings` (`lib/features/exam_attempt/speaking_writing/constants/speaking_writing_strings.dart`) uses a private `const ClassName._()` constructor with `static const String` fields grouped by section, comment-headed. `DeviceCheckStrings` follows the same shape.
- **UI precedent**: `PersonalIntroductionScreen` (`lib/features/exam_attempt/speaking_writing/presentation/pages/personal_introduction_screen.dart`) shows the app's established visual language — `StatefulWidget` owning cubit lifecycle explicitly in `initState`/`dispose`, `AppDimensions.spacingMedium` padding/gaps, `TextStyle(color: AppColors.textPrimary)` for body text — but it renders inside `ExamScaffold`, which does not apply here (no exam chrome, no timer). The closest precedent for a plain top-level screen is `SpeakingWritingTaskPreviewScreen`'s own bare `Scaffold` usage as dev tooling.
- **Test-file convention (corrected from the feature brief's suggested paths)**: this repo's actual convention is `test/unit/features/{module}/{name}_cubit_test.dart` (flat, no mirrored `presentation/cubit/` subpath — confirmed via `auto_record_cubit_test.dart`) and `test/widget/features/{module}/{name}_screen_test.dart` (flat, confirmed via `personal_introduction_screen_test.dart`), using `bloc_test` + `mocktail`. This plan creates `test/unit/features/device_check/device_check_cubit_test.dart` and `test/widget/features/device_check/test_mic_and_sound_screen_test.dart`, not the deeper paths suggested in the original brief.

## Dependencies
None — no backend/API dependency, no new package (uses `just_audio`, `path_provider`, `package:path`, all already dependencies via existing exam_attempt code), no new asset (`assets/audio/listening_sample_dictation.wav` reused).

## Risks
- MEDIUM: Reusing a real Listening-task sample clip (`listening_sample_dictation.wav`) as the "sound test" asset is a placeholder, not a purpose-built test tone — flagged for user awareness; a bespoke short "can you hear this" clip would be a nicer long-term choice but isn't required to ship this feature. Mitigation: keep the asset path in one named constant so swapping it later is a one-line change.
- LOW: `just_audio`'s `setFilePath()` behavior on a freshly-overwritten file (same path reused across re-records) could hit a stale-cache edge case on some platforms. Mitigation: dispose/recreate the underlying `AudioPlayer`'s source cleanly on each `playFile` call (call `setFilePath` fresh each time, never rely on a cached duration/state) and verify manually on at least one physical/emulated device during Phase 2.
- LOW: Microphone/speaker permissions (OS-level mic permission prompt) are outside this plan's control — `AudioRecorderServiceImpl` already owns that handling from the Speaking feature; no new permission code needed, but Phase 3's manual verification step should confirm the permission prompt still appears correctly the first time this new entry point triggers `recorder.start()`.
- LOW: This is a `kDebugMode`-gated dev-only entry point with no real pre-exam flow to attach to yet — mitigation is explicitly out of scope per the confirmed design; a future plan will wire this screen (or a variant) into a real onboarding/pre-exam-setup feature once one exists. (User was explicitly asked whether to wire into the real, newly-discovered `SessionEntryPage` flow instead — confirmed dev-preview-only for this round.)
- LOW: `AudioRecorderService` is a shared `registerLazySingleton` across the whole app — this dev screen and any concurrently-open real exam-attempt speaking screen share the same underlying `record` package session. Not a regression (the existing Reading/Listening/Speaking-Writing preview screens already share this same singleton), but worth stating explicitly: this dev tooling assumes only one recording screen is active at a time in a debug session.

# Plan: Client-side Exam Timer — Remove Server-Side Per-Task Timer Polling/Enforcement
Status: 🟢 Complete (all 7 phases, awaiting final user sign-off)
Date: 2026-09-08 — 2026-09-09
Mode: Hard

## Overview
Move prep/response countdown and auto-advance for the PTE exam-delivery flow entirely to the client (`pte-app`), delete server-side deadline computation/enforcement (`TimerState`, `TimerController`, `AttemptService`'s deadline checks) in `pte-api`, and add a new decoupled heartbeat endpoint for an unrelated parallel connectivity-monitoring feature — all while keeping both services independently deployable at every commit boundary.

**Status note (confirmed with user, 2026-09-08): the product has not deployed to production yet — still dev-only, no real users/tenants.** The expand → client-cutover → contract phase ordering below is still worth following (it's sound engineering order independent of deploy stage, and `pte-api`/`pte-app` are still separately-run services even in a local/dev stack), but the *production-rollout ceremony* baked into several phases' Risks (API access-log evidence of zero `/timer` traffic before Phase 5, dual-write for Phase 1 rollback safety, Phase 6's drain sweep/exam-window scheduling/B2B kiosk sign-off) is written for **when this ships to real users** — none of it blocks implementing all 7 phases sequentially now. Phase 6 in particular should be implemented/reviewed as a runbook now (so it's ready), without literally executing a production drain against real traffic that doesn't exist yet.

## Research Summary
Built on the spec (`d:\FPT\9thSemester\pte\pte-app\plans\phat-client-side-exam-timer\spec.md`) and direct source reads of both repos during this planning session (not re-derived from the two prior `plan-researcher` reports, which are already folded into the spec):

- **`TimerState` (pte-api, `exam-delivery`) carries two unrelated groups of state**, confirmed by direct read: (1) deadline/enforcement fields (`phase`, `taskStartedAt`, `prepDeadline`, `responseDeadline`, `activeSection`, `isResponseWindowExpired`'s 15s grace) — the actual target of this refactor; and (2) `currentOrderIndex` (read by `AttemptService.currentItem`/`itemAt`, the basis of `NotCurrentTaskException`) plus `playCount`/`lastPlayRequestId`/`lastPlayAllowed` (read/written by `playAudio`'s idempotent replay-limit logic, under a pessimistic lock via `getStateWithLock`). Group (2) has no other home today (`ExamAttempt` has no matching fields) and must move to `ExamAttempt` in a phase that lands and is verified *before* the phase that deletes `TimerState` — Phase 1 does this, Phase 5 does the deletion.
- **`AttemptService.processAnswer`/`advanceUntilLiveOrComplete`** (`AttemptService.java`) are the two methods that actually consult deadlines: `processAnswer` calls `timerService.isResponseWindowExpired(timer)` before accepting an answer; `advanceUntilLiveOrComplete` (used by `getNextTask` and attempt-resume) loops "catch up" past every expired task using `TimerState`'s deadlines. Both must be deleted per FR-03/FR-08, but only after the client (Phase 3/4) no longer depends on server-side deadline enforcement to gate its own submission timing.
- **`SubmitAnswerRequest.payload` is `@NotBlank`** (confirmed by direct read) — will 400 an empty-payload timeout resubmission (FR-07) until relaxed. This relaxation is backend-additive (Phase 2) and must ship and be confirmed live before pte-app (Phase 4) starts sending empty payloads — sequencing risk called out explicitly in Phase 4.
- **pte-app's `TimerService` (`lib/features/exam_attempt/domain/timer_service.dart`) is a mature, well-tested class** (periodic poll + one-shot poll + local sub-second tick, `Stopwatch`-anchored, generation-guarded against stale async callbacks) built up over a prior plan (`phat-speaking-dynamic-prep-timing`). The rewrite (Phase 3) removes the poll/one-shot machinery and the `TimerRepository` dependency, but should preserve the existing `TimerScheduler`-injection pattern, stream contracts (`ticks`, `taskAdvancedExternally`), and generation-guard convention so downstream consumers (`ExamAttemptBloc`, `AutoRecordTimerBridgeMixin`, `TaskAdvanceButton`, all 5 audio-prompt Speaking cubits) need no interface changes.
- **`TaskAdvanceButton` already contains the general "submit-on-expiry" mechanism** (`_isExpired` + `_advance(reason: AdvanceReason.timeExpired)`, calling `cubit.flushPendingEdit()` then `syncEngine.flushOne(...)`) — FR-07's "resubmit via the existing `POST /answers` with empty payload" is largely this same existing path exercised with no prior answer content, not a new endpoint or new advance mechanism. Phase 4 must confirm this path already produces an empty/null payload correctly per task-type cubit, or extend it minimally where a cubit currently skips flushing when nothing was answered.
- **`SyncEngine`'s active-task exclusion** (`setActiveTask`/its own doc comment: "a background flush must never flush the row for the task currently displayed") is the mechanism FR-04 explicitly says the new heartbeat must *not* inherit — heartbeat needs its own independent interval loop, not a reuse of `SyncEngine`'s periodic timer.
- **No Flyway/Liquibase in `exam-delivery`** — schema is `ddl-auto: update` (Hibernate), confirmed by direct read of `application.yml`. This never drops columns/tables, so deleting the `TimerState` entity (Phase 5) leaves `timer_states` physically present until an explicit `DROP TABLE` is run (Phase 6) — this is a real, separate migration step, not automatic.
- **`pte-api/scripts/seed-e2e.ps1`** was checked directly: it contains only a stale explanatory comment referencing `TimerState.isResponseWindowExpired` (about a past grace-window bug fix) and makes no functional call to `/timer` or any timer-specific setup — no functional change needed there, but Phase 7's sweep re-confirms this once implementation is done.
- **Reading section's shared countdown** (`TimerService.startTaskTimer`'s `SECTION_SCOPED_SECTIONS`/`sectionBudgetSeconds`, server-side) computes one shared `responseDeadline` reused across every item in a contiguous Reading run — this is a genuine design question not spelled out step-by-step in the spec's FR list: once no deadline is persisted at all, this section-shared-budget *value* must still reach the client in some per-item form (FR-06 says the underlying computation stays "as before"). Flagged as a HIGH risk on Phase 5, not resolved here — the spec's own Assumptions/FRs authorize planner judgment on exact plumbing, but the *value* produced for Reading items must not silently change.

## Risks
- HIGH **(plan-reviewer finding, resolved)**: the entire security justification for removing server-side deadline enforcement (Phase 5) rests on one precondition stated in `spec.md`'s NFR — B2B tenants' exam machines must be genuinely OS-locked (kiosk mode), not just physically screened at the door — and the plan explicitly rejected a feature-flag fallback (spec P2), so there's no code-level safety net if a tenant doesn't meet it. This caveat previously lived only in `spec.md`, invisible to anyone skimming just this plan. **Current status (confirmed with user): no B2B tenant exists yet — product is pre-production/dev-only** — so this is a standing checklist note (Phase 6 Step 0), not a gate blocking anything in this cook cycle. Mitigation: restated explicitly in Phase 5's Risks and Phase 6 Step 0 so it isn't forgotten by the time an actual B2B deal happens — the gate activates then, not now.
- HIGH: deploying Phase 5 (backend deletes `TimerState`/`/timer`) before every in-field client version has cut over to local timing (Phase 3/4) breaks any client still polling `/timer` or relying on server-enforced deadlines outright. Mitigation: treat the expand → client-cutover → contract ordering as a hard release gate, confirmed via API access-log evidence of zero `/timer` traffic before Phase 5 deploys, not just "the code merged."
- HIGH: folding the FR-02-mandated `TimerState` non-deadline-state migration (`currentOrderIndex`, `playCount`, `lastPlayRequestId`, `lastPlayAllowed`) into the same commit/phase that deletes `TimerState` would break `getNextTask`/`processAnswer`/`playAudio` outright, not just timer behavior. Mitigation: Phase 1 lands this migration fully, independently tested, before Phase 5 touches `TimerState` at all.
- HIGH: Phase 4's client-side empty-answer-on-timeout resubmission will 400 every time if it ships before Phase 2's `@NotBlank` relaxation is confirmed live in production. Mitigation: explicit release-order dependency called out in Phase 4, not assumed from phase numbering alone.
- MEDIUM: the Reading section's shared-countdown value (today computed via a live `responseDeadline` reused across a section's items) has no spelled-out post-refactor mechanism in the spec's FR list beyond "keep the computation as before" — risks silently changing effective Reading time if not deliberately preserved. Mitigation: Phase 5 Step 6 explicitly requires confirming this value is preserved, not just that the code compiles.
- MEDIUM: removing server-side timer reconciliation also removes the only mechanism that previously corrected client/server drift after the app is backgrounded — `AppResumed`'s current behavior (re-arm polling) has nothing left to reconcile against. Mitigation: Phase 3 explicitly redesigns what `AppResumed` does (recompute from wall-clock task-start rather than trust a possibly-stalled `Stopwatch`).
- LOW: `TimerTaskAdvancedExternally` (proctor-initiated advance detection) currently depends on the timer poll noticing a changed `currentOrderIndex` — this detection path disappears with polling. Mitigation: Phase 3 explicitly flags this capability gap for product/spec sign-off rather than silently dropping it.
- LOW: `ddl-auto: update` failures on new non-null `ExamAttempt` columns against an already-seeded dev/prod database (precedent: `MediaObject.audioPrompt` in the reference plan) — mitigated by giving new columns explicit defaults, verified against an existing seeded database in Phase 1.
- NOTED (plan-reviewer, not blocking): Phase 5 has no rollback-impact discussion — after Phase 5 deploys, pre-Phase-5 code (if rolled back alone) expects a `TimerState` row per attempt that no longer gets created. Resolved by adding an explicit note to Phase 5's Risks: safe rollback is only a full Phase 1–5 revert done before any attempt progresses under Phase 5 code, never a Phase-5-alone revert.

### Phase 4 decisions made this session
- **`HeartbeatService` (new file, plain Dart class, not a `Bloc`)**: fires an immediate ping plus every 15s thereafter via an injectable `PeriodicTimerFactory` (mirrors `SyncEngine`'s own fake-timer testing convention); idempotent `start(attemptPublicId)` — a no-op if already running for the *same* attempt, since `ExamAttemptBloc` calls it on every in-progress transition (every task, not just the first) and without that guard a run of quick task-by-task submissions would nearly suppress the 15s cadence entirely. Heartbeat failures are caught and logged only, never surfaced — this is a presence signal for the separate connectivity-monitoring feature (FR-04), not exam-critical.
- **`ExamAttemptBloc` wiring**: `HeartbeatService` started in `_emitFromResponse` (real attempts) and `_onForceSubmitRequested`'s `_completeAttempt` stops it; `close()` disposes it. `_onTimerSnapshotUpdated` now edge-detects the exam-wide countdown's `examRemaining` transitioning from >0 to exactly zero and self-dispatches `ForceSubmitRequested` (FR-05) — the only mechanism left that can close out an attempt once the exam clock runs out, since server-side deadline enforcement is gone entirely as of Phase 1.
- **`code-reviewer` verdict: WARNING, 1 HIGH + 2 LOW, all fixed same session (no re-review cycle needed — fixes were mechanical, not open design questions)**:
  - **HIGH (real bug)**: `bloc`'s default `EventTransformer` is concurrent, and `_onForceSubmitRequested` only checked `_attemptPublicId != null` *before* its `await repository.forceSubmit(...)`, never re-checking or guarding during the await. The new exam-clock-zero auto-trigger gives this a second, deterministic source of `ForceSubmitRequested` that can race the pre-existing manual button path (its confirm dialog is async and the button is never disabled mid-submit) — both handlers could pass the guard before either's network call resolves, double-calling `forceSubmit`; the server rejects the loser with `AttemptAlreadyCompleteException`, which would overwrite an already-emitted `AttemptCompleted` with `AttemptError` (a real "completion screen flashes into an error screen" regression for an attempt the student already finished). **Fixed**: added a synchronous `_forceSubmitInFlight` guard, set/cleared only outside any `await`, so a second concurrent invocation is rejected before making any network call at all. New regression test added (`ForceSubmitRequested` group) using a `Completer` to hold the first call in flight and assert the second is a no-op.
  - **LOW**: `HeartbeatService.start`'s doc comment claimed to "mirror `SyncEngine.startSync`'s own idempotency guard" without disclosing that `SyncEngine.startSync` actually throws `StateError` for a genuinely different attempt while running, whereas `HeartbeatService.start` silently supersedes via `stop()`. Harmless today (`ExamAttemptBloc` always routes through `_completeAttempt` — which stops the heartbeat — before a new attempt can start) but undocumented as deliberate. **Fixed**: doc comment now explicitly names the divergence and why silent-supersede is acceptable here (best-effort presence signal, not exam-critical state).
  - **LOW**: `_onDevPreviewAttemptSeeded` (kDebugMode-only fixture path) was calling `heartbeatService.start('dev-preview-attempt')`, pinging the real endpoint every 15s for an attempt id that doesn't exist server-side — harmless (failures are swallowed) but produces recurring warning-log noise during dev preview for no benefit. **Fixed**: removed that call from the dev-preview path only; the real `_emitFromResponse` path is unaffected.
- **8 Listening cubits fixed (self-discovered during this phase's own investigation, not a code-reviewer finding)**: `flushPendingEdit()` was a complete no-op in all 8 (`mc_listening_single`, `mc_listening_multiple`, `write_from_dictation`, `highlight_incorrect_words`, `select_missing_word`, `fill_blanks_listening`, `highlight_correct_summary`, `summarize_spoken_text`), unlike their Reading counterparts which unconditionally upsert to the outbox. An untouched Listening task left no outbox row at all; `SyncEngine.flushOne` silently no-ops on a missing row; and with Phase 5 about to delete the server-side catch-up loop, an attempt could get permanently stuck on such a task with no client-side path forward. Fixed all 8 to write unconditionally, matching `McReadingSingleCubit`'s reference pattern — confirmed correct field-by-field by `code-reviewer`.
- **`AttemptService.submitAttempt`/`HeartbeatController` confirmed still correctly wired** on the backend side (`code-reviewer` cross-checked routes/auth against the client's new `sendHeartbeat`/`forceSubmit` calls) — no backend changes needed this phase, Phase 2's heartbeat endpoint and Phase 1's `submitAttempt` already cover everything Phase 4 needed.

### Phase 2 decisions made this session
- **New entity `AttemptHeartbeat`** (own table `attempt_heartbeats`), separate from `TimerState`/`ExamAttempt` by design — confirmed by `code-reviewer` to never touch the `@Version`-guarded `ExamAttempt` row Phase 1 just fixed the locking for.
- **code-reviewer 1st pass, HIGH finding (real)**: original design relied on `BaseEntity.updatedAt` alone as the "last seen" signal (to avoid a redundant field) — but Hibernate's dirty-checking for a `@OneToOne` association compares the associated id, not object identity, so re-setting the same already-associated attempt on a repeat heartbeat call is never "dirty," no UPDATE fires, and `updatedAt` silently freezes at creation time forever. **Fixed**: added an explicit `AttemptHeartbeat.lastSeenAt` field, set to `Instant.now()` on every call — a plain scalar column always triggers real dirty-checking.
- **code-reviewer 1st pass, MEDIUM finding**: two racing first-ever heartbeat calls for the same attempt could both miss the find-or-create check and both insert, throwing an uncaught `DataIntegrityViolationException`. First fix attempt (catch the exception in the same transaction) was itself found broken by the **2nd pass, HIGH finding**: this project runs on Postgres with `GenerationType.IDENTITY`, so a failed INSERT poisons the *entire* transaction — catching the exception in Java doesn't stop Spring's implicit commit from then failing with a confusing `TransactionSystemException` at the caller. **Actually fixed**: `HeartbeatService.recordHeartbeat` now runs in its own `Propagation.REQUIRES_NEW` transaction (a normal inter-bean call from `AttemptService`, so Spring's AOP proxy correctly intercepts it — no self-invocation issue) — the DB-level abort is now contained to just this call, so catching `DataIntegrityViolationException` there actually works. Also added a warning log (2nd pass MEDIUM: the original catch was silent and too broad, indistinguishable from an unrelated constraint violation).
- **code-reviewer 2nd pass, LOW finding**: `AttemptHeartbeat.attempt`'s uniqueness relied on Hibernate's implicit default for `@OneToOne` — made explicit via `@JoinColumn(unique = true)` so a future refactor (e.g. to `@ManyToOne`) can't silently drop the guarantee the duplicate-race handling depends on.
- **Not fixed, disclosed (2nd pass MEDIUM, accepted)**: the new `lastSeenAt`-advances test is Mockito-mocked (repository echoes back its argument) — it proves the service *calls* `setLastSeenAt`, not that Hibernate's real dirty-checking/flush actually persists the change. Same class of gap as Phase 1's disclosed concurrency-test limitation: this module has zero `@DataJpaTest`/Testcontainers integration-test infrastructure today, so a test that would catch e.g. an accidental `updatable = false` regression isn't achievable without introducing that infrastructure — treated as a pre-existing module-wide gap, not something this phase should newly solve.
- **`AttemptService.recordHeartbeat`** uses a new lightweight `ExamAttemptRepository.findByPublicIdAndStudentPublicId` (no `pinnedSnapshot` eager-fetch, no lock) rather than `findOwned`/`lockAttempt` — correct per `code-reviewer`: heartbeat only needs ownership+status, never mutates `ExamAttempt`.
- **`SubmitAnswerRequest.payload`'s `@NotBlank` removed** (FR-07) — confirmed by `code-reviewer` via cross-service grep that `scoring`'s `ObjectiveScoringService` parsers already null/blank-guard before use; `AttemptAnswer.payload` is already a nullable column; `AnswerSubmitService.autoExpire` already persisted `null` payloads before this phase. No downstream breakage.
- **New tests**: `HeartbeatServiceTest` (5 tests incl. the upsert-reuse and race-swallowing regression tests), `AttemptServiceHeartbeatTest` (3 tests: ownership/status), `AttemptServiceSubmitAnswerTest` (5 tests: blank/null/whitespace/non-blank payload acceptance) — filling gaps that predate this plan (`submitAnswer`/heartbeat had no dedicated happy-path coverage before).

### Phase 1 decisions made this session
- **Field relocation**: `currentOrderIndex`/`playCount`/`lastPlayRequestId`/`lastPlayAllowed` moved from `TimerState` to `ExamAttempt` exactly as planned, with `columnDefinition = "integer not null default 0"` on the two new int columns (mirrors the `MediaObject.audioPrompt` precedent, safe under `ddl-auto: update` against a seeded dev DB).
- **`playAudio`'s pessimistic lock relocated**: `TimerStateRepository.findWithLockByAttemptId` deleted (dead — `TimerState` no longer holds anything worth locking); new `ExamAttemptRepository.findWithLockById` (`PESSIMISTIC_WRITE`) added. `TimerService.getStateWithLock` deleted — `playAudio` no longer depends on `TimerService` at all (it never needed deadline data).
- **code-reviewer 1st pass, HIGH finding (real, not anticipated by the plan text)**: `ExamAttempt` carries `@Version` (pre-existing, for a different reason — guarding a racing timer-expiry auto-submit vs. manual submit). Relocating `currentOrderIndex`/`playCount` onto that same row meant `playAudio`'s new lock could race `processAnswer`'s advance step / `advanceUntilLiveOrComplete` (used by `getNextTask`/resume), which still wrote unlocked — a concurrent locked commit bumps `version` out from under the unlocked transaction's stale read, throwing an uncaught `ObjectOptimisticLockingFailureException` (bare 500). This is a genuinely new collision surface this migration introduced (before, `playAudio` and the advance path almost never touched the same `@Version`-guarded row in the common per-task case). **Fixed**: added a private `lockAttempt(ExamAttempt)` helper; `processAnswer` and `advanceUntilLiveOrComplete` now call it, matching `playAudio` — all three lock consistently before mutating the relocated fields.
- **code-reviewer 2nd pass, HIGH finding**: `submitAttempt` was a 4th unlocked writer of the same row (`findOwned` → `completeAttempt` → `attempt.submit()` + `save`), missed by the first fix. **Fixed** by moving the lock inside `completeAttempt()` itself instead of each caller individually — a single choke point all four paths (`playAudio`, `processAnswer`, `advanceUntilLiveOrComplete`, `submitAttempt`) now funnel through; callers that already locked earlier in the same transaction just re-acquire their own already-held lock (confirmed harmless, not a double-lock hazard, by both review passes).
- **Locking scope deliberately NOT extended to `createAndPin`**: its two `attemptRepository.save(attempt)` calls are the *initial insert* of a brand-new row — nothing else can race a row whose id doesn't exist yet, and the existing unique-constraint catch (`DataIntegrityViolationException` → `AlreadyAttemptedException`) already guards the real double-creation race. Confirmed via grep this is the only unlocked `attemptRepository.save` remaining, and it's a different (already-handled) class of race.
- **New test coverage for a pre-existing gap**: `playAudio` had zero tests before this phase — added `AttemptServicePlayAudioTest` (8 tests: happy path, replay idempotency, replay-limit exceeded, expired URL, wrong current item, already-complete short-circuit, UNLIMITED policy, lock-routing/TimerService-decoupling). `submitAttempt` likewise had zero tests — added `AttemptServiceSubmitAttemptTest` (2 tests: locks-before-completing, already-complete short-circuits without locking). Both gaps predate this plan; filled because this phase's own changes touched exactly these methods.
- **Not tested (disclosed, not silently missing)**: real multi-threaded/concurrent-transaction testing of the pessimistic lock is out of scope for this module's existing test infrastructure (Mockito-only, no Testcontainers/`@DataJpaTest` integration harness present anywhere in `exam-delivery`'s test suite today) — the new tests verify *routing* (the right repository method is called) and the fix's *logic* (locking before mutation, consistently across all four writers), not genuine DB-level lock contention under real concurrency. Flagged by `code-reviewer` as a MEDIUM finding, accepted as a pre-existing infrastructure gap rather than blocking this phase.
- **Test updates for the relocation itself** (per Step 6): `AttemptServiceTest`, `AttemptServicePhase2Test`, `AttemptMapperTest`, `TimerServiceTest` updated to build/assert against `ExamAttempt` instead of `TimerState` for the relocated fields (behavior asserted unchanged, per the step's own instruction). `TimerStateTest` needed zero changes (only exercises `isResponseWindowExpired`, untouched by this phase). New regression test added to `TimerServiceTest` (Step 7): `multiItemReadingSection_currentPointerAndSharedBudgetStayConsistentAcrossAllThreeItems`, confirming the pointer/shared-budget split across two entities doesn't desync across a 3-item Reading run.

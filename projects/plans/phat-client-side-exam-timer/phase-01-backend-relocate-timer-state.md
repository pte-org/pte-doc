# Phase 1: Backend expand — relocate TimerState's non-deadline state onto ExamAttempt

## Requirements
`ExamAttempt` becomes the durable source of truth for "which pinned item is current" and the audio-replay-limit counters, so this state can outlive whatever happens to `TimerState`/deadlines later. No client-visible behavior changes — this phase is a pure internal refactor.

## Steps
1. Add fields to `ExamAttempt` for the current-item order pointer and the three audio-replay-limit fields (play count, last play request id, last play allowed), with defaults so existing rows migrate cleanly under `ddl-auto: update`.
2. Repoint every read/write of these fields across `AttemptService` (current-item lookup used by `processAnswer`/`getNextTask`/`playAudio`, the answer-advance flow, and `playAudio`'s idempotent increment logic) from `TimerState` to the new `ExamAttempt` fields.
3. Preserve `playAudio`'s existing concurrency guarantee (its pessimistic lock today is taken on `TimerState` via `getStateWithLock`) by carrying the same locking behavior forward onto whichever entity now owns the replay counters — **(plan-reviewer HIGH finding, resolved)** explicitly, not just "whichever entity, preserve equivalent behavior": enumerate every method that reads or writes the relocated fields — at minimum `playAudio` (replay-limit read+increment), `processAnswer`'s current-item advance step, and `getNextTask`'s current-item read — and state which of them must take the pessimistic lock on the new `ExamAttempt` row so a concurrent advance and a concurrent replay-check can't race each other once both fields live on the same entity. Also note as an explicit tradeoff: `ExamAttempt` is touched by many more code paths than `TimerState` ever was, so locking it introduces more contention surface than the narrow `TimerState` lock did — size the lock scope (row-level, not table-level) and keep it minimal.
4. Leave `TimerState` holding only its deadline-related fields (phase, task-started-at, prep/response deadline, active section) — do not touch deadline enforcement behavior in this phase.
5. Confirm the Reading section's shared-timer budget computation (which reads/writes `TimerState.activeSection` alongside the now-relocated current-item pointer) still produces identical values after the split — same transaction, no behavioral change.
6. Update the existing unit tests that construct/assert on `TimerState`'s now-relocated fields (`AttemptServiceTest`, `AttemptServicePhase2Test`, `AttemptMapperTest`, `TimerServiceTest`, `TimerStateTest`) to build/assert against `ExamAttempt` instead, without changing what behavior they verify.
7. Add a regression test for a multi-item Reading section confirming the shared-budget/current-pointer relocation didn't split state across two inconsistent writes.

## Success Criteria
- `AttemptServiceTest`, `AttemptServicePhase2Test`, `AttemptMapperTest`, `TimerServiceTest`, `TimerStateTest` all pass, updated (not deleted) to reference the relocated fields.
- Full `exam-delivery` module test suite (`mvn test`) passes with zero regressions.
- Manual: a full attempt run against a local stack behaves identically to before this phase — task order and audio-replay limits unchanged from the client's perspective (no API contract change).

## Risks
- HIGH: repointing `playAudio`'s pessimistic lock without preserving equivalent locking semantics could reopen the exact replay-limit race the lock exists to prevent — mitigate by carrying the lock forward onto the new field owner (covering `playAudio`, `processAnswer`'s advance step, and `getNextTask` — see Step 3) and covering it with a concurrency test (two racing plays for the same item, plus a play racing an advance).
- LOW **(plan-reviewer finding, downgraded — project is pre-production)**: this migration is a one-way repoint with no dual-write to the old `TimerState` fields, which would matter for safe rollback *after* real attempts have progressed under it in production. The project has not deployed to production yet (dev-only at planning time) — there is no live traffic or real in-flight attempt to make rollback-after-the-fact a real scenario, so dual-write is unnecessary overhead right now. Do not add dual-write for this rollout. Revisit only if this specific migration is still pending by the time the app has real production traffic — at that point, re-evaluate whether a dual-write window is worth adding before that deploy.
- MEDIUM: splitting the current-item pointer and the Reading section's `activeSection`/shared-budget bookkeeping across different entities/transactions could desync them — mitigate by keeping both writes in the same transaction and testing a 2+ item Reading section explicitly.
- LOW: adding non-null columns to `exam_attempts` under `ddl-auto: update` can fail against an already-seeded database if no default is given (precedent: `MediaObject.audioPrompt` in a prior plan) — mitigate with explicit column defaults, verified against an existing seeded dev database.

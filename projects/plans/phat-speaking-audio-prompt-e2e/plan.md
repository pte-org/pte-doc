# Plan: Speaking Audio-Prompt Playback End-to-End
Status: ✅ Complete
Date: 2026-08-31
Mode: Hard

## Overview
Wire up real audio-prompt playback end-to-end for the Speaking tasks that require it (`REPEAT_SENTENCE`, `RE_TELL_LECTURE`, `ANSWER_SHORT_QUESTION`, `RESPOND_TO_A_SITUATION`, `SUMMARIZE_GROUP_DISCUSSION`), backed by a real locally-running `pte-api` — extending the seed-script + manual-walkthrough pattern from the just-completed `phat-speaking-api-e2e-verify` plan to cover the audio-prompt-playback gap that plan explicitly left out of scope.

## Phases
- [x] Phase 1: Backend — resolve Speaking audio-prompt URLs — extend `SnapshotPinService.toPinnedItem`'s presign branch to cover non-LISTENING sections (preserving LISTENING's existing required-audio invariant unchanged), so the already-existing on-demand `/audio` endpoint can serve Speaking items too. No `TaskView`/`AttemptMapper` changes.
- [x] Phase 2: Frontend — wire real audio-prompt playback — call the existing `GET /attempts/{attemptId}/items/{itemId}/audio` endpoint (with a generated `X-Play-Request-Id`) when the "Playing" sub-stage begins, add network-URL playback to `AudioPlayerServiceImpl`, and handle replay-limit/expiry errors gracefully.
- [x] Phase 3: Seed script — Repeat Sentence audio question support — extend `pte-api/scripts/seed-e2e.ps1` with the media-upload sub-flow needed to seed a published `REPEAT_SENTENCE` question with a real `audioPromptRef`.
- [x] Phase 4: Manual E2E walkthrough — confirm the real stack resolves and serves a playable URL via the real `/audio` endpoint, the app actually plays it during prep, and the already-proven record → upload → submit leg still works for this task type.

## Research Summary
This plan is built on findings already confirmed against current source in the requesting session, later corrected once by an independent `plan-reviewer` source check (see below — not re-derived here):
- `SnapshotPinService.toPinnedItem` already calls `mediaClient.presignGet(...)` to resolve `audioPromptRef` into a playable URL, but only inside `if (LISTENING_SECTION.equals(source.section()))` — never runs for SPEAKING items. Result is written to `PinnedItem.audioUrl`/`audioUrlExpiresAt`, fields that already exist on the entity.
- **Corrected by plan-reviewer (superseding the original assumption):** a dedicated on-demand endpoint already exists — `GET /attempts/{attemptId}/items/{itemId}/audio` (`AttemptController.playAudio` → `AttemptService.playAudio`) — which reads `PinnedItem.audioUrl`/`audioUrlExpiresAt` directly (the exact fields Phase 1's widened presign branch populates) and returns `AudioPlayResponse.audioUrl`. It already enforces real exam-integrity semantics: per-item play-count limits (`resolvePlayLimit`: item's `maxPlayCountOverride`, else session `replayPolicyType`/`replayPolicyLimit`; `UNLIMITED`/no override → never rejects) → `ReplayLimitExceededException` once exceeded; idempotent retries via a client-generated `X-Play-Request-Id` header (same id replays the prior outcome without re-incrementing `playCount`); `AudioUrlExpiredException` once the resolved URL's TTL has passed; `NotCurrentTaskException` guarding against off-task calls — all behind a pessimistic lock on `TimerState`. **Because this endpoint already exists and already reads the fields Phase 1 populates, `TaskView` must NOT be extended with a baked-in `audioUrl` field** — doing so would let the FE bypass all of this play-limit/expiry enforcement. `TaskView.audioPromptRef` (already present, raw UUID) remains sufficient signal for the client to know an item has an audio prompt; the actual URL is fetched on-demand via `/audio` when the student reaches the "Playing" sub-stage. Phase 1 and Phase 2 below reflect this corrected scope — the original assumption ("no separate media call, URL must be baked into task-fetch responses") is superseded.
- `AttemptController.playAudio`/`AttemptService.playAudio` need no changes themselves — they already do everything this plan needs; this plan only needs to make sure `PinnedItem.audioUrl` gets populated for Speaking items in the first place (Phase 1) and that the FE actually calls this existing endpoint (Phase 2).
- Media service itself needs no changes — `InternalMediaController`'s `GET /internal/{publicId}/presigned-url` (service-to-service, `INTERNAL_SERVICE_KEY`-protected) is already the exact endpoint `mediaClient.presignGet` calls, and is already what backs `/audio`'s resolved URL indirectly via the presign step in Phase 1.
- FE: `task_view.dart`'s existing `audioPromptRef` field is unchanged and sufficient — no new URL field is added to the model.
- FE: `AudioPlayerServiceImpl` (backed by `just_audio`) today only has `play(String source)` → `_player.setAsset(source)`, explicitly documented as asset-path-only, never a network URL, for the mock-data phase. Needs a real network-URL playback path added without breaking existing asset-based mock-data callers (Listening screens' bundled sample assets).
- FE: `AudioListeningPrepCard` (in `audio_prompt_record_body.dart`) is currently a pure UI countdown driven only by `TimerSnapshot` elapsed time — it never reads `task.audioPromptRef` and never calls any endpoint or touches any `AudioPlayer`. This is where the real `/audio` call and playback must be wired into the "Playing" sub-stage.
- Seed script: `pte-api/scripts/seed-e2e.ps1` (built in `phat-speaking-api-e2e-verify`) currently only seeds `READ_ALOUD` (text-only, no media). Extending it to `REPEAT_SENTENCE` requires adding the media-upload sub-flow (`POST /api/media/objects` → `PUT` file bytes → `POST complete` → use returned `mediaPublicId` as `audioPromptRef`).
- Out of scope: `DESCRIBE_IMAGE`'s missing image content-type support in the media service — a separate, already-identified gap (image, not audio).
- Correction (plan-reviewer NOTED): the timer-poll endpoint (`GET /attempts/{id}/timer`) does not carry `TaskView`/task content at all — it returns `TimerStateResponse` only, per its own code comment. It is not one of the "task-fetch endpoints" relevant to this plan's audio-URL question; the relevant endpoints are `startOrResumeAttempt`/`fetchNextTask` (for `TaskView.audioPromptRef`) and the separate on-demand `/audio` endpoint (for the actual URL).
- Three decision points were flagged during planning; all three are now resolved (user confirmed during Step 4 validation, superseding the plan's original defaults for two of them — see each phase's Steps for the resolved detail): (1) `AudioListeningPrepCard`'s "Playing" sub-stage progress bar is driven off the real audio player's position/duration stream, not `TimerSnapshot` elapsed time (overrides the plan's original simpler default); (2) a fresh `X-Play-Request-Id` is generated once per entry into the "Playing" sub-stage (confirms the plan's original default); (3) the seed fixture must be a short, genuinely audible recording — none of the existing `.wav` assets qualify (all confirmed silent), so a new one is recorded and committed (overrides the plan's original silent-fixture default).

- NOTED: the `/audio` endpoint's `audioUrlTtlSeconds` is computed once per attempt-pin as the full session window (`opensAt`→`closesAt` + 60s grace) and reused for every item, so no single task's prep+response window can exceed it — confirmed not a risk, no phase action needed.
- NOTED: Phase 4's LISTENING regression check is only a spot-check of Read Aloud (no audio involved), not a live-stack check of an actual LISTENING item's audio resolving post-change — Phase 1's unit tests do cover this at the service level, so this is not a blocker, just a nice-to-have gap if Phase 4 has spare time.

- NOTED (2nd plan-reviewer pass): `attemptPublicId` is not currently threaded into `AudioPromptRecordBody`/`AudioListeningPrepCard` — it exists one level up as a field on each of the 5 Speaking screens (`RepeatSentenceScreen`, `RetellLectureScreen`, `AnswerShortQuestionScreen`, `SummarizeGroupDiscussionScreen`, `RespondToASituationScreen`, sourced from `AttemptInProgress` state) but isn't passed down to the shared widgets that need it for the new `/audio` call. ### Post-completion exploratory findings (user-requested, ad-hoc — session/plan-reviewer process not re-run for these)
After this plan was marked complete, the user asked to also manually spot-check **Answer Short Question** (shares the identical `AudioPromptCubit`/`AudioPromptRecordBody` code path with Repeat Sentence) — seeded ad-hoc via direct API calls (not added to `seed-e2e.ps1`, since this was exploratory, not a plan deliverable). Two real, user-observed bugs surfaced, **deliberately left unfixed at the user's explicit choice ("ghi nhận, để sau" — note and defer)**:

1. **"Playing" sub-stage's countdown label and progress bar are two independent clocks that can visibly disagree.** The label (`AudioListeningPrepCard`'s "Playing N seconds left" text) is still driven by the *original* fixed-window timer arithmetic (`audioSeconds = prepSeconds - preListenSeconds - preRecordSeconds` — 8s for Answer Short Question, 6s for Repeat Sentence), unchanged since before this plan. The progress bar (Phase 2's change) is driven by the *real* audio player's position/duration. These only agree if the real audio's actual runtime happens to match the screen's fixed window — the 2.5s synthetic tone fixture is much shorter than either window, so the bar visibly fills to 1.0 and the audio finishes while the label still counts down several more seconds. Not purely a fixture-length artifact: even a well-matched real recording wouldn't guarantee exact agreement, since the two clocks have no structural link. Real fix would need a design decision (e.g., derive the label from the same real position/duration the bar uses, and/or let real audio-finish drive the transition into the pre-record sub-stage instead of a fixed elapsed-time offset) — bigger than a one-line patch, hence deferred.
2. **Recording can start several seconds late relative to the "Beginning in" countdown reaching 0, for short-`prepSeconds` task types.** `TimerService`'s poll interval is a fixed 10s (`_defaultPollInterval`), and the client's local `TimerSnapshot.phase` only updates on a server reconciliation (never self-advances between polls, by design). For a task with `prepSeconds` in the 10–15s range (all 5 of this plan's audio-prompt Speaking types — see Phase 1's `task-timing.json` additions), the worst-case ~10s poll staleness after the real server-side `prepDeadline` passes is a large fraction of (sometimes longer than) the entire prep window, so the UI can sit at "Beginning in 0 seconds" for several real seconds before the next poll reconciles `phase` to `response` and recording actually starts. Read Aloud's 35s prep window never surfaced this (same absolute lag, much smaller relative to the whole window) — this is the first time any task type with a short `prepSeconds` was walked through against a live server. Pre-existing `TimerService` behavior, not introduced by this plan; exposed by it. Real fix (e.g. a shorter poll interval, or an immediate extra poll right when the local countdown hits zero) needs its own design pass, hence deferred.

Both are real, reproducible, user-confirmed — worth a dedicated `/ck:plan` if picked up later.

## Research Summary
Both parallel researchers this session independently confirmed the same root causes and the same adopted design — captured directly in the feature description this plan was generated from, not re-derived here:

- **Gap 1 (`task-timing.json`):** `DESCRIBE_IMAGE` and `PERSONAL_INTRODUCTION` have no entry in `task-timing.json`, so `TaskTimingConfig.timingFor()` throws `TaskTimingNotConfiguredException` the moment either type is pinned into a real attempt. User-confirmed, Dart-fixture-matched values: `DESCRIBE_IMAGE` prepSeconds=25/responseSeconds=40 (static shape, matches `READ_ALOUD`'s — no `preListenSeconds`/`preRecordSeconds`, no sub-stage split); `PERSONAL_INTRODUCTION` prepSeconds=25/responseSeconds=30 (also static, needs nothing else — no image/audio resolution).
- **Gap 2 (`imagePromptRef` never resolved):** `Question.imagePromptRef`/`PinnedItem.imagePromptRef` are `UUID` (a MediaObject public ID), copied through raw by `SnapshotPinService.toPinnedItem` with zero presign resolution — the Describe Image screen would try to `Image.network()` a raw UUID, which can never load.
- **Adopted design:** mirror `SnapshotPinService.resolveAudioUrl` (added by `phat-speaking-audio-prompt-e2e`) — resolve once, eagerly, at pin time via the same `MediaClient.presignGet(...)` call and the same `audioUrlTtlSeconds` value already computed in `pin()` (media-type-agnostic, no rename needed). Store on `PinnedItem` as new `imageUrl`/`imageUrlExpiresAt` fields, parallel to (not replacing) `audioUrl`/`audioUrlExpiresAt`, since `imagePromptRef` stays typed `UUID` and unchanged.
- **Rejected alternatives** (do not reintroduce): an on-demand `/image` endpoint (images have no replay-limit/idempotency concern the audio `/audio` endpoint exists for); a public/unauthenticated MinIO URL (reverses `PresignService.presignGet`'s tenant-scoped defense-in-depth); response-build-time live-resolution (violates `SnapshotPinService`'s "exam-delivery never calls out again after pin" invariant).
- **Critical correction vs. the audio precedent:** audio's `audioUrl` stops at `PinnedItem` — served via the separate on-demand `/audio` endpoint, never reaching `PinnedItemView`/`TaskView`. Since Describe Image needs `imageUrl` directly in the student-facing `TaskView` JSON (no on-demand endpoint), it must be threaded one layer further than audio: `PinnedItem` → `PinnedItemView` → `TaskView` → `AttemptMapper.toTaskResponse` → Dart `TaskView`. `imageUrlExpiresAt` stops at `PinnedItem` (nothing downstream needs it, mirrors `audioUrlExpiresAt`).
- **Fail-fast behavior:** `DESCRIBE_IMAGE` with a null `imagePromptRef` throws a new `MissingImagePromptException` (mirrors `MissingAudioPromptException` exactly — `DomainException`, HTTP 422, new `ExamDeliveryConstants.MISSING_IMAGE_PROMPT`), using the same task-type-string-check style `LISTENING_SECTION.equals(source.section())` already establishes (no cross-module `PteTaskType` enum import). A null presign response throws a new `ImageResolutionFailedException` (mirrors `AudioResolutionFailedException`).
- **Confirmed by direct source read this session** (both researchers agreed, verified fresh during plan-writing): `SnapshotPinService.java` (176 lines, `resolveAudioUrl` at line 166), `PinnedItem.java` (audio fields at lines 83-88, both nullable — new `imageUrl`/`imageUrlExpiresAt` fields must stay nullable too, same pattern, avoiding the NOT-NULL-column-on-existing-rows `ddl-auto: update` pitfall this session already hit once elsewhere), `PinnedItemView.java` (17-field record), `PinnedSnapshotCacheService.toView` (the entity→view builder call site), `TaskView.java` (exam-delivery DTO, already carries `imagePromptRef` unchanged), `AttemptMapper.toTaskResponse` (the `new TaskView(...)` construction site), `task-timing.json` (12 currently-configured types, none for these two), `SnapshotPinServiceTest.java` (existing 3-pattern audio-resolution test suite to clone), `AttemptMapperTest.java` (constructor-arity fix site), `pte-app`'s `task_view.dart`/`describe_image_screen.dart`/`task_image_display.dart`/`task_type_dispatcher_test.dart`/`describe_image_screen_test.dart` (the `_ImageRegion` widget already reads `task.imagePromptRef` as if it were a URL — a pre-existing placeholder bug this plan fixes by switching the read site to a new `imageUrl` field).

## Dependencies
- Phase 2 depends on Phase 1 (an item can't be pinned/tested end-to-end without `task-timing.json` configured for `DESCRIBE_IMAGE`).
- Phase 3 depends on Phase 2's new `PinnedItem.imageUrl` field existing.
- Phase 4 (frontend) depends on Phase 3's `imageUrl` reaching the student-facing JSON.
- Phase 5 depends on Phases 1–4 all being deployed to a local stack, plus a new test image fixture.
- No external services beyond the already-existing `media`/MinIO stack this session's prior plan already exercises.

## Risks
- MEDIUM: a new NOT-NULL column with no default breaks Postgres `ddl-auto: update` against an existing dev DB with rows (hit once already this session, in a different table) — mitigated because `imageUrl`/`imageUrlExpiresAt` are both nullable, matching `audioUrl`/`audioUrlExpiresAt`'s own shape exactly; Phase 2 explicitly verifies this before considering itself done.
- MEDIUM: widening `PinnedItemView`/`TaskView`'s constructors breaks every existing positional-argument test call site that constructs them directly (`AttemptMapperTest`, possibly others) — mitigated by Phase 3 explicitly doing a mechanical arity-fix pass across all call sites, same pattern the prior `phat-speaking-dynamic-prep-timing` plan used successfully for its own field additions.
- LOW: no image test asset exists anywhere in `pte-api` today (only 2 WAV fixtures) — mitigated by Phase 5 generating a small synthesized PNG fixture, same spirit as the existing synthesized WAV tones, no external asset dependency.
- LOW: `PERSONAL_INTRODUCTION`'s tiny scope (config-only) could get lost inside the much larger Describe Image work — mitigated by keeping it as an explicitly separate, clearly-labeled step within Phase 1 rather than folding it silently into a Describe-Image-titled phase.
- HIGH (plan-reviewer finding, resolved): Phase 5 originally reused the same seeded session for both its API-level verification step and the human app walkthrough — since `DESCRIBE_IMAGE`'s prep/response window is short (25s/40s) and `ExamAttempt` is one-shot per (student, session), the verification step's own `startAttempt` call would begin that session's countdown, risking an already-expired or already-resumed-mid-flight attempt by the time the human walkthrough runs. Mitigated by Phase 5 now seeding two sessions per task type (one for verification, one left untouched for the walkthrough), mirroring the identical fix already proven in `phat-speaking-dynamic-prep-timing`'s own Phase 5 this same session.
- LOW (plan-reviewer NOTED, accepted as pre-existing precedent, not a new bug): `resolveImageUrl`'s presign-failure path (`ImageResolutionFailedException`) isn't scoped to `DESCRIBE_IMAGE` only — it fires for *any* item with a non-null `imagePromptRef` that fails to presign, regardless of task type, hard-failing the whole attempt pin. This exactly mirrors `resolveAudioUrl`'s existing, already-shipped behavior for `audioPromptRef` (same blast radius, same precedent) — not a new risk this plan introduces, but worth having on record since it means a stray/legacy non-null `imagePromptRef` on an unrelated task type could unexpectedly block pinning that item's whole attempt.

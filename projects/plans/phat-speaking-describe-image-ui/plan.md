## Research Summary
Two independent research passes converged on the same shape, used as settled guidance (not re-litigated here):

1. **Cubit/state unification is warranted now.** `ReadAloudCubit`/`ReadAloudState` and `RepeatSentenceCubit`/`RepeatSentenceState` are byte-for-byte identical in mechanics (constructor wiring, `_startInFlight`/`_stopInFlight` guards, `onTimerSnapshot`, `startRecording`/`stopRecording`, `close`) — `RepeatSentenceCubit`'s own doc comment already flags this as "the 2nd auto-record cubit... extract a shared base/mixin if a 3rd lands." Describe Image is that 3rd occurrence. Delete the two old cubit/state pairs outright (not typedefs); replace with one `AutoRecordCubit extends Cubit<AutoRecordState>` / `AutoRecordState implements UploadTrackingState`. The `_startInFlight`/`_stopInFlight` re-entrancy guards are a previously-fixed CRITICAL/HIGH bug class — copied verbatim, never re-derived. `resolveReadAloudFilePath` renames to `resolveRecordingFilePath` and relocates into the new cubit file, behavior/doc unchanged.

2. **Timer-bridge boilerplate is identical across screens** (`initState`/`_forwardIfCurrentTask`/`dispose`, including the `pinnedItemPublicId` identity guard that fixes a previously-found CRITICAL plan-reviewer finding — a `TaskTypeDispatcher` dispose-timing race). Extract to `AutoRecordTimerBridgeMixin`, called explicitly from each screen's own `initState`/`dispose` (no hidden `State.initState` override — matches this codebase's explicit-lifecycle style). All 3 screens adopt it, including the 2 existing ones (in-scope now, not deferred).

3. **`TaskImageDisplay` is a new, simple, props-only `StatelessWidget`** using `Image.network` (Flutter SDK built-in, no new dependency) with `loadingBuilder`/`errorBuilder`, mirroring `RecordedAnswerStatusCard`'s "shared `widgets/` even with one current consumer" precedent.

4. **Open design question resolved: extract a shared status-card widget too.** `ReadAloudScreen`'s private `_StatusCard` (recorded-always-wins → live "Recording" countdown → live "Beginning in…" countdown, progress forced to `0.0` during prep) is exactly the state machine Describe Image needs — reusing it verbatim would make it a 2nd occurrence today and would have hit a 3rd if any future screen needed the same non-sub-staged single-card shape. Per this project's own "extract at 3rd occurrence" rule, the plan extracts it now as `AutoRecordStatusCard` in Phase 3, used by both `ReadAloudScreen` and `DescribeImageScreen`. `RepeatSentenceScreen`'s `_RecordCard` is **not** merged into it — it has extra pre-record sub-stage clamping logic (`_elapsedPrepSeconds`, `_preRecordSeconds` boundary) that genuinely diverges, so forcing a shared abstraction there would add branching complexity for no duplication removed. Documented explicitly so this isn't re-litigated later.

5. **Instruction text needs a 2-variable template**, unlike Read Aloud's 1-variable (`responseSeconds`, interpolated twice) template. Literal wording (matches real PTE "Describe Image" instruction tone): "Look at the image below. In {prepSeconds} seconds, please speak into the microphone and describe in detail what the image is showing. You will have {responseSeconds} seconds to give your response."

6. **Dev fixture timing (`prepSeconds: 25`, `responseSeconds: 40`) is intentionally off the 10s poll boundary** — mirrors the existing `repeatSentence` fixture's own documented trade-off (`speaking_writing_task_fixtures.dart` lines 36–51): up to ~5s of dev-preview-only UI lag at the prep→response and response→recorded transitions, since `ExamAttemptBloc`'s dev-preview poll only lands on 10s multiples and `TimerService.seedFromTask` only self-derives phase once — every later transition needs an actual poll response to flip it. Never a production concern (production timing comes from real server-pushed deadlines). Do not "fix" by rounding — the user has explicitly confirmed these literal values.

7. **`TaskImageDisplay`'s dev fixture requires real network access** (`https://picsum.photos/seed/describe-image-fixture/800/600`) — a new, documented exception to every other fixture's offline-safe design, scoped to this one dev-preview task type only. Automated widget tests do not depend on the image actually loading (they assert on the widget tree/props, not on a completed network fetch).

## Dependencies
None. `DESCRIBE_IMAGE` as a `TaskView.taskType` value and `TaskView.imagePromptRef` already exist in the domain model (`lib/features/exam_attempt/domain/task_view.dart`) — no backend contract change required. No new pubspec dependency (`Image.network` is Flutter SDK built-in).

## Risks
- HIGH: Cubit/state unification could silently change Read Aloud/Repeat Sentence production behavior if the merge drifts from the original logic — Mitigation: copy the guard/lifecycle code verbatim (not re-derived), full regression suite gate at the end of Phase 1 before any later phase proceeds.
- HIGH: The dev fixture's non-poll-aligned `prepSeconds: 25`/`responseSeconds: 40` causing dev-preview lag could later be "fixed" by a well-meaning contributor who doesn't understand the trade-off — Mitigation: explicit doc comment on the fixture (mirroring `repeatSentence`'s), and this plan's explicit instruction not to round.
- MEDIUM: Extracting `AutoRecordStatusCard` out of `ReadAloudScreen`'s private `_StatusCard` could subtly change its rendering/progress-fraction math — Mitigation: port logic verbatim; `read_aloud_screen_test.dart`'s existing assertions (unchanged) are the regression gate.
- MEDIUM: `TaskImageDisplay`'s network dependency could make the dev-preview screen appear broken offline/in CI — Mitigation: documented as an intentional, scoped exception; automated tests don't require the image to actually load.
- LOW: A real backend `DESCRIBE_IMAGE` task with `imagePromptRef == null` — Mitigation: treated as a fixture/data error per PTE task definition (real Describe Image tasks always carry an image); render a graceful fallback message via `AppStrings`, never crash.
- LOW: `AutoRecordTimerBridgeMixin`'s dispose-timing race doc comment could be shortened/lost during extraction — Mitigation: explicit instruction (this plan + Phase 2's own file) to preserve it verbatim inside the mixin's forwarding closure.

- LOW (NOTED, plan-reviewer): The Research Summary item 6 phrase "mirrors the existing `repeatSentence` fixture's own documented trade-off" is imprecise — `repeatSentence`'s `prepSeconds: 10` (and `readAloud`'s `prepSeconds: 30`) were deliberately chosen to *land on* the 10s poll boundary and avoid lag; the Describe Image fixture makes the opposite choice, keeping the literal 25/40 and accepting the lag. Both are legitimate trade-offs but not the same one — read it as "unlike `repeatSentence`/`readAloud`, which round to a poll-boundary-aligned value to avoid lag, this fixture keeps the user-mandated literal 25/40 and accepts the resulting lag," not as the two fixtures making an identical decision.

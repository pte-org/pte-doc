# Research — Primary implementation

Date: 2026-10-11. Source inspection only; no application edits or tests executed.

## Verdict

Implement the approved P1 workspace with three bounded REST projections and the existing plain STOMP transport. Keep resource ownership inside Session, Attempt, Identity, and Proctoring; add public facade records rather than exposing entities, internal repositories, pinned answers, or HOST directory endpoints. Harden authorization before connecting the product UI. Do not introduce a message broker replacement, video, a durable command log, or a new authorization tier for LEAD/ASSISTANT.

## REST ownership and concrete contracts

- `session/internal/controller/ProctorAssignmentQueryController`: new GET `/api/v1/proctor-assignments/mine`, actor from CurrentUserContext, PROCTOR role, nonnull current tenant. Add Session-owned query service and pageable assignment/session join projection to `ProctorAssignmentRepository`; use exact tenant + actor + nondeleted predicates. DTO includes assignmentPublicId, assignmentRole, examSessionPublicId, session name/code/status/opensAt/closesAt. Default page 0/size 25, maximum size 100; deterministic schedule/publicId order. Existing assignment management remains HOST only.
- `proctoring/internal/controller/MonitoringController`: new GET `/api/v1/exam-sessions/{id}/monitoring`, returning metadata, assignmentRole, server snapshotAt, whole-exam summary, and a page of enrolled student rows. A row has enrollmentPublicId, studentPublicId, studentName, nullable latestAttempt, attemptCount; latestAttempt contains attemptPublicId, attemptNumber, status, startedAt/submittedAt, lastSeenAt, manualViolationCount. No student email is required. Missing identity display information uses a safe unnamed fallback while preserving enrollment.
- Same controller: GET `/api/v1/exam-sessions/{id}/monitoring/students/{studentId}/attempts`, a paginated minimal attempt history; validate that student is actually enrolled in this exam before querying. Include the same minimal attempt fields, no pinned snapshot/content. Stable latest selection is highest immutable attemptNumber, following the production lifecycle repository method; publicId is a deterministic fallback only for corrupt ties. Correct the former spec assumption about createdAt/publicId ordering. Do not accidentally use the old Optional repository method for multiple attempts.
- Add Session facade metadata/assignment projection + bounded enrollment page + enrollment membership check. Add Attempt facade batch latest/attempt-count/heartbeat projections for page student IDs, bounded history, aggregate latest-status counts, and tenant/session/attempt validation. Add Identity facade `findStudentDisplayNames(tenantId, ids)` backed by existing `UserRepository.findByPublicIdInAndTenantIdAndDeletedFalse`, with a new exported minimal record in `identity/dto/response`.
- All three DTOs live in the owning module's `internal/dto/response`; facade views crossing modules live in exported `dto/response` packages with `package-info.java` NamedInterface. Proctoring must never import another module's `internal` namespace. Use explicit constructor injection and manual mapping as existing code does.

## Pagination and counts

Smallest reliable MVP omits roster search/status filter controls: the spec permits those controls only with proper server-side filtering. Paginating enrollment first and filtering enriched name/status afterwards is incorrect. Avoid loading the entire tenant directory or full attempt history to implement filters. Assigned-list status filter is straightforward in its Session-owned query and can be included; global student-name/attempt-status filters are a separate deliberate query design if required.

Registered count comes from Session's enrollment count. In-progress/submitted counts are counts of each student's latest nondeleted attempt, not counts of all retry attempts. Attempt's aggregate SQL returns a fixed-size status-count projection without materializing all attempts; filter by tenant/session and select each student's latest row with a correlated NOT EXISTS or PostgreSQL window query. Page latest projections likewise select latest in SQL and batch heartbeat for at most 100 students, not all their historical attempts. Enrollment mutations are already restricted to SCHEDULED in `session/internal/service/EnrollmentService.requireManualAudienceMutationAllowed`; enrollment cannot be manually removed after OPEN, supporting consistent operational counts. Verify imported/generated cohort invariants in tests and treat nonexistent/soft-deleted attempt rows consistently.

Recommended counter: **manualViolationCount**, grouped `ViolationEvent` by attempt and tenant/session, excluding deleted entries. UI label **“Ghi nhận của giám thị”**. Combined security audit contains STUDENT_LOCKDOWN events with WARNING/CRITICAL and PROCTOR manual records synthesized as WARNING; adding them together under “Vi phạm” implies an assessment that the backend does not make. Audit remains combined and source-labelled. If total security-event count is later needed, give it a distinct name and batch facade aggregate rather than reading every audit page.

Bound query count per snapshot: authorize/metadata, enrollment page/count, whole-exam attempt aggregate, page latest/attempt counts, page heartbeats, page names, page manual-event aggregates. Use scalar projections and batch queries; no eager pinned snapshots. Count queries may scan cohort rows but return fixed-size results. Confirm with a PostgreSQL fixture of 100 enrollments and multiple retry attempts; row count must not produce per-student query growth. Add new Flyway indexes only after explain/query inspection identifies need.

## Authorization and race boundaries

Existing `SessionService.checkProctorAssignment` returns tenant but takes no caller tenant; strengthen or add a facade that explicitly validates tenant and provides assignment role/session metadata. Existing security audit PROCTOR branch also trusts assignment tenant without comparing caller tenant; fix it and legacy violation-list reads. HOST+PROCTOR actors must use PROCTOR scope on monitoring and WS, even if the existing combined audit legitimately allows HOST reads.

Use a reusable Proctoring access policy for read-assigned, control-open, owned-active, and close-owned. Read permits CLOSED/SCHEDULED (and other actual SessionStatus values); control requires OPEN and opensAt-inclusive/closesAt-exclusive gate. Resume must authorize before returning ACTIVE. Close remains owned + tenant and idempotent, even after assignment revocation or exam close.

For mutations, serialize assignment revocation and command/flag/open with the same Session row lock: Session facade `lockForProctorOperation(sessionId, tenantId, proctorId)` checks assignment and entry window while locked; `EnrollmentService.unassignProctor` must acquire that same row lock. Preserve lock order session → attempt/proctor aggregate consistently. Target validation and FORCE_SUBMIT must occur in Attempt's transaction with exact tenant/session identity; change/add scoped facade rather than checking existence in one call and mutating a differently scoped resource in another. Existing attempt force-submit locks session only after reading attempt; refactor ordering and lock attempt for concurrent submission to avoid optimistic-lock surprises. Missing/wrong-scope target is denied, already SUBMITTED is a safe no-op. Flag the selected explicit attempt only.

Violation append currently reads chain head without an explicit repository lock despite its comment promising no race. Add a locked owned-session query before advancing sequence/hash; test two concurrent flags. Dispatch broadcasts only after commit; both current violation/command services broadcast inside the transaction. Otherwise the UI can observe rolled-back records. Retain existing domain notification event behavior.

## STOMP recommended implementation

`proctoring/internal/config/WebSocketConfig.java` already uses simple broker `/topic`, `/queue`, application prefix `/app`, endpoint `/ws`, no SockJS. `StompAuthChannelInterceptor` only verifies CONNECT. `ProctorStompController` checks PROCTOR per handler, but uses connect-time roles indefinitely.

1. Maintain authenticated session registry keyed by simpSessionId containing validated CurrentUser, token expiresAt (not raw JWT), and subscription destination→exam IDs. Capture CONNECT/SUBSCRIBE/UNSUBSCRIBE/DISCONNECT; remove abandoned entries.
2. Inbound allowlist exact SEND patterns for open/commands/violations and exact SUBSCRIBE `/topic/proctor-sessions/{uuid}` plus own `/user/queue/proctor-session`, existing `/user/queue/errors`, and added correlated queues. Deny direct `/topic` or `/queue` writes, wildcard topic subscriptions, foreign `/user/{id}` subscriptions, malformed destinations. Require current tenant, valid unexpired connection, role, assignment and ownership where applicable. SUBSCRIBE allows assigned read scope even after CLOSED; control SEND requires open gate.
3. Add an **ExecutorChannelInterceptor.beforeHandle on clientOutboundChannel**. Retrieve the *recipient* by simpSessionId and subscription registry, not the producer's simpUser. Immediately before WebSocket handler dispatch, recheck current assignment + tenant + identity active PROCTOR membership + token expiry for exam-topic messages. Drop denied deliveries by returning null. Private responses are checked for recipient ownership and expiry but close/rejection responses must not require current assignment. This covers subscriptions created before revocation and messages queued before revocation. An optional post-commit assignment-revoked event can proactively disconnect affected transport sessions, but it is not a substitute for per-delivery gating.
4. Preserve the raw legacy topic shapes. Command request broadcast is not success. Violation event broadcast is observation, not a unique acknowledgement of the current user's write (another proctor can flag the same target/category).

Define “no new delivery after revocation” as no dispatch newly authorized after revocation commits; bytes already written before revocation cannot be retracted. Integration test with outbound executor blocked: enqueue event, revoke assignment and commit, release executor; denied recipient receives nothing, authorized peer does. Test new event after revoke, plus topic subscribe denial, mutation denial, and revoked resume. This is stronger than only checking SUBSCRIBE once.

The Framework's executor interceptor callback runs immediately before the target handler and can return null to suppress it: [ExecutorChannelInterceptor API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/messaging/support/ExecutorChannelInterceptor.html). The ordinary authorization interceptor is driven by message user headers: [Spring STOMP authorization](https://docs.spring.io/spring-framework/reference/web/websocket/stomp/authorization.html). Apply the project's resolved Spring version in code, not an arbitrary dependency upgrade.

## Correlated errors and save acknowledgement

Current errors already go to `/user/queue/errors` as `{status,code}`; preserve this legacy queue. Add optional native STOMP header `requestId` for new clients rather than changing existing command/violation topic DTOs. Add private `/user/queue/proctor-errors` with `{requestId,operation,targetPublicId,status,code}`; controller handlers and validation/domain exception handlers retain headers to associate failures. Transport-auth failures before controller invocation also need safe ERROR/disconnect behavior; do not assume MessageExceptionHandler handles channel-interceptor exceptions.

Add `/user/queue/proctor-results` for write acknowledgement, scoped to originating socket with `@SendToUser(broadcast=false)` or equivalent simpSessionId targeting. Violation response `{requestId,operation:"FLAG_VIOLATION",targetPublicId,outcome:"SAVED",eventPublicId,occurredAt}` is delivered only after commit and discharges exactly that pending request. Command response can acknowledge APPLIED/NO_OP but must not replace authoritative SUBMITTED snapshot confirmation. Open response remains existing DTO; new request is single pending open with 10-second timeout, and correlation may be carried as private response native header or additive result. No durable command journal or idempotent automatic replay is introduced. Legacy clients without requestId keep existing behavior.

## Frontend lifecycle reuse and gap

Reuse tenant `lib/apiClient.ts` → UI `createSessionApiClient`, UI `sessionStorage.getAccessToken()`, `getSessionGeneration`, and `subscribeSessionLifecycle`. `app/providers.tsx` already cancels/clears TanStack cache on identity lifecycle. But **sessionLifecycle deliberately does not notify on token refresh**; `useSessionManager` therefore is not a token-refresh observer. New WS code must obtain current token in `beforeConnect`, track token expiresAt, and use one shared refresh mechanism instead of separately rotating the refresh token while HTTP refresh runs.

Recommended small shared extension: expose a generation-safe `ensureFreshAccessToken()` using the same in-flight refresh promise as HTTP client, plus a separate token-update notification that does not clear caches or change session generation. WS renews before expiry, reconnects with latest token, resubscribes and reopens through authorization; it never retries command/flag automatically. Preserve identity/tenant/role lifecycle semantics and test simultaneous HTTP+WS refresh and stale old-account results. `sessionStorage` currently uses localStorage; do not introduce another token store or token-bearing URL/log. WS owner is mounted per room and disposes on unmount/workspace switch/logout; 5-second polling stops on 403 and when hidden.

## Spec-to-code adjustments to record in plan

1. User explicitly approved design in this turn; root is updating status metadata without changing approved P1 scope.
2. Existing error queue exists already; use an additive correlated queue, not a replacement. Real topic DTOs do not contain actor/correlation; preserve them.
3. Define manual counter and label, authoritative latest aggregate semantics, and absence of server-filter controls in MVP explicitly.
4. Existing auth lifecycle is not a token refresh event; plan a shared single-flight refresh extension, otherwise “refresh/reconnect” is underspecified and can race refresh token rotation.
5. Existing assignment removal and command reads need shared lock ordering and outbound async-dispatch authorization, not just an event that eventually disconnects.
6. SessionStatus is DRAFT/PREPARING/READY/SCHEDULED/OPEN/CLOSED/CANCELLED; UI must handle all values, not a fictional three-state enum.
